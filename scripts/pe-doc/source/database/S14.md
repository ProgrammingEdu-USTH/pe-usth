# S14 · Functions và stored procedures

Chặng: core. Điều kiện trước: S07,S12-S13. Nguồn đối chiếu: Database System Concepts7e,5.2; USTH Lecture7; [MySQL routines](https://dev.mysql.com/doc/refman/8.4/en/create-procedure.html). Mức thực thi: mã MySQL8.4 trên database học; cần quyền CREATE ROUTINE, chưa phải log xác minh mọi routine.

## Phép tính được đặt tên và công việc được gọi

Một stored function trả về một giá trị, thường dùng trong biểu thức. Một stored procedure được gọi như một công việc, có thể nhận tham số, trả result set hoặc tham số OUT. Chúng được lưu trong database catalog; ứng dụng có thể gọi thay vì gửi lại mọi câu SQL. Tách hai vai giúp chọn giao diện phù hợp: công thức line_total là giá trị; “lấy báo cáo khách của một thành phố” là một thao tác trả bảng.

Không nên kết luận routine luôn nhanh hơn câu SQL thường vì “chỉ biên dịch một lần”. Hiệu năng phụ thuộc engine, plan, dữ liệu, số round-trip và mã thực thi. Khóa dùng routine để gom quy tắc và tạo giao diện rõ, còn hiệu năng cần đo thực tế.

## Function thuần không đọc bảng

```sql
CREATE FUNCTION pe_line_total(
  p_quantity INT,p_unit_price DECIMAL(10,2),p_discount DECIMAL(4,2)
) RETURNS DECIMAL(12,2)
DETERMINISTIC
NO SQL
RETURN p_quantity*p_unit_price*(1-p_discount);

SELECT pe_line_total(2,30,0) AS total_a,
       pe_line_total(1,120,0.10) AS total_b;
```

Kết quả dự kiến60.00 và108.00. DETERMINISTIC là cam kết cùng input cho cùng output; NO SQL nói routine không truy cập dữ liệu SQL. MySQL không tự chứng minh mọi lời khai của tác giả là đúng. Nếu function đọc thời gian hiện tại hoặc bảng thay đổi, không tùy tiện gọi nó deterministic để vượt kiểm cấu hình.

RETURNS DECIMAL(12,2) đặt miền đầu ra; thiết kế thực tế cần kiểm đủ độ lớn và quy tắc làm tròn. Input NULL có thể làm công thức ra NULL; quantity âm không tự bị loại chỉ vì item table có CHECK. Function nhận tham số trực tiếp, nên muốn bảo vệ chúng phải định nghĩa xử lý input riêng hoặc nêu tiền điều kiện.

## Procedure có tham số IN

```sql
DELIMITER //
CREATE PROCEDURE pe_customers_by_city(IN p_city VARCHAR(40))
BEGIN
  SELECT customer_id,customer_name,city
  FROM customers
  WHERE city=p_city
  ORDER BY customer_id;
END//
DELIMITER ;

CALL pe_customers_by_city('Hanoi');
```

Kết quả An và Dung. p_city là biến tham số, không phải tên cột. Tiền tố p_ giúp tránh câu `WHERE city=city` vô tình luôn đúng cho giá trị không NULL. Với p_city NULL, phép bằng không chọn Chi; nếu muốn “NULL nghĩa là tìm khách thiếu city”, phải viết nhánh IS NULL hoặc điều kiện null-safe có chủ đích.

DELIMITER là lệnh của client hỗ trợ nhập routine có nhiều dấu chấm phẩy nội bộ; không phải SQL server cần thực thi như một câu nghiệp vụ. Khi gửi CREATE PROCEDURE qua driver, thường gửi toàn bộ định nghĩa theo API thay vì gửi lệnh DELIMITER. MySQL dùng CALL; không bê EXEC/GO/AS của SQL Server vào mẫu này.

## OUT và ranh giới transaction

```sql
DELIMITER //
CREATE PROCEDURE pe_count_paid(OUT p_total INT)
BEGIN
  SELECT COUNT(*) INTO p_total FROM orders WHERE status='paid';
END//
DELIMITER ;

CALL pe_count_paid(@paid_count);
SELECT @paid_count;
```

Giá trị dự kiến3, gồm order103 chưa có item. Biến @paid_count thuộc phiên client; tham số p_total là phần giao diện routine. OUT không tự tạo một cột hay một bảng mới.

Procedure có thể sửa dữ liệu; khi thiết kế cần nói bên gọi hay procedure chịu trách nhiệm COMMIT/ROLLBACK. Một procedure tự COMMIT có thể phá kỳ vọng của người gọi đang nhóm nhiều thao tác. Routine cũng cần quyền thích hợp; quyền thực thi không đồng nghĩa người dùng được quyền chạy mọi SQL tùy ý bên trong một chuỗi nhập vào.

## Luyện tập

1. Dự đoán `pe_line_total(5,10,0.20)` và input discount NULL. Nêu một tiền điều kiện cần có nếu function dùng cho bán hàng thật.
2. Sửa procedure city để khi p_city NULL thì chỉ trả khách city NULL, còn p_city có giá trị thì lọc bằng giá trị ấy. Không dùng nối chuỗi SQL động.
3. Vận dụng: viết procedure nhận p_customer_id, trả result set các order_id,status của người đó theo mã tăng dần. Dự đoán CALL cho1,4 và999.

## Gợi ý

Tầng1: input function không tự được CHECK của bảng bảo vệ. Tầng2: có thể dùng `(p_city IS NULL AND city IS NULL) OR city=p_city`. Tầng3: không có order thì result set rỗng, không tạo một order NULL.

## Đáp án và tiêu chí tự kiểm

1.40.00 vàNULL. Tiền điều kiện ví dụ quantity>0, unit_price>=0, discount trong[0,1], các input bắt buộc không NULL. Khai báo DETERMINISTIC không kiểm những điều đó.
2. Thay WHERE bằng `(p_city IS NULL AND city IS NULL) OR (p_city IS NOT NULL AND city=p_city)`. CALL(NULL) trả Chi; CALL('Hanoi') trả An,Dung. Giữ ORDER BY để output contract xác định.
3. Body: `SELECT order_id,status FROM orders WHERE customer_id=p_customer_id ORDER BY order_id;`, giao diện IN p_customer_id INT. Cho1 trả100,101; cho4 và999 đều rỗng. Nếu muốn phân biệt “khách có tồn tại nhưng chưa có đơn” với “mã không tồn tại”, phải thêm cơ chế kiểm/giao diện khác, không suy ra từ một result set rỗng.

## Biến thể và lỗi thường gặp

Tạo tham số có giá trị không có kết quả, NULL và giá trị có nhiều kết quả. Ca biên gọi routine sau khi đổi schema có thể lỗi hoặc đổi ý nghĩa; cần quản lý version đối tượng. Lỗi trộn dialect được phản hồi bằng một mẫu MySQL tối thiểu và phân biệt client directive với server SQL.

## Điều cần giữ lại

Bạn cần thiết kế được input/output, phân biệt function/procedure, giải thích NULL và trách nhiệm transaction. Routine là một hợp đồng thực thi; việc cất code vào database không tự chứng minh code đúng, nhanh hay có quyền an toàn.
