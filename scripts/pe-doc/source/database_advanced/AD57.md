# AD57 · PostgreSQL: types, functions và FDW

Đã học: AD14, AD55; S18 và O07 của bộ 85 bài. Nguồn: DSC7e online §32.6–32.7. Môi trường web: runner PostgreSQL với role/schema dùng một lần; FDW có remote endpoint do backend dựng sẵn. Người học không nhập credential server hoặc cài extension trên máy cá nhân.

Một ứng dụng có quy tắc “phí không âm” và dùng nó ở nhiều bảng. Nhóm đang chép cùng CHECK vào từng cột; một chỗ quên CHECK nên dữ liệu sai lọt qua. PostgreSQL cho phép đưa một số quy tắc vào domain hoặc kiểu mở rộng, nhưng không phải mọi invariant nghiệp vụ đều là một kiểu dữ liệu. Chọn đúng lớp mở rộng giúp tái dùng quy tắc mà không che mất giới hạn.

## Type system không chỉ là tên SQL

Một type có cách biểu diễn, phép nhập/xuất, operator và các hàm liên quan. Kiểu base là kiểu nền có cơ chế lưu/đọc của nó; composite type là một tuple có các trường; array chứa các phần tử của một type; domain thêm ràng buộc trên type đã có; enum cho tập nhãn có thứ tự đã định nghĩa. PostgreSQL còn có các kiểu range và những pseudo/polymorphic types phục vụ chữ ký hàm. Một pseudo-type dùng làm hợp đồng hàm không có nghĩa người học tạo cột table với nó như một type thông thường.

Một table cũng có row type tương ứng, nhưng table là dữ liệu được quản lý và row type là mô tả cấu trúc một giá trị. Thêm field hoặc đổi type có thể ảnh hưởng hàm/view/client đang dùng kiểu đó. Khi migrate, phải kiểm dependency chứ không chỉ thử một INSERT. Với JSONB/array, khả năng lưu dữ liệu linh hoạt không xóa nhu cầu xác định shape, NULL/missing và invariant.

## Ví dụ 1: domain, enum và NULL

Fixture SQL PostgreSQL riêng:

```sql
CREATE DOMAIN ad_nonnegative AS numeric(10,2)
  CHECK (VALUE >= 0);
CREATE TYPE ad_invoice_state AS ENUM ('new','paid','cancelled');
CREATE TABLE ad_invoice (
  id integer PRIMARY KEY,
  amount ad_nonnegative NOT NULL,
  state ad_invoice_state NOT NULL
);
INSERT INTO ad_invoice VALUES (1,20,'paid'),(2,0,'new');
SELECT id,amount,state FROM ad_invoice ORDER BY id;
```

Expected hai hàng(1,20.00,paid),(2,0.00,new). INSERT amount=-1 bị ràng buộc domain từ chối; state='closed' chưa phải nhãn hợp lệ nên bị từ chối. Domain CHECK(VALUE>=0) không thay NOT NULL: trong logic CHECK, NULL cần được xử lý theo hợp đồng; bảng dùng NOT NULL để cấm không có amount. Tương tự, enum không tự diễn workflow chỉ cho new→paid hoặc new→cancelled; nó chỉ giới hạn nhãn và quy ước thứ tự của type. Chuyển trạng thái hợp lệ còn là invariant liên giá trị cũ/mới.

Nếu giá cần ít nhất một decimal và không vượt budget của một hàng khác, domain một cột không tự kiểm toàn yêu cầu ấy. Một type dùng lại ở nhiều bảng cũng trở thành dependency dùng chung: sửa type/rule cần xem tác động đến dữ liệu đã có và ứng dụng cũ. “Ít dòng SQL hơn” chưa phải lý do đủ để chọn domain thay bảng danh mục hoặc constraint riêng.

## Function signatures, overload và casts

Function có tên, type các đối số, type trả về và những metadata hành vi. Hai hàm cùng tên khác loại đối số là overload; lời gọi cần được phân giải theo type thực và các phép cast hợp lệ. Literal chưa có type rõ có thể tạo ambiguity, nên ví dụ/lab cần khai báo cast tại nơi cần, không để checker chỉ thử đúng một literal tình cờ phân giải được.

Hàm scalar trả một giá trị; hàm trả set/table cung cấp nhiều tuple. Composite result phải có schema đúng; NULL của cả composite khác một composite có các field NULL. Polymorphic signature có thể ràng buộc type đối số và kết quả với nhau, chẳng hạn phần tử/array; nó không phải “hàm nhận bất cứ byte nào rồi tự đoán”. Cast implicit, assignment hoặc explicit có mức sử dụng khác nhau; thêm cast toàn cục có thể đổi cách nhiều query được phân giải.

Ví dụ 2, một hàm phí có hợp đồng đơn giản:

```sql
CREATE FUNCTION ad_fee(amount numeric, rate numeric)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE STRICT
AS $$ SELECT round(amount*rate,2) $$;
SELECT ad_fee(100.00,0.05) AS fee,
       ad_fee(NULL::numeric,0.05) AS missing_fee;
```

Expected fee=5.00 và missing_fee=NULL. STRICT nói với hệ không gọi hàm cho những input NULL theo quy ước ấy, mà trả NULL. Nó không kiểm amount≥0 hoặc rate trong [0,1]; nếu brief cần hai điều này, thêm kiểm input hoặc type/rule phù hợp. Hàm mới phải nêu rounding/precision; hai cách tính phí line-level rồi SUM và SUM rồi tính phí không luôn bằng nhau khi làm tròn.

IMMUTABLE cam kết cùng đối số cho cùng kết quả không phụ thuộc trạng thái thay đổi của database hoặc môi trường được phép biến đổi. STABLE và VOLATILE có hợp đồng khác về khả năng thay đổi/quan sát trong statement; không gán nhãn chỉ để optimizer dùng index. Một hàm đọc bảng discount hiện tại không trở thành immutable vì “tên và id khách giống nhau”. Nếu discount đổi giữa hai thời điểm, cùng id có kết quả đúng khác; metadata immutable ấy đã nói sai, cho phép tối ưu dựa trên một giả định không còn đúng.

Parallel safety là một phân loại riêng: kết quả xác định chưa bảo đảm hàm có thể được gọi trong parallel worker. Hàm có side effects/session state cần đánh giá riêng. Hàm SECURITY DEFINER cũng có hợp đồng quyền khác invoker; role, search_path và object có thể bị thay thế phải được backend quản lý. Khóa học không cho người học tạo một hàm có quyền cao trong database dùng chung để thử chuyện này.

## Aggregate có state khác function scalar

§32.6.2.2 còn mô tả aggregate do người dùng định nghĩa: transition nhận state cũ và input tiếp theo, final biến state cuối thành kết quả. Ví dụ mới dưới tính mean của các numeric không NULL. State là mảng đúng hai phần tử `[sum,count]`, được aggregate khởi tạo bằng `[0,0]`; đây là contract riêng, không dùng một mảng tùy ý làm state:

```sql
CREATE FUNCTION ad_mean_step(s numeric[],x numeric)
RETURNS numeric[] LANGUAGE SQL IMMUTABLE
AS $$ SELECT CASE WHEN x IS NULL THEN s
                  ELSE ARRAY[s[1]+x,s[2]+1] END $$;
CREATE FUNCTION ad_mean_finish(s numeric[])
RETURNS numeric LANGUAGE SQL IMMUTABLE STRICT
AS $$ SELECT CASE WHEN s[2]=0 THEN NULL ELSE s[1]/s[2] END $$;
CREATE AGGREGATE ad_mean(numeric) (
  SFUNC=ad_mean_step, STYPE=numeric[],
  FINALFUNC=ad_mean_finish, INITCOND='{0,0}'
);
SELECT ad_mean(x) FROM (VALUES (10::numeric),(NULL::numeric),(20::numeric)) AS t(x);
```

Expected 15 theo giá trị numeric; output scale tùy phép chia, không chấm chuỗi cố định `15.00`. Trace state `[0,0]→[10,1]→[10,1]→[30,2]`, final trả 30/2. Với input rỗng hoặc toàn NULL, state vẫn `[0,0]`, final trả NULL, tránh chia cho 0. Step cố ý không STRICT vì nó cần xử lý x=NULL; copy nhãn STRICT từ ví dụ scalar mà không xét state/null contract có thể đổi giao thức gọi.

Bất biến sau một prefix: s[1] bằng tổng các input không NULL đã xử lý và s[2] bằng số input ấy. Nhánh NULL giữ nguyên hai giá trị; nhánh còn lại cộng đúng một giá trị và tăng count một, nên bất biến giữ theo quy nạp. Input hữu hạn thì quá trình kết thúc; final trả mean nếu count>0. State có hai trường, nhưng kích thước numeric và chi phí số học tăng theo độ chính xác/độ lớn; không được gọi mọi phép cộng numeric là O(1) trên miền không giới hạn. Ví dụ không khai combine/serialize functions hay parallel aggregate support; một aggregate chạy tuần tự đúng chưa tự trở thành aggregate phân tán đúng. Các SQL này là lời giải biên soạn, chưa được chạy PostgreSQL trong lượt audit.

## Operators, operator classes và index

Một operator SQL gắn cú pháp với function và metadata; cú pháp gọn không tự làm nó tương thích mọi access method. B-tree cần quan hệ thứ tự nhất quán, hash cần quy tắc bằng nhau và hash phù hợp, GiST/GIN cần những support functions/operator classes theo hợp đồng của access method. Operator family nhóm các quan hệ/operator liên quan giữa các type theo cấu trúc hệ hỗ trợ.

Ví dụ mô hình: định nghĩa x≈y khi x mod 10=y mod 10. Khi đó 3≈23 đúng. Nếu custom hash index dùng hash(x)=x cho phép so này, 3 và 23 có thể vào bucket khác và một lookup bỏ sót match. Tính chất bắt buộc là a≈b kéo theo hash(a)=hash(b), không phải “hàm hash chạy nhanh”. Một custom operator bị khai báo equality/commutator sai có thể làm tối ưu trả kết quả sai, không chỉ làm chậm.

Tương tự, B-tree comparator phải tạo một thứ tự tổng thích hợp với equality theo hợp đồng operator class. Comparator không bắc cầu có thể làm một key không tìm được sau khi chèn dù từng phép so riêng có vẻ hợp lý. Để kiểm, cần những bộ a,b,c làm lộ consistency/order, ngoài các ca query thông thường. Viết extension C cho type/index đi qua AD58/AD84; bài này không nhận một tên operator mới là một access method đã được kiểm đúng.

Procedural languages như PL/pgSQL cung cấp cách viết function/trigger phía server; language trusted/untrusted, quyền tạo và resource limit cần môi trường phù hợp. SQL-language function, C function và stored procedure có khác nhau về interface/lifecycle. Dev phải dùng đúng engine/version chứ không chạy nguyên DELIMITER hoặc cú pháp MySQL trong runner PostgreSQL.

## Ví dụ 3: foreign data wrapper và ranh giới hệ thống

FDW biểu diễn một nguồn ngoài bằng foreign table trong PostgreSQL. Một wrapper có các callback/capability để lập plan và lấy dữ liệu từ nguồn ấy; không phải mọi wrapper hỗ trợ cùng kiểu predicate, join, aggregate, update hoặc transaction. Foreign table metadata là một lời mô tả nguồn; nếu type/encoding/timezone mapping sai, query local vẫn có thể lỗi hoặc đổi nghĩa.

Backend chuẩn bị remote table Customers(id,city) với(1,Hanoi),(2,Hue),(3,Hanoi), và local Orders(order_id,customer_id) với(10,1),(11,1),(12,2). Foreign table local được đặt ad_remote_customer(id,city), local table ad_local_order có ba hàng ấy. Query:

```sql
SELECT c.city,COUNT(*) AS order_count
FROM ad_local_order AS o
JOIN ad_remote_customer AS c ON c.id=o.customer_id
GROUP BY c.city ORDER BY c.city;
```

Expected theo dữ liệu đầy đủ: Hanoi 2, Hue 1. Runner phải dựng nguồn ngoài và wrapper thật trước khi gắn nhãn FDW lab; một local table đổi tên remote không đủ. EXPLAIN VERBOSE có thể giúp xem công việc nào được gửi sang nguồn, nhưng output/Remote SQL phụ thuộc wrapper và plan thực, nên không có một chuỗi plan cố định được in sẵn là kết quả vừa chạy.

Nếu chuyển `WHERE c.city='Hanoi'` sang nguồn làm giảm dữ liệu chuyển, đó là pushdown. Nó chỉ đúng khi nguồn hỗ trợ semantics tương thích về type/collation/function và snapshot cần thiết. Nếu một function chỉ có local, nguồn không xử lý được nguyên predicate ấy; planner có thể cần giữ local filter. “Ít bytes mạng hơn” chưa đủ chứng minh rewrite đúng.

Hai foreign sources không tự chia sẻ một global snapshot hoặc một atomic commit chỉ vì cùng được SELECT trong một query local. Với báo cáo cần một mốc thời gian nhất quán, phải có giao thức/phiên bản dữ liệu/cam kết nguồn phù hợp. Với ghi liên hệ thống, capability của FDW và transaction manager phải được kiểm; không hứa 2PC từ cú pháp JOIN hoặc BEGIN duy nhất. AD49/AD65 phân tích phần phân tán đó sâu hơn.

## Chọn điểm mở rộng đúng lớp

Nếu chỉ cần chuẩn hóa một giá trị, domain/function có thể đủ. Nếu cần shape nhiều field, composite có ích. Nếu cần operator có index support, phải thiết kế cả semantics và access-method contract. Nếu cần truy cập nguồn ngoài, FDW giải bài toán interface/plan nhưng không tự giải correctness nghiệp vụ xuyên nguồn. Có thể ghép nhiều lớp, song mỗi lớp cần input/output và điều kiện thất bại riêng.

Một bản bàn giao extension tối thiểu có type signature, NULL/rounding policy, volatility/parallel/security classification, fixture đúng/sai, expected và engine version. Với FDW thêm schema nguồn, capability, quy tắc snapshot/quyền và ca mất kết nối. Những trường này phục vụ dev/checker; không cần đẩy toàn bộ metadata triển khai lên màn hình bài đầu tiên của người học.

## Chọn type theo phép toán cần làm

SQL variation được nhận diện bằng feature và semantics thực: một kiểu có trong PostgreSQL nhưng không có cùng syntax/behavior ở MySQL cần runner PostgreSQL hoặc mô hình rõ, không dịch tên type rồi nhận portability. Base type có representation/I/O; composite là record fields; domain tái dùng constraint; enum ràng nhãn; array có element type; pseudo-type mô tả interface hàm. PostgreSQL có cả họ polymorphic anyelement/anyarray ràng type tương ứng và họ anycompatible cho phép chọn common type theo quy tắc riêng. Ví dụ identity(anyelement) nhận integer thì trả integer; signature không có input định type mà đòi trả anyelement không có đủ thông tin phân giải. Không dùng danh sách pseudo-types lịch sử trong sách như danh sách toàn bộ bản 18. [Pseudo-types](https://www.postgresql.org/docs/18/datatype-pseudo.html).

Ví dụ composite độc lập `CREATE TYPE ad_point_label AS (label text,x numeric,y numeric)` định nghĩa shape giá trị dù chưa có table. Row type sinh từ một table cũng không tự mang mọi CHECK/NOT NULL của table khi dùng làm giá trị ở nơi khác. Mô hình label='A',x=2,y=3 có ba field; array[2,3] chỉ hai numeric và thiếu label nên không là cùng contract. Domain thích hợp cho hạn chế giá trị dùng lại, còn quy tắc “tổng đặt chỗ không vượt một row capacity khác” cần transaction/constraint ở lớp tương ứng, không ép vào một domain CHECK đọc table thay đổi.

Geometric types point/line/lseg/box/path/polygon/circle mang phép toán không gian 2D, không tự bảo đảm mô hình tọa độ địa lý của Trái Đất. Full text dùng tsvector chứa lexemes/positions và tsquery chứa điều kiện; chọn text-search configuration khi chuyển raw text quyết định stemming/stop words. Ví dụ `to_tsvector('simple','sql lock') @@ to_tsquery('simple','sql & !wal')` expected true theo hai lexemes đã có. Điều này khác substring LIKE '%sql%' và không chứng minh tìm mọi biến thể tiếng Việt; lab phải ghi configuration. Network types inet/cidr nhận IPv4/IPv6, hỗ trợ subnet/operator và validation; inet có thể biểu diễn host kèm mask còn cidr yêu cầu phần host bits bằng 0. MAC là hardware address type riêng, không phải chỉ thêm dấu ':' vào IP. Bit string có chiều dài và bit operators, không là integer tự động bỏ leading zeros.

XML type kiểm well-formedness theo context và cung cấp XML operations; không tự xác nhận tài liệu đúng mọi schema nghiệp vụ. JSON giữ representation text, JSONB phân rã để xử lý/index và không giữ whitespace/key order/duplicate-key text như JSON. Ví dụ JSON text `{"x":1,"x":2}` giữ văn bản ấy; JSONB chỉ giữ một giá trị theo quy tắc duplicate key của hệ, nên không chọn nó cho yêu cầu lưu nguyên bản payload ký số. Missing key khác key có JSON null, lại khác SQL NULL. Đây là quyết định dữ liệu trước quyết định index. [Types PG 18](https://www.postgresql.org/docs/18/datatype.html).

## Một type mở rộng cần đủ đường nhập, lưu và thao tác

Catalog lưu cả types/functions/operators/access methods nên extension có thể đăng ký qua DDL thay vì sửa mọi nhánh hard-code của server. Dynamic loading đưa module vào backend; CREATE FUNCTION chỉ đăng ký metadata/đường symbol, không compile C. Module SQL, control file, version/update script và dependency là các phần của một extension có thể quản lý; built-in và extension dùng nhiều interface giống nhau nhưng code C không vì thế trở thành sandbox an toàn tự động. `contrib` là nơi có các module bổ sung đi cùng source, không khẳng định mọi module ngoài đều được cài/cho phép trên runner.

Mô hình type `ad_pair` có hai số nguyên nhỏ x,y, format text `(x,y)`. Input parser phải xác nhận delimiter, đúng hai số, miền/overflow và không bỏ trailing junk; output dùng format chuẩn. Contract round trip là parse(print(v))=v cho mọi giá trị hợp lệ, không buộc print(parse(s)) giữ nguyên whitespace của input. Với v=(-2,7), print→'(-2,7)',parse trả cặp ấy; '(2,7)junk' phải bị từ chối theo contract. Base type native còn cần length/alignment/pass-by-value/by-reference đúng và binary I/O nếu cung cấp; không đăng ký struct bằng internallength tùy ý rồi đọc pointer như mọi machine có cùng ABI. Composite SQL thường đủ nếu chỉ cần hai field, giảm phần C phải chứng minh.

Định nghĩa operator/index cho ad_pair cần tách equality của cả cặp với order theo một tiêu chí. Nếu order chỉ theo x²+y², cặp(3,4) và (0,5) có cùng độ lớn; gắn operator '=' là equality hai tọa độ nhưng comparator trả0 cho hai cặp khác ấy phá consistency của B-tree opclass. Có thể thiết kế order từ điển (magnitude,x,y) với số học miền không overflow, hoặc định nghĩa quan hệ equivalence theo magnitude và công bố đúng nghĩa của operator. Với hash, equal phải kéo theo hash bằng nhau; với B-tree, thứ tự phải bắc cầu và nhất quán với equality. Strategy operators nối WHERE với access method; support routines như comparator/hash phục vụ vận hành nội bộ. Chỉ khai năm tên operator chưa chứng minh các luật ấy.

PL/pgSQL có variables/control flow và là trusted language theo mô hình quyền của hệ; trusted không có nghĩa function nào cũng vô hại hoặc không giữ locks. PL/Perl/PL/Tcl có biến thể trusted/untrusted theo installation, PL/Python là untrusted; availability/quyền tạo phải kiểm backend. Ví dụ loop gọi một UPDATE cho mỗi row vẫn có thể N+1 work dù chạy server-side; ưu tiên SQL theo tập khi giữ đúng semantics. Function/procedure có khác biệt transaction control và calling interface, nên code `CALL` không thay mọi `SELECT f()` theo tên giống nhau.

Có thể viết đầy đủ parser cho model ad_pair mà chưa đụng ABI. Chọn miền mỗi tọa độ là integer trong `[-32768,32767]`, grammar chính xác là `(`, một integer có dấu trừ tùy chọn, `,`, một integer, `)` rồi hết input; không cho whitespace. Parser dùng số nguyên toán học trong pseudocode:

```text
read_integer(s,i):
    sign := +1
    if s[i] là '-': sign := -1; i := i+1
    require còn ít nhất một chữ số ở i
    limit := 32768 nếu sign=-1, ngược lại 32767
    v := 0
    while i còn trong s và s[i] là chữ số:
        digit := giá trị chữ số s[i]
        require v <= floor((limit-digit)/10)
        v := 10*v+digit; i := i+1
    return (sign*v,i)

parse_pair(s):
    require ký tự đầu là '('; i := 1
    (x,i) := read_integer(s,i)
    require s[i] là ','; i := i+1
    (y,i) := read_integer(s,i)
    require s[i] là ')' và i+1=length(s)
    return (x,y)

print_pair(x,y):
    require x,y trong miền đã khai
    return '(' + decimal(x) + ',' + decimal(y) + ')'
```

Mọi phép đọc `s[i]` đều kiểm i còn trong chuỗi trước. Bất biến vòng chữ số: v là trị số của prefix đã đọc, 0≤v≤limit. Bất đẳng thức kiểm trước nhân/cộng giữ giới hạn; nếu thất bại thì số không thuộc miền. Vòng tăng i nên dừng sau O(length(s)) bước. `print_pair` ghi lại đúng hai số theo grammar, nên parse(print_pair(x,y))=(x,y); leading zeros hoặc `-0` có thể được parser nhận nhưng printer chuẩn hóa. Các ca `'(32768,0)'`, `'(2)'`, `'(2,7)junk'` bị từ chối, còn `'(-32768,32767)'` hợp lệ. Đây là grammar tự chọn cho model, không khẳng định là parser PostgreSQL của một base type đã cài.

## Dựng đường FDW và quan sát phần được push xuống

FDW cần bốn lớp: extension/handler thực hiện access, foreign server chứa connection endpoint/capability, user mapping ánh xạ local role sang quyền remote, foreign table mô tả schema đối tượng. Mapping không phải nhét password vào SELECT của học viên. Backend cấp fixture/credential giả đã giới hạn; learner chỉ chọn nguồn trên web và đọc metadata được phép. `file_fdw` đọc file hoặc output được backend cho phép theo COPY-compatible format và read-only; `postgres_fdw` truy cập PostgreSQL remote, có thể update theo capability/quyền. Bảng local đổi tên foreign không thử được đường network, authentication hay schema mapping.

Với remote Customer có 1.000 row và city Hanoi có 20 row, giả định mỗi row 100 byte: fetch toàn bộ rồi filter gửi 100.000 byte payload; filter pushdown chỉ gửi 2.000 byte trước protocol overhead. Nhưng một function local khác semantics remote thì không được push chỉ để lấy ít bytes. postgres_fdw kiểm những expressions phù hợp, có thể push joins giữa foreign tables cùng server khi an toàn/có lợi; join local Orders với remote Customer còn cần cost/strategy riêng. ForeignScan callback trả tuple tới executor; callback như GetForeignJoinPaths là chỗ cung cấp candidate path, không tự hứa optimizer luôn chọn remote join. EXPLAIN VERBOSE/Remote SQL thật giúp kiểm ranh giới ấy.

Một local transaction dùng postgres_fdw mở remote transaction tương ứng; remote snapshot của một nguồn được giữ thích hợp cho nhiều scan, với isolation mapping có quy tắc. Cùng mốc nguồn A không là global snapshot của A+B, và postgres_fdw không cung cấp prepare remote transactions cho 2PC. Mô hình hai remote nguồn: A hiển thị order đã chuyển nhưng B chưa cập nhật payment; một JOIN local vẫn có thể thấy trạng thái ghép chưa từng tồn tại ở một mốc chung. Cần publication/version watermark hoặc giao thức phù hợp nếu báo cáo đòi cutoff chung. Remote mất kết nối phải hiện lỗi/partial status theo contract, không silently dùng cache rồi gọi là kết quả hiện tại. [postgres_fdw PG 18](https://www.postgresql.org/docs/18/postgres-fdw.html).

## Luyện tập bổ sung

E1. Chọn domain/composite/array/enum/pseudo-type cho lần lượt số tiền không âm, nhãn cùng tọa độ, dãy numeric, trạng thái nhãn, chữ ký identity generic. Vì sao row type không thay mọi constraint table? Phân biệt anyelement với anycompatible và nêu một return type không phân giải được.

E2. Chọn representation cho host có mask,mạng subnet,tìm lexeme,các bit có leading zeros,XML well-formed và payload JSON phải giữ văn bản gốc. Phân biệt JSON missing/JSON null/SQL NULL. Vì sao point 2D không đủ khẳng định đúng khoảng cách địa lý?

E3. Viết input/output contract cho ad_pair, cho hai ca hợp lệ và hai ca invalid. Chứng minh round trip trên miền ấy; giải thích mâu thuẫn giữa equality tọa độ và comparator chỉ magnitude. Tại sao trusted language vẫn phải kiểm quyền/resource/transaction?

E4. Vẽ bốn lớp FDW, phân biệt file_fdw/postgres_fdw. Tính bytes mô hình 1.000→20 rows và nêu điều kiện pushdown đúng. Hai foreign tables cùng server so với local+remote có khác gì? Một BEGIN local có cho atomic 2PC/global snapshot không?

## Đáp án phần bổ sung

E1. Domain cho tiền với constraint,composite cho(label,x,y),array cho dãy,enum cho nhãn,pseudo/polymorphic cho interface identity. Constraint table không tự trở thành constraint của mọi composite value. anyelement ràng cùng actual type trong họ; anycompatible chọn common type theo quy tắc. Return anyelement không có input ràng type thiếu căn cứ; không dùng pseudo-type làm table column.

E2. inet cho host+mask,cidr cho network hợp lệ,tsvector/tsquery với configuration cho lexeme,bit/varbit cho bit length,xml cho well-formed input,JSON text cho văn bản gốc theo yêu cầu ấy. Key vắng không có JSON value; JSON null là value trong document; SQL NULL là không có giá trị cột/expression. Point2D chưa chọn hệ tọa độ/đơn vị/phép đo mặt cầu; cần model đúng nghiệp vụ. Type validation không thay domain-specific correctness.

E3. Miền x,y nhỏ khai báo rõ,parser đòi đúng hai integer/trailing delimiter,print canonical decimal. Ví dụ(0,0),(-2,7) round-trip; '(2,7)junk' và '(2)' bị từ chối. Với mỗi v,print ghi đủ x,y trong miền và parser khôi phục đúng hai giá trị nên parse(print(v))=v; phải kiểm miền/overflow của implementation riêng. (3,4),(0,5) có magnitude bằng nhưng coordinate equality false, nên comparator 0 không nhất quán '=' đã khai. Trusted giới hạn một số access nhưng code vẫn có thể tốn tài nguyên/giữ locks; metadata/quyền và contract vẫn cần.

E4. Handler/extension→server→user mapping→foreign table; file wrapper read-only format file,postgres wrapper nối remote PostgreSQL với quyền/capability riêng. Payload 100.000→2.000 byte trong mô hình, tiết kiệm 98.000 byte trước overhead. Chỉ push expressions/type/collation/function tương thích; remote join candidate cùng server có thể khác chiến lược local+remote. Local BEGIN không tự prepare mọi remote nguồn và không đồng bộ snapshots A+B. Cần hợp đồng lỗi/snapshot, plan thực và nguồn thật để nhận thực thi FDW; số mô hình không phải network measurement.

## Luyện tập

1. Domain ad_nonnegative có CHECK(VALUE>=0). Một table dùng cột domain nhưng không NOT NULL. Giải thích vì sao việc thiếu amount cần được xét riêng; thêm ràng buộc cho brief bắt buộc có giá trị.
2. Hàm price_for(customer_id) đọc bảng giá hiện tại nhưng được gắn IMMUTABLE để tạo expression index. Dựng hai trạng thái cùng input nhưng cần output khác; nêu metadata nào đang sai và vì sao sửa query chưa đủ.
3. Tự làm: viết function tính tổng phí từ amount và rate với rounding tới 2 chữ số, policy NULL rõ, cấm rate ngoài [0,1] theo cách chọn. Dùng ca 0, ca NULL, ca biên làm tròn và ca sai input; trả đúng type, không chỉ SELECT chuỗi đã format.
4. Với mô hình modulo10, chọn hash bảo đảm a≈b⇒hash(a)=hash(b), rồi giải thích vì sao tính chất này chưa chứng minh toàn custom hash index đúng. Với FDW, nêu hai thông tin còn thiếu trước khi coi một báo cáo local+remote là snapshot nhất quán.

## Gợi ý

Mức 1: một domain chỉ nói những điều được khai báo; một metadata function là lời cam kết mà optimizer được phép tin. Không gắn nhãn mạnh hơn hành vi.

Mức 2: câu 2 đổi giá trong table mà không đổi customer_id. Câu 3 phân biệt NULL policy với invalid-rate policy. Câu 4 hash từ phần dư là một lựa chọn, nhưng collision handling/build/concurrency còn phải đúng.

## Đáp án và lập luận

1. NULL không phải một số âm; domain CHECK không thay đầy đủ yêu cầu có giá trị. Thêm NOT NULL ở cột hoặc dùng domain với constraint phù hợp đã được kiểm theo cách sử dụng. Ca kiểm phải phân biệt NULL,0,-1 và giá hợp lệ.
2. Cùng customer 1, trước update giá 100, sau update 120. Hàm đúng phải trả khác dù đối số không đổi, nên không immutable. Đổi metadata và xem lại index/plan/dữ liệu phụ thuộc theo quy trình; không chỉ buộc gọi thêm một lần rồi tin index cũ còn đúng.
3. Chấp nhận SQL/PLpgSQL phù hợp nếu signature/rounding/NULL và input validation đúng. Ví dụ 100×0.05→5.00;0×rate→0.00; NULL theo policy; rate=-0.1 hoặc 1.1 bị từ chối nếu brief cấm. Test phải đối chiếu numeric, không coi chuỗi '5.00' là cùng contract với numeric nếu đề yêu cầu type. Lượt mở lời giải chỉ là có hỗ trợ.
4. hash(x)=x mod 10 đáp ứng tính chất trên lớp equality cho số nguyên với modulo được định nghĩa nhất quán. Cần kiểm representation, collision resolution, operator semantics, update/concurrency để nhận cả index đúng. Báo cáo FDW còn cần ít nhất snapshot/cutoff của từng nguồn và cách giữ một mốc chung, cùng capability/type mapping nếu có predicate pushdown. Có một BEGIN local không tự là bằng chứng.

Một lời giải thực chất cho câu 3 chọn NULL truyền qua, amount không âm, rate trong [0,1], và làm tròn **sau** một phép nhân numeric:

```sql
CREATE FUNCTION ad_fee_checked(amount numeric, rate numeric)
RETURNS numeric
LANGUAGE plpgsql IMMUTABLE STRICT
AS $$
BEGIN
  IF amount<0 OR amount='NaN'::numeric OR amount='Infinity'::numeric
     OR rate<0 OR rate>1 THEN
    RAISE EXCEPTION 'amount/rate outside the declared finite domain'
      USING ERRCODE='22023';
  END IF;
  RETURN round(amount*rate,2);
END;
$$;
SELECT ad_fee_checked(100,0.05);          -- expected 5.00
SELECT ad_fee_checked(0,1);              -- expected 0.00
SELECT ad_fee_checked(0.05,0.1);         -- expected 0.01
SELECT ad_fee_checked(NULL::numeric,1);  -- expected NULL
SELECT ad_fee_checked(10,1.1);           -- expected error 22023
```

Numeric NaN được PostgreSQL so lớn hơn các giá trị hữu hạn, nên kiểm rate>1 cũng loại NaN và +Infinity; rate<0 loại −Infinity. Với amount, các trường hợp vô hạn/NaN được loại theo policy hữu hạn vừa chọn; −Infinity cũng bị amount<0 loại. STRICT trả NULL trước khi vào thân hàm nếu bất kỳ đối số NULL: vì vậy `(NULL,1.1)` theo hợp đồng này trả NULL, không báo invalid-rate. Nếu brief muốn luôn kiểm rate kể cả khi amount NULL thì bỏ STRICT và viết nhánh kiểm NULL/input rõ; không thay metadata mà giữ nguyên lời hứa. Các expected trên được suy từ contract và semantics numeric, chưa là artifact chạy PostgreSQL của lượt này.

## Biến thể và cách kiểm

Biến thể function có NULL, numeric precision và domain boundary; type/metadata là một phần contract. Operator model có cặp equivalent và bộ so thứ tự không bắc cầu. FDW lab giữ source revision/schema/capability, có lỗi nguồn rõ. Checker không chỉ so tên function hoặc một output đẹp; phần thiết kế cần lập luận về metadata và boundary xuyên hệ.
