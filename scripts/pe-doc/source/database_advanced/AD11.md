# AD11 · SQL từ ứng dụng: transaction boundary và retry

Đã học: S18, A04, AD01. Nguồn: DSC 7e §5.1, §9.1–9.7. Môi trường thiết kế: workspace web có code dịch vụ và connector do backend cấp; đoạn JDBC là ví dụ API, pseudocode được ghi rõ. Người học không cài Java, Python hoặc database. Backend lab/driver là hợp đồng cần triển khai và kiểm, không là tuyên bố đã có MySQL đang chạy.

## Một lần bấm có thể tạo hai lần ghi

Trang thanh toán gửi yêu cầu tạo order. Server commit nhưng response bị mất. Người dùng bấm lại; một request giống hệt đến server. Không thể nhìn timeout mạng rồi kết luận transaction trước đã rollback. Nếu tạo mã order mới mỗi lần nhận request, cả hai lần có thể được ghi hợp lệ trong database nhưng sai ý định người dùng.

Cần phân biệt ba ranh giới: HTTP request; transaction database; và ý định nghiệp vụ có thể được thử lại. HTTP không tự gộp chúng. Một session đăng nhập có thể sống qua nhiều requests, trong khi một connection pool cho nhiều requests lần lượt mượn các kết nối. Không giữ transaction mở suốt thời gian người dùng xem form: vừa giữ tài nguyên, vừa làm quyết định phụ thuộc dữ liệu cũ.

## Ví dụ 1: tham số là giá trị, không phải cú pháp

Một dịch vụ nhận customer_id và trả các đơn paid. Prepared statement cố định cấu trúc query rồi bind dữ liệu. Trong JDBC, phần trọng tâm có dạng sau; `connection` là kết nối đã mượn từ pool, không phải biến do browser gửi:

```java
String sql = "SELECT id,amount FROM purchases "
           + "WHERE customer_id=? AND status=? ORDER BY id";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setInt(1, customerId);
    ps.setString(2, "paid");
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            emit(rs.getInt("id"), rs.getBigDecimal("amount"));
        }
    }
}
```

Với customerId=1, fixture có (101,100),(102,50). Dùng getBigDecimal giữ tiền đúng kiểu; getString có thể phù hợp để hiển thị nhưng không thay kiểu tính toán. ResultSet có vị trí cursor; `next()` mới đưa tới hàng đầu và trả false khi hết. Tên/kiểu cột có thể đọc từ metadata khi xây công cụ chung, nhưng không vì vậy tin mọi cột là được phép lộ ra API.

Bind `ORDER BY ?` bằng chuỗi `amount` không biến chuỗi thành tên cột; nó là một giá trị trong biểu thức. Nếu cho người dùng chọn sort, ánh xạ một enum đã kiểm vào đoạn SQL do tác giả kiểm soát. Không nối tùy ý tên bảng/cột từ request. ODBC là giao diện truy cập khác với cơ chế chuẩn bị, binding và lấy metadata tương ứng; placeholder và API phụ thuộc driver. Embedded SQL lại cần tiền xử lý mã nguồn, dùng host variables và indicator cho NULL. Ba cách cùng giải bài “chương trình trao đổi với DBMS” nhưng không có cùng bước compile hoặc cùng cú pháp.

Một cursor mở quá lâu có thể giữ tài nguyên server. Fetch size, pagination và streaming phải theo contract của driver; trả một triệu rows rồi chỉ hiển thị 20 hàng không phải pagination. CallableStatement gọi routine; nó không tự làm routine an toàn về quyền hay transaction.

## Ví dụ 2: chuyển tiền cần đúng một transaction

Giả sử accounts có hai hàng balance=100. Muốn chuyển 30 từ 1 sang 2, hai UPDATE phải commit cùng nhau. Nếu autocommit từng câu, lỗi sau lần trừ cho trạng thái 70,100. Tổng tiền giảm dù từng câu SQL đã chạy đúng.

Pseudocode dịch vụ:

```text
borrow connection
begin transaction
try:
    lock account1 and account2 in increasing id order
    reject if source balance < 30
    update source: balance = balance - 30
    update destination: balance = balance + 30
    commit
catch database error:
    rollback if transaction is still active
    classify error and report/retry according to operation policy
finally:
    restore session settings and return clean connection to pool
```

Khi thành công, số dư 70,130 và tổng 200. Nếu lỗi trước commit, rollback phải trả về 100,100. Lock theo cùng thứ tự giảm một lớp deadlock, không chứng minh mọi code path không deadlock. Transaction boundary thuộc business-logic layer; data-access layer không được âm thầm commit từng hàm nhỏ nếu nghiệp vụ cần ghép chúng.

Không trả connection còn transaction hoặc isolation/session variables đã thay sang request khác. Pool có tập connections idle/busy và hàng đợi mượn; bất biến là một connection không được trao đồng thời cho hai request. Khi trả, chỉ đưa vào idle sau khi rollback/cleanup thành công; connection hỏng bị loại. Pool hết chỗ cần timeout/backpressure, không tạo vô hạn connection để che tải. Giới hạn pool dựa workload/server, không lấy số request làm số kết nối bắt buộc.

## Ví dụ 3: retry phải biết điều gì được lặp

Một deadlock có thể làm DBMS hủy transaction. Retry toàn bộ transaction với đầu vào cố định thường phù hợp hơn chỉ chạy lại câu UPDATE cuối, vì các lần đọc trước có thể đã hết hiệu lực. Nhưng “không nhận được response commit” là trạng thái khác: kết quả commit chưa biết từ phía client. Lặp thao tác có side effect bên ngoài càng nguy hiểm.

Thiết kế một `request_id` duy nhất cho ý định nghiệp vụ. Trong cùng transaction, insert request_id vào bảng có UNIQUE, thực hiện chuyển và lưu kết quả. Nếu request_id đã có, trả kết quả đã lưu thay vì chuyển lần nữa. Nếu request_id giống nhưng payload khác, từ chối hoặc báo conflict; không nhận một key thành quyền sửa nội dung cũ. Client gửi lại cùng key cho cùng ý định; key mới cho ý định mới.

Trong mô hình đơn giản, tính đúng dựa UNIQUE bảo đảm nhiều nhất một transaction giữ bản ghi key đã commit; effect và result cùng commit nên không có trạng thái “key thành công nhưng chưa chuyển” sau commit hợp lệ. Trước commit, effect chưa được giữ bền như một kết quả hoàn tất. Đối với gửi email/thanh toán ngoài DBMS, transaction database không bao gồm server ngoài: dùng outbox hoặc protocol riêng. Nếu worker gửi rồi chết trước khi đánh dấu, vẫn có thể gửi lại; phía nhận cần idempotence hoặc deduplication. Không gọi một bảng key là giải pháp exactly-once end-to-end cho mọi hệ.

Retry loop có input là operation có chính sách lặp, số lần tối đa và deadline; mỗi vòng bắt đầu transaction mới, đọc lại dữ liệu, commit hoặc rollback. Nó dừng khi thành công, gặp lỗi không được retry hoặc hết budget. Backoff có jitter tránh mọi client đụng lại cùng lúc. Quota là điều kiện dừng vận hành; lý do đúng của operation là invariant và idempotence, không phải đợi đủ lâu.

## HTTP, UI và kiến trúc không làm biến mất concurrency

URL xác định resource/route; HTML form hoặc JavaScript gửi dữ liệu lên endpoint. Browser validation giúp người nhập sửa nhanh nhưng server vẫn kiểm kiểu, quyền và quy tắc nghiệp vụ. Một servlet thường có lifecycle do container quản lý; nhiều requests có thể dùng cùng instance nên field mutable theo request không được dùng như bộ nhớ riêng an toàn. JSP/server-side scripting/templates đặt HTML ở tầng trình bày; ORM/Django/Hibernate giảm mã mapping nhưng không tự chọn đúng transaction boundary hoặc ngăn N+1 query.

Responsive UI có thể gửi request bất đồng bộ; thứ tự response không nhất thiết giống thứ tự bấm. Gắn request/version để bỏ response cũ khi người dùng đã đổi filter. Khi offline, hàng đợi local phải lưu ý định và version; hòa giải conflict khi kết nối lại chứ không gửi một UPDATE mù dựa bản cũ. Mobile client cũng đối mặt cùng vấn đề.

Cache ở browser, application hoặc DBMS có scope/độ mới khác nhau. Cache số dư mà không có invalidation có thể hiển thị stale; một cache hit không được dùng để bỏ kiểm invariant trong transaction. Gửi nhiều request song song giảm latency khi độc lập nhưng làm concurrency thật tăng. Application architecture cần thể hiện rõ presentation, business logic và data access để các giới hạn này có chỗ kiểm, thay vì gộp mọi trách nhiệm vào một callback.

## Cầu nối giữa quan hệ SQL và biến chương trình

### A1 · Kết nối, gửi lệnh và đọc kết quả JDBC

SQL xử lý tập hàng; code dịch vụ còn phải đọc request, gọi dịch vụ khác và tạo response. Vì vậy cần một API nối hai mô hình. Dynamic SQL gửi chuỗi lệnh lúc chạy qua driver; embedded SQL đánh dấu lệnh trong mã nguồn để tiền xử lý trước khi biên dịch. “Dynamic” không bắt buộc nối dữ liệu người dùng vào chuỗi. Cũng không nên hiểu mô tả giới hạn biểu đạt SQL trong sách thành định lý về mọi phần mở rộng đệ quy/thủ tục của mọi DBMS.

JDBC chuẩn hóa API Java, còn driver chuyển lời gọi thành giao thức phù hợp sản phẩm. Ví dụ URL minh họa `jdbc:mysql://db.lab.invalid:3306/shop` chỉ định driver family, host, port và database; nó không phải URL HTTP của browser. Backend giữ cấu hình và secret, learner chỉ chọn connection profile trong web. Driver phải được backend cung cấp trước khi mở kết nối; một API chung không khiến cú pháp SQL của mọi engine giống nhau.

Chuỗi thao tác là mở hoặc mượn `Connection` → tạo `Statement`/`PreparedStatement` → execute → đọc → đóng theo thứ tự ngược. `executeQuery` trả `ResultSet`; `executeUpdate` trả update count cho INSERT/UPDATE/DELETE, còn DDL thường trả 0 theo JDBC. Count=0 có thể có nghĩa không hàng nào khớp, không mặc định là exception. `SQLException` mang lỗi DB; lỗi chỉ số mảng hoặc null pointer là lỗi chương trình khác. Handler phải rollback transaction cần rollback rồi phân loại lỗi, không bắt mọi lỗi và báo “DB bận”. Try-with-resources đóng tài nguyên cả khi exception; đóng tài nguyên không thay quyết định commit/rollback.

Ví dụ đọc hai hàng `(101,100),(102,50)`: cursor ban đầu ở trước hàng1; ba lần `next()` cho true,true,false. Sau true đầu, `getInt(1)` đọc cột1, `getBigDecimal("amount")` đọc theo nhãn. Chỉ số JDBC bắt đầu từ1. Nếu đọc một cột nullable bằng getter primitive, phải phân biệt SQL NULL với giá trị mặc định Java qua contract như `wasNull()`; không đổi NULL thành0 rồi tính tiền như đã biết. Khi dùng prepared statement nhiều lần, giá trị parameter cũ giữ tới khi set lại hoặc clear: set id=201,owner=1; execute; chỉ set id=202; execute thì owner vẫn1. Đây là lý do mỗi operation nên bind đủ đầu vào của nó. Driver có thể trì hoãn prepare ở server; lợi ích tái dùng kế hoạch cần đo, còn tách value khỏi cú pháp là yêu cầu đúng.

**Tự kiểm A1.** Một UPDATE không có hàng phù hợp trả0; sau đó code đọc `ResultSet.getInt(0)` và báo lỗi transient để retry. Tách hai vấn đề; viết trace cursor cho kết quả rỗng, và cho biết parameter owner lần hai nếu tác giả quên set lại.

**Đáp án A1.** Count0 cần nhánh nghiệp vụ “không tìm thấy/version không khớp”, không đủ cơ sở retry. Cột0 sai vì JDBC dùng1; sửa code và không retry lỗi lập trình. Kết quả rỗng có `next()` đầu=false, tuyệt đối không đọc hàng. Owner giữ giá trị lần trước; bind đủ hoặc clear trước khi bind giúp phát hiện thiếu, không tự suy ra owner mới.

### A2 · Metadata, routine, large object và result set có trạng thái

Metadata nghĩa là dữ liệu mô tả cấu trúc. `rs.getMetaData()` cho số cột, tên/nhãn và kiểu của kết quả cụ thể; `connection.getMetaData()` cho product/version, capabilities, bảng, cột, khóa và giới hạn. Công cụ bảng chung lặp i=1..columnCount, tạo header thân thiện, rồi lặp các rows. `getColumns(catalog,schemaPattern,tablePattern,columnPattern)` trả một hàng mô tả mỗi cột, các pattern `%`/`_` cần hiểu như pattern chứ không identifier literal. `getTables` có bộ lọc loại bảng để không lẫn system tables. Metadata dùng để thích ứng schema và kiểm capability, không tự cấp quyền xuất mọi cột tìm thấy.

Ví dụ result có `id INTEGER, amount DECIMAL`, renderer tạo đúng hai headers và hai cells mỗi row; nếu migration thêm `internal_note`, policy projection của API vẫn phải loại cột này. Header hiển thị có thể là “Mã đơn” thay tên vật lý. Khi render HTML, dùng text escaping, không chép nguyên giá trị vào markup như một số mẫu tối giản trong sách.

`CallableStatement` chuẩn bị lời gọi routine với input/output. Chẳng hạn fragment JDBC minh họa `prepareCall("{? = call tax_for(?)}")`: register output slot1 với SQL type thích hợp, bind input slot2, execute rồi lấy output slot1; procedure có OUT parameter cũng phải đăng ký OUT trước khi gọi. Quyền EXECUTE và transaction của routine vẫn phải kiểm riêng ở AD85. Không dùng getter trước execute để mong output mới.

Updatable result set có thể ghi ngược một row về bảng nếu query/driver đáp ứng điều kiện; không phải mọi JOIN hay aggregate đều updatable. RowSet có thể đóng gói/chuyển kết quả và hỗ trợ cách duyệt khác; bản copy đã tách kết nối có thể cũ, cần policy hòa giải khi ghi lại. BLOB là binary large object, CLOB là character large object. Locator là handle để đọc từng đoạn; ví dụ ảnh64MiB, buffer64KiB cần1024 lần đọc đủ nếu mỗi lần đủ buffer, nhưng thực tế phải lặp tới EOF vì lần đọc có thể ngắn. `getBlob`/`getClob`, stream input `setBlob`/`setClob` tránh cấp phát toàn bộ object. Locator/stream có vòng đời phụ thuộc transaction/driver, phải đóng và không gửi raw locator DB ra browser như một URL công khai.

**Tự kiểm A2.** Đổi query từ2 sang3 cột, cột mới là bí mật; làm sao renderer chung vẫn đúng hình thức và API không lộ bí mật? Nêu thứ tự gọi function có input và output; chọn cách trả video1GiB khi giới hạn buffer1MiB. Phân biệt metadata của result với danh sách PK/FK/capabilities của database.

**Đáp án A2.** Kiểm allowlist projection trước query/serialize, metadata chỉ định dạng các cột đã được phép; sau đó headers/cells cùng arity và escape output. Chuẩn bị call → đăng ký OUT → bind IN → execute → đọc OUT → đóng. Stream từng đoạn với bộ nhớ hữu hạn, kiểm số byte/EOF/quyền và lifecycle; không `getBytes` toàn bộ1GiB. Updatable capability phải được kiểm thay vì suy từ tên API. ResultSetMetaData mô tả cột kết quả; DatabaseMetaData mô tả schema/system/capabilities, nên một query projection không tự cho toàn bộ FK của database.

### A3 · Python DB-API, ODBC và embedded SQL

Ví dụ sau là pseudocode Python DB-API, cấu hình connector được backend cấp. Marker `%s` ở đây theo driver PostgreSQL minh họa trong sách, không phải phép format chuỗi Python; driver SQLite thường dùng `?`. Không chuyển placeholder giữa drivers bằng tìm/thay tùy ý.

```text
conn = backend_connect(profile)
cur = conn.cursor()
try:
    cur.execute("INSERT INTO notes(id,body) VALUES(%s,%s)", (7,"O'Hoa"))
    conn.commit()
    cur.execute("SELECT id,body FROM notes WHERE id=%s", (7,))
    for row in cur: append_to_response(row[0], row[1])
except database_error:
    conn.rollback()
    raise
finally:
    cur.close()
    conn.close_or_return_clean_to_pool()
```

Kết quả mong đợi là `(7,"O'Hoa")`, dấu nháy thuộc dữ liệu. Tuple một phần tử `(7,)` khác số7; code phải theo DB-API driver. Không mặc định autocommit của JDBC cũng là mặc định Python: đọc profile transaction của connector, gọi commit/rollback rõ trong bài. Việc cleanup hoặc trả pool nằm trong finally của backend, learner không cài Python.

ODBC là API cho ứng dụng C và nhiều môi trường khác, driver/library xử lý giao thức sản phẩm. Trace khái niệm: allocate environment → allocate connection → connect → allocate statement → prepare/execute → bind result columns → fetch → free statement → disconnect/free connection → free environment. `SQLBindCol` gắn cột SQL vào địa chỉ buffer và kiểu C; `SQLFetch` điền giá trị cho hàng tiếp theo. Buffer char cần dung lượng và chỉ báo độ dài/NULL; phải xét diagnostics/truncation, không in buffer như chắc chắn đầy đủ. Bind parameter cho input khác bind column cho output. Mọi lời gọi cần kiểm return status và cleanup cả đường lỗi; mẫu ngắn trong sách đã lược nhiều checks. Khi tắt autocommit phải kết thúc transaction rõ; khả năng catalog metadata, parameter arrays và các mức conformance không có ở mọi driver. SQL CLI là giao diện gọi ở chuẩn SQL có mục đích tương tự.

Embedded SQL dùng host language và các lệnh `EXEC SQL`; host variable được phân biệt bằng dấu `:`. Pseudocode dưới đây biểu diễn cursor, không phải C có thể chạy trực tiếp trong editor:

```text
declare host variables wanted_owner, out_id, out_amount, amount_null_indicator
EXEC SQL CONNECT using backend profile
EXEC SQL DECLARE c CURSOR FOR
    SELECT id,amount FROM purchases WHERE customer_id=:wanted_owner
EXEC SQL OPEN c
repeat:
    EXEC SQL FETCH c INTO :out_id, :out_amount :amount_null_indicator
    if end-of-data: break
    if SQL error: handle and stop
    consume row, using indicator to distinguish NULL
EXEC SQL CLOSE c
EXEC SQL COMMIT
```

Preprocessor biến lệnh SQL thành lời gọi API trước host compiler, nên có thể bắt một số lỗi SQL/type sớm nhưng mã sinh ra làm debug phức tạp; SQL động trong API được xử lý lúc chạy. Embedded database như SQLite là engine nằm cùng ứng dụng; đó là trục triển khai khác với embedded SQL, không suy ra cứ dùng SQLite là có preprocessor.

Cursor embedded SQL còn có thể định vị row hiện tại để update theo cú pháp embedding; thao tác ấy vẫn chịu quyền, constraint và transaction, không sửa một bản copy trong host rồi mặc định DB đã đổi. Query được tích hợp vào host language như LINQ là hướng khác với preprocessor EXEC SQL. Embedded database hữu ích cho dữ liệu nội bộ/offline không cần một server riêng; giới hạn concurrency, kích thước và features phải xét engine/workload cụ thể, không suy mọi embedded engine có đầy đủ contract của hệ server.

**Tự kiểm A3.** Với một giá trị NULL và một chuỗi dài120 ký tự vào buffer80 byte, ODBC cần thêm bằng chứng gì trước khi in? So JDBC, Python `%s` và embedded SQL theo thời điểm xử lý, binding, transaction; phân loại “SQLite trong process” thuộc khái niệm nào. Driver chỉ cung cấp core nhưng công cụ đòi catalog metadata: xử lý ra sao? Sửa một biến host sau FETCH có tự UPDATE DB không?

**Đáp án A3.** Kiểm indicator NULL và return diagnostics/độ dài để phát hiện truncation, không lấy nội dung buffer cho NULL; byte length còn khác character count. JDBC/Python gửi runtime SQL, marker và transaction theo driver; embedded SQL tiền xử lý rồi compile host, host variables dùng `:` và cursor/indicator. `%s` nhận sequence values riêng, không dùng `%` của Python. SQLite trong process là embedded database, vẫn có thể được gọi bằng dynamic API. Kiểm capability/conformance thật rồi tắt feature hoặc báo thiếu support; không giả định API name đảm bảo mọi level. Biến host chỉ là giá trị đã fetch; muốn ghi phải execute UPDATE hoặc cursor update theo contract rồi commit.

## Từ form đến response qua web server

### W1 · URL, HTML, HTTP và session

Ứng dụng đăng ký học có ba trách nhiệm: presentation nhận/hiển thị, business logic kiểm điều kiện đăng ký, data access đọc/ghi. Browser và mobile UI cùng có thể gọi backend API; người dùng không nhận credential DB. Client–server kiểu desktop nối DB trực tiếp gây khó cập nhật đồng loạt và mở rộng mặt truy cập. Web chuyển code phía server thành điểm thay đổi chung; browser nhận HTML/CSS/JavaScript. JavaScript vẫn là code cần kiểm an toàn; sandbox của browser không bảo đảm ứng dụng miễn XSS.

Trong URL minh họa `https://lab.invalid/orders?status=paid`, scheme=https, host=lab.invalid, path=/orders, query parameter status=paid. Path có thể được router ánh xạ sang chương trình, không nhất thiết là file. Form GET dưới đây gửi các control có `name`; CSS quyết định cách trình bày, không sửa nghĩa query. `table/tr/th/td` tạo bảng/header/cell, không tự truy vấn DB.

```html
<form action="/orders" method="get">
  <select name="status"><option value="paid">Đã trả</option></select>
  <input type="number" name="limit" min="1" max="50" value="20">
  <button type="submit">Tra cứu</button>
</form>
<table><thead><tr><th>Mã đơn</th><th>Số tiền</th></tr></thead>
<tbody><tr><td>101</td><td>100</td></tr></tbody></table>
```

Submit mặc định trên fixture tạo request tương đương `/orders?status=paid&limit=20`; encode parameter bằng URL encoder, không nối thô ký tự `&` trong dữ liệu. POST đưa dữ liệu vào body, nhưng không tự mã hóa hay tự chống CSRF; HTTPS bảo vệ kênh và server vẫn kiểm quyền. Date/time/file inputs và min/max/step giúp nhập thuận tiện; file upload còn cần giao thức/kiểm server riêng. GET dùng để đọc, không biến GET thành chuyển tiền.

HTTP request không mang sẵn session nghiệp vụ giữa hai requests. Transport có thể tái dùng hoặc ghép kênh, nhưng login không nên phụ thuộc một TCP connection giữ mãi. Server có thể phát session ID ngẫu nhiên khó đoán trong cookie và ánh xạ nó tới state phía server. Cookie `userid=1` do client sửa không đủ xác thực. Request không có ID hợp lệ dẫn tới login/401; logout hoặc timeout xóa hiệu lực ID phía server. Không chỉ xóa cookie mà giữ session server còn dùng được. Cookie scoping/attributes theo browser policy, không coi “cookie của site” là một nguyên tắc đơn giản áp dụng mọi domain/subdomain.

**Tự kiểm W1.** Đổi `limit` bằng request thủ công thành5000, giữ UI max50. Server nên làm gì? Sau logout, phát lại request với cookie cũ; nêu kết quả. Phân biệt3 thành phần URL và4 tag bảng trong ví dụ.

**Đáp án W1.** Server reject hoặc clamp theo contract đã công bố, không tin form. Cookie cũ không còn ánh xạ active session nên không đọc đơn riêng; request cần xác thực lại. Scheme/host/path và query có vai trò khác nhau; `table` bao bảng, `tr` một hàng, `th` header, `td` ô dữ liệu. POST vẫn cần TLS, validation và kiểm quyền.

### W2 · Servlet: một instance phục vụ nhiều requests

Servlet API là hợp đồng giữa application server và handler Java. Container ánh xạ route/method tới handler; `HttpServletRequest` cung cấp parameters/session, `HttpServletResponse` nhận status/content type/body. Trace cho `/orders?status=paid`: route chọn OrdersServlet → `service` chọn `doGet` → lấy `getSession(false)` → kiểm principal → parse/validate → business service → JDBC → tạo HTML đã escape → trả response. `getSession(false)` không tạo session mới; `true` cho phép tạo. Session attribute userid chỉ được đặt sau xác thực và được lấy lại qua session object, khác request parameter cùng tên.

Container nạp class, tạo instance và gọi `init()` một lần cho instance; nhiều lần service có thể chạy đồng thời; `destroy()` phục vụ cleanup khi instance được dỡ. Ví dụ lưu `currentCustomer` vào field rồi R1 đặt1, R2 đặt2 trước khi R1 query sẽ làm R1 dùng2. Giữ state request trong biến cục bộ và state session theo đúng scope; không dùng một JDBC connection chung cho mọi threads. Application server còn quản lý deploy/stop, monitoring, thread/resource services; CGI cổ điển tạo process mỗi request có chi phí khác servlet tái dùng instance. Hình9.5–9.6 tách/gộp web server và application server; số tầng triển khai ấy khác ba trách nhiệm logic của code.

**Tự kiểm W2.** Mô phỏng interleaving của hai requests trên field `currentCustomer`; sửa scope. Chỉ rõ nơi tạo session và nơi trả pool, rồi so một servlet instance với một transaction. Chọn hai việc application server phải hỗ trợ khi deploy và theo dõi handler.

**Đáp án W2.** R1:set1 → R2:set2 → R1:read2 là phản ví dụ; dùng local principal lấy từ session đã xác thực của từng request. Login tạo/đổi session hợp lệ; handler đọc session, mượn connection theo operation, finally trả sạch. Instance có thể sống qua nhiều requests/transactions và nhiều threads; init không mở một transaction dùng mãi. Deploy/stop handler và xem trạng thái/error/latency là hai nhóm việc server hỗ trợ; monitoring không thay tính đúng business logic.

### W3 · Template và framework đặt code ở đâu

Server-side scripting trộn khung HTML tĩnh với vùng sinh nội dung ở server. JSP truyền thống đánh dấu Java bằng `<% ... %>`, được server dịch thành servlet rồi compile; tag library/expression/template giảm việc viết HTML bằng chuỗi Java. PHP dùng `<?php ... ?>`, đọc request vào biến/array và `echo` sinh output. Browser chỉ nhận HTML sinh ra, không cần chạy Java/PHP. Tuy vậy code/secret vẫn có thể rò nếu cấu hình server làm lộ source; ẩn source không phải authorization.

Ví dụ khung `<p>Xin chào {{ display_name }}</p>` có input `Lan & An` phải sinh text nhìn thấy “Lan & An”, còn HTML nguồn chứa `Lan &amp; An` ở text context. Mẫu chèn thẳng tên vào HTML trong sách chỉ minh họa vị trí thực thi; bài dùng escaping đúng ngữ cảnh. Template không chứa commit hay credential; handler chuẩn bị view model hẹp.

Framework tích hợp routing/controller, forms+validation, session/authentication, templates và ORM; generated CRUD tạo khung nhanh nhưng quyền cho từng action còn phải xác định. Trong ví dụ Django kiểu khái niệm: `urls.py` ánh xạ `/orders` tới view function; function kiểm session, đọc `request.GET`, chọn query template cố định theo enum, bind values qua cursor, rồi render template. Django “view function” là handler, không đồng nghĩa SQL VIEW. `settings` ở backend chứa connection profile, không phải file gửi browser. Cursor context đóng resources; trả rỗng vẫn render header và empty-state. Chọn nhánh bằng `else` cho mọi input lạ sẽ vô tình chấp nhận enum sai; reject giá trị ngoài tập cho phép.

**Tự kiểm W3.** Với tên chứa ký hiệu `<b>`, nơi nào chạy JSP/PHP, nơi nào hiện chữ? Cho route Django nhập `kind=admin` dù form chỉ có customer/support; sửa nhánh và nêu kiểm sau khi scaffold CRUD.

**Đáp án W3.** JSP/PHP chạy server, output text được escape trước khi browser parse; tên hiện nguyên ký hiệu nếu policy là plain text. Router chỉ chọn handler; handler reject kind lạ trước query, bind giá trị trong nhánh cho phép. Scaffold cần allow/deny cho read/create/update/delete, validation và transaction; có template/ORM không chứng minh các kiểm ấy đã có.

## Client, dịch vụ và dữ liệu khi mất kết nối

### C1 · DOM, validation và response đến đảo thứ tự

DOM là cây biểu diễn tài liệu browser. JavaScript có thể thêm hàng “mặt hàng” vào bảng, cập nhật số tổng hoặc widget thay vì tải lại cả trang. CSS/library widgets giúp trình bày và tương tác; chúng không tạo transaction DB. Validate khoảng ngày phải kiểm thiếu/invalid trước so start≤end; chỉ `start>end` không bắt giá trị không parse được. Server lặp lại kiểm ấy vì client có thể bỏ JavaScript.

Ajax là cách gọi server bất đồng bộ rồi cập nhật DOM từ dữ liệu, thường JSON. Contract minh họa autocomplete `/names?prefix=La` trả `["Lan","Lâm"]`, còn `/orders?customer=1` trả `{"data":[{"id":101,"amount":"100.00"}]}`; hai schema khác nhau không thay lẫn được. Serialize/query encode parameters bằng thư viện và render values bằng text API. Hình9.12–9.13 cho thấy textbox gợi ý và bảng được nạp riêng. Ví dụ hai requests prefix=`L` version1, `La` version2: response2 đến trước hiện Lan; response1 đến sau phải bỏ, không ghi đè bằng danh sách rộng cũ. Country đổi phải xóa state đã chọn không còn thuộc country mới. SSE là luồng server gửi events cho client; nó không thay sự kiện commit đã được backend xác nhận.

**Tự kiểm C1.** Viết pseudocode tăng version khi đổi prefix và chỉ nhận response mới nhất. Thử start trống/end hợp lệ và response có thiếu `data`; mô tả UI cần hiện gì.

**Đáp án C1.** `v=++latest; send(prefix).then(r => {if(v===latest) validateSchemaThenRender(r)})`; giữ v local từng request. Thiếu/invalid date bị validation, không gửi ghi; thiếu schema response báo lỗi có kiểm soát, không render như0 rows đã được xác nhận. Request cũ có thể vẫn chạy server, nên bỏ response không phải rollback server. Đây là bảo đảm hiển thị của mô hình hữu hạn, không phải exactly-once cho mutation.

### C2 · Web service là hợp đồng dữ liệu

Web service nhận request qua HTTP và trả dữ liệu cho code gọi; HTML page dành hiển thị khác JSON/XML response dành parser. Phong cách REST dùng resources/methods/status theo hợp đồng HTTP; chỉ đặt tên URL `/doEverything` và trả JSON chưa đủ chứng minh mọi ràng buộc REST. Browser, mobile và backend khác có thể gọi cùng service; API nội bộ vẫn cần xác thực, quyền, hạn mức và version schema. Dịch vụ kiểu SOAP dùng XML envelope và mô tả formal như WSDL là họ hợp đồng khác; không cần learner cài cả hai stack.

Ví dụ service tính phí nhận order/version và trả fee currency+amount; service storage nhận object bytes trả object ID. Khi backend gọi service ngoài, timeout có thể xảy ra sau remote side effect; transaction local không rollback storage/fee provider. API contract phải nêu lỗi, retry/idempotence và dữ liệu tối thiểu được chia sẻ. Kết quả JSON tiền dùng string decimal ở ví dụ, không tự ép float rồi mất precision. Tách nguyên tắc web service khỏi các tên sản phẩm/mức độ phổ biến trong sách năm2019.

**Tự kiểm C2.** Một handler trả HTML login với HTTP200 vào chỗ client đang đợi JSON `data`. Đây có phải0 rows không? Vẽ hai ranh giới transaction khi backend ghi DB rồi gọi storage service.

**Đáp án C2.** Không: kiểm status/content type/schema và xử lý hết phiên bằng contract riêng. DB transaction và remote operation có hai commit/failure domains; cần kế hoạch compensation/outbox/idempotence thích hợp, không hứa rollback chung. XML hay JSON là encoding, không tự xác thực hoặc định nghĩa quyền.

### C3 · Offline, mobile và đồng bộ có version

Client offline cần local storage cho draft/outbox. Web Storage lưu key/value strings: `setItem`, `getItem`, `removeItem`; tên `deleteItem` trong phần nguồn là lỗi API, bài dùng `removeItem`. IndexedDB lưu object và indices, có version/schema migration; quota/eviction phụ thuộc môi trường nên không cố định5MB thành cam kết. Ví dụ draft D7 `{baseVersion:4,text:"mới",requestId:"r7"}` được giữ khi mất mạng; server đã ở version5 thì gửi lại phải conflict/merge theo policy, không ghi mù đè version5. Chỉ xóa outbox sau outcome được xác nhận; cùng r7 retry không tạo hai bản.

Mobile native có code tải trước, UI thiết kế cho màn nhỏ, local data và quyền truy cập thiết bị; web/PWA có thể đạt nhiều chức năng tương tự. Cross-platform frameworks chia sẻ code nhưng vẫn có hành vi/quyền phụ thuộc nền tảng. Service worker chạy nền riêng page để hỗ trợ cache/sync, không được coi là tiến trình chắc chắn sống mãi; permission location/camera phải theo lựa chọn người dùng. JIT/biên dịch là kỹ thuật thực thi, không thay invariant đồng bộ; bài không yêu cầu xây native app hoặc cài toolchain. Cả desktop browser lẫn mobile dùng cùng bài kiểm version ở web lab.

**Tự kiểm C3.** D7 được gửi, response mất, người dùng reload. Trace outbox và requestId khi reconnect; nêu ích lợi của IndexedDB index và việc cần làm khi draft schema đổi v1→v2. Chọn native/cross-platform/PWA cho cùng exercise web: dữ liệu local và permission thiết bị có thể bỏ kiểm ở backend không?

**Đáp án C3.** Giữ r7 tới xác nhận, tra/retry cùng key+payload; nếu server đã thành công trả result cũ, nếu baseVersion xung đột đưa UI merge. Không phát key mới chỉ vì reload. Index theo owner/status giúp tìm drafts chờ không quét mọi object; migration phải chuyển dữ liệu cũ có kiểm và xử lý lỗi, không giả định đổi class tự đổi local store. Background sync có thể bị trì hoãn, nên UI cần trạng thái pending/conflict rõ. Cả ba loại client vẫn cần backend authn/authz/version checks; chia sẻ code không làm quyền camera/location của các nền tảng giống nhau.

## Kiến trúc dữ liệu và chi phí mỗi request

### D1 · MVC, workflow và object–relation mapping

Theo luồng hình9.14: (1) browser gửi event tới controller; (2) controller gọi model/business logic; (3–4) model dùng data-access layer và DB; (5) model trả result; (6–7) controller chọn view để render result; (8) trả response. View có thể chạy phía client. Đây là phân trách nhiệm, không buộc tám network hops hoặc tám servers. Đăng ký môn cần kiểm prerequisite/fees tại business action, data access cung cấp query/update trong cùng boundary, presentation hiển thị kết quả; một mobile view khác dùng lại cùng action.

Workflow nhiều người khác transaction kéo dài nhiều ngày. Ví dụ đơn xin mở lớp có states Draft→Submitted→Approved hoặc Rejected. Chỉ Submitted được quyết định; mỗi transition kiểm actor+expected version và ghi state/event trong một transaction ngắn. Deadline có thể tạo nhiệm vụ nhắc/escalate tới supervisor. Chứng minh cục bộ: ban đầu Draft hợp lệ; mỗi cạnh cho phép chỉ đi tới state trong tập và kiểm guard; quy nạp theo số transitions thì không có Approved trực tiếp từ Draft. Bằng chứng dựa mọi đường ghi đều dùng transition function, bị phá nếu có UPDATE raw bypass.

ORM tự ánh xạ hàng↔object theo nhu cầu vì không thể nạp cả DB vào RAM. Class Order có id ánh xạ PK, amount ánh xạ decimal. Relationship nhiều–nhiều User↔Group cần bảng `membership(user_id,group_id)` với PK ghép; hai tập `user.groups` và `group.users` mô tả hai hướng cùng dữ liệu. Thêm cùng cặp hai lần phải bị unique/PK chặn. Mapping không biến object reference thành địa chỉ bền trên disk; identity, NULL, type, cardinality vẫn cần khai báo.

Hibernate minh họa Java/JPA mapping bằng `@Entity`, `@Id`, `@Table`, `@Column` hoặc file mapping, cấu hình kết nối tách riêng. Session/unit of work mở transaction, persist/load object theo PK; object managed bị sửa có thể được flush thành UPDATE theo contract khi commit. HQL truy vấn class/fields rồi dịch sang SQL, khác tên bảng SQL; raw SQL hữu ích nhưng phải giữ policy và đồng bộ state ORM. Các tên method trong sách là ví dụ của API ở thời điểm nguồn, không là bài cài version mới.

Django ORM dùng model fields/primary_key, filter tạo tập kết quả và relationship manager cho hai hướng. Ví dụ Student s1 có advisors a1,a2 và s2 có a2: bảng nối có đúng3 cặp. Loop mỗi student rồi tải advisors riêng có thể gây N+1 queries; dùng chiến lược fetch/batch phù hợp và kiểm SQL/query count trong backend, không suy từ số dòng Python. Migration có thể tạo/đổi schema hoặc model sinh từ DB; thêm cột NOT NULL lên dữ liệu cũ cần default/backfill và kế hoạch deploy tương thích, không coi version label là phép biến đổi dữ liệu đã chứng minh.

**Tự kiểm D1.** Vẽ3 cặp membership và kết quả chiều ngược của a2. Cho3 students, một query lấy students và một query riêng mỗi advisors: đếm queries. Thiết kế guard để hai reviewers cùng approve Submitted version4 không tạo hai quyết định.

**Đáp án D1.** Cặp `(s1,a1),(s1,a2),(s2,a2)`; a2.advisees={s1,s2}. Trace giả định lazy mỗi student riêng cho1+3=4 queries, batching có thể là2 nhưng phải đo contract. Transition dùng điều kiện state=Submitted AND version=4 và tăng version trong transaction; chỉ một cạnh thắng, request còn lại nhận conflict. Kiểm actor trước action, không để view tự quyết. ORM không thay PK/FK/transaction hoặc migration dữ liệu.

### D2 · Cache và nhiều application servers

Pool cache connection đã mở để giảm phí connect; JDBC DataSource có thể cấp handle từ pool và `close` trả handle về pool theo contract. Cache query result, cache page/fragment và cache connection giữ ba loại tài nguyên khác nhau. Query/page cache giống materialized result: khi base data đổi, cần invalidation, recompute hoặc maintenance; eviction vì thiếu RAM chỉ giải capacity, không bảo đảm freshness. Key phải gồm parameters, principal/role, locale và data/policy version khi các yếu tố ấy làm đổi kết quả.

Cache-aside ví dụ `order-summary:principal1:v8`: miss→DB query→store→return, hit→đọc bản đã cho phép. Writer commit v9 rồi reader cũ store v8 là race nếu cả hai dùng cùng key không version. Có thể dùng versioned key và chính sách chọn current version, hoặc cơ chế consistency/invalidation khác được kiểm; TTL chỉ chặn thời gian stale theo assumptions, không chứng minh tức thì. Không cache trang có side effect rồi bỏ operation ở lần gọi kế. Memcached/Redis trong nguồn minh họa key–value cache phân tán; chia key theo instances tăng tổng RAM nhưng mất cache vẫn phải có đường đọc DB và kiểm overload.

Nhiều application servers chia tải qua load balancer, còn DB chung vẫn có thể là bottleneck. State session ở RAM một server cần affinity hoặc shared session store/thiết kế stateless phù hợp; IP không phải định danh session đáng tin do NAT, proxy và đổi mạng. Ví dụ giả định mỗi request dùng5 queries, DB budget1000 queries/s: trần lý tưởng chỉ200 requests/s, thêm application servers không vượt trần đó; nếu cache hợp lệ giảm còn2 queries/request, trần lý tưởng500. Các số này là mô hình không đo thực, còn contention, cache miss và tail latency có thể làm thấp hơn. Measure throughput/latency/error và query count cùng workload trước khi chọn pool/cache/parallelism.

**Tự kiểm D2.** Cache key chỉ có `report:month` cho finance lẫn support gây lỗi gì? Session ở A, request sau tới B thì cần gì? Tính trần khi DB600 queries/s và3 queries/request, rồi nêu vì sao không gọi đây là benchmark.

**Đáp án D2.** Có thể lộ projection/principal của role khác; key+policy và kiểm quyền phải bao đúng scope, invalidation khi policy đổi. Dùng affinity có giới hạn hoặc shared/verified session design; B không tự suy user từ IP. Trần lý tưởng200 requests/s; giả định bỏ nhiều chi phí nên đây chỉ capacity bound, không kết quả chạy. DB chung, pool tối đa và backpressure vẫn cần phối hợp.

## Luyện tập

1. Sửa endpoint nối chuỗi `sort` trực tiếp vào ORDER BY. Chấp nhận đúng `amount_asc` và `date_desc`, giữ id làm tie-breaker; nêu dữ liệu nào vẫn bind bằng parameter.
2. Viết trace chuyển 30 với lỗi sau lần trừ, so autocommit và một transaction. Chỉ ra trạng thái sau rollback.
3. Một request timeout sau khi server gửi COMMIT. Đề xuất cách client thử lại cùng request_id và ca kiểm bảo đảm không trừ hai lần. Nêu tình huống không thể chỉ retry câu cuối.
4. Tự làm: thiết kế pool tối đa 2 connections cho 3 requests, trong đó request thứ hai thay isolation rồi bị lỗi. Ghi mọi bước borrow/return/cleanup và chứng minh không trao một connection cho hai request cùng lúc.

## Gợi ý

Tầng 1: marker parameter thay giá trị; request timeout không tiết lộ kết quả commit. Pool quản lý tài nguyên thực, không chỉ là một list có thể pop tùy lúc.

Tầng 2: sort dùng dictionary cố định của server; request_id và effect nằm cùng transaction. Pool cần khóa hoặc primitive đồng bộ ở thao tác chuyển idle↔busy, cùng finally/cleanup cho mọi đường lỗi.

## Đáp án và lập luận

1. Ánh xạ amount_asc→`amount ASC,id ASC`, date_desc→`created_on DESC,id ASC`; giá trị khác bị reject. customer_id, status, ngưỡng tiền dùng marker của driver. Không bind tên cột bằng string rồi nhận là dynamic identifier an toàn.
2. Autocommit: 100,100→70,100 và lỗi giữ trạng thái đã commit lần đầu. Một transaction: trạng thái nội bộ 70,100 rồi rollback thành 100,100. Nếu đã commit cả hai thì 70,130; lỗi response sau đó không đảo commit.
3. Backend lưu key cùng payload hash/result trong transaction. Hai lần cùng key/payload trả một result; cùng key khác payload báo conflict. Ca kiểm chạy request hai lần và đọc số dư+count key. Sau deadlock phải đọc lại và lặp cả operation, không dùng các quyết định từ transaction đã abort.
4. R1 giữ C1,R2 giữ C2,R3 chờ. R2 lỗi: rollback, khôi phục settings rồi trả C2; nếu cleanup lỗi thì đóng C2 và tạo replacement theo policy. Chỉ sau bước đó R3 nhận connection sạch. Invariant idle∩busy=rỗng và mỗi busy có đúng một owner, được bảo toàn bởi thao tác cấp/trả nguyên tử. Timeout của R3 trả lỗi overload rõ, không cấp C1 đang bận.

## Biến thể và cách kiểm

Biến thể đổi lỗi trước/giữa/sau commit, hai request cùng key, key trùng khác payload và response đến đảo. Chấm post-state, số operation thực, cleanup và error classification. Nếu code bắt mọi exception rồi retry vô hạn, phản hồi đưa lỗi validation không nên retry. Nếu query SQL đúng nhưng mất session state, kết quả activity vẫn chưa đạt hợp đồng dịch vụ.

## Học trên web

Người học sửa code trong workspace hoặc điền transaction boundary trên sequence diagram. Hợp đồng web lab yêu cầu backend sandbox thực thi API test trên engine/driver đã công bố; UI có nút inject lỗi ở các checkpoint và hiển thị request_id/transaction_id, không lộ credential. Pseudocode/model chỉ chấm lập luận; muốn nhận bằng chứng chạy cần event và state đọc lại từ dịch vụ. Kiểm SQL hữu hạn bằng SQLite của tác giả không xác nhận JDBC, ODBC, Django, Hibernate, MySQL, mạng hay concurrency thật. Không yêu cầu learner chạy terminal hoặc cài driver.
