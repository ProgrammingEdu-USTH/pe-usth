# AD58 · PostgreSQL internals: từ source đến một extension nhỏ

Đã học: AD55, AD57; C tối thiểu được giải thích tại chỗ. Nguồn: DSC7e online §32.8.1–32.8.3, §32.8.8–32.8.10. Môi trường web: workspace đọc C và build/test trong backend riêng đã ghim PostgreSQL 18, compiler và server headers. AD83 tách sâu memory contexts; AD84 tách Node/Datum/tuple. Người học không cài compiler, PostgreSQL hoặc Docker cá nhân.

Một hàm SQL mới trả kết quả đúng với 2+3 nhưng làm backend lỗi khi input NULL hoặc số quá lớn. “Code C đã compile” chưa chứng minh hợp đồng SQL đúng. Bài này đi qua một thay đổi nhỏ đủ nhìn trọn: nhận hai integer, cộng có kiểm overflow, trả integer hoặc lỗi được định nghĩa. Cùng lúc, ta học cách lần theo source, catalog và executor mà không phải đọc toàn bộ PostgreSQL từ đầu.

## Chuẩn bị để đọc C

`int32` và `int64` là các kiểu số nguyên có chiều rộng được PostgreSQL quy định; dấu `*` trong một khai báo chỉ pointer tới vùng nhớ, không phải phép nhân. Một struct nhóm các field; dấu `p->field` truy cập field qua pointer. Hàm có input và kiểu trả về; macro viết hoa có thể mở thành nhiều thao tác C, không luôn là một lời gọi hàm bình thường.

Trong C, overflow signed integer không được coi là một cách wrap an toàn để phát hiện sau. Vì hai integer32 cộng lại luôn nằm trong miền integer64, ta có thể nâng lên int64 trước, cộng rồi kiểm giới hạn int32. NULL SQL không phải số 0 và cũng không phải một pointer bất kỳ; API gọi hàm có metadata NULL riêng. AD84 sẽ đi sâu representation; bài này dùng các macro giao diện thay vì tự đọc bits.

## Source tree và một đường đi có mục tiêu

Một bản source có frontend/client, backend, headers, contrib/test và build files. Trong backend, nhóm xử lý câu lệnh nhận query; parser/analyzer/rewrite/planner tạo biểu diễn thích hợp; executor thực hiện plan; storage/access quản lý page/index/visibility; catalog và utilities cung cấp metadata/lifecycle. Đường dẫn và function cụ thể phải được ghi cùng commit/version khi bài code-reading gắn một repo.

Một cách khảo sát tốt là theo một query nhỏ đã biết kết quả: tìm nơi nhận command, nơi gọi planner, nơi tạo executor state và một scan node lấy tuple. Trên source PostgreSQL, các vùng như `src/backend/tcop`, `parser`, `optimizer`, `executor`, `access`, `storage`, `catalog` và `utils` giúp định vị. Không suy file ở một thư mục chứa mọi implementation của một khái niệm; các helper và headers thường nằm nơi khác.

Người học nên ghi một call-path ngắn có input/output của từng chặng, không chỉ danh sách mười tên hàm. Bài web source browser cần pin ref và giữ số dòng theo ref ấy; link một nhánh đang thay đổi không đủ cho một đáp án line-number cố định.

## Build và tạo một server học riêng

Build từ source cần compiler/linker, build tools và dependencies theo phiên bản/platform. Server development headers phải cùng major version và cấu hình tương thích với binary mục tiêu. Bản cài chỉ có client không đủ để build extension C. `pg_config` cung cấp thông tin của installation được chọn; nếu PATH trỏ installation khác, một build thành công vẫn có thể sinh module không phù hợp server đang chạy.

Workflow backend của khóa là: chọn image/source ref đã kiểm; build hoặc dùng server/dev package đã pin; tạo cluster dữ liệu riêng; khởi chạy với role/database riêng; thực hiện ca kiểm kết nối; build extension; cài vào đúng instance học; chạy regression; hủy environment. Đây là thao tác do dev triển khai sau các nút web, không phải yêu cầu học viên mở terminal. Source/build logs không được coi là bằng chứng extension đã load cho đến khi SQL chạy thật trên server đúng version.

Không dùng một extension build cho major version khác chỉ vì cùng tên file. Module magic giúp phát hiện một số bất tương thích; nó không phải chứng minh ABI/API nội bộ ổn định cho mọi phiên bản. Container/image và extension source/version là thành phần của artifact tái lập.

## Ví dụ 1: hàm cộng kiểm overflow

File `ad_advanced.c`, được biên soạn mới cho bài:

```c
#include "postgres.h"
#include "fmgr.h"
#include "utils/errcodes.h"
#include <stdint.h>

PG_MODULE_MAGIC;
PG_FUNCTION_INFO_V1(ad_add_checked);

Datum
ad_add_checked(PG_FUNCTION_ARGS)
{
    int32 a = PG_GETARG_INT32(0);
    int32 b = PG_GETARG_INT32(1);
    int64 total = (int64) a + (int64) b;

    if (total > INT32_MAX || total < INT32_MIN)
        ereport(ERROR,
                (errcode(ERRCODE_NUMERIC_VALUE_OUT_OF_RANGE),
                 errmsg("integer sum is outside int32 range")));

    PG_RETURN_INT32((int32) total);
}
```

`postgres.h` đứng trước các header server khác. Function nhận interface `PG_FUNCTION_ARGS`, lấy hai đối số bằng macro đúng type và trả bằng macro tương ứng. `Datum` là giao diện giá trị nội bộ, không phải lời hứa mọi type là một int32. `PG_FUNCTION_INFO_V1` khai báo calling convention; `PG_MODULE_MAGIC` cho thông tin tương thích module.

SQL interface sau cần đi kèm binary đã build/cài đúng. Bản extension có thể dùng control file:

```text
comment = 'Checked integer addition for an isolated teaching lab'
default_version = '1.0'
module_pathname = '$libdir/ad_advanced'
relocatable = true
```

Trong file `ad_advanced--1.0.sql` được CREATE EXTENSION nạp:

```sql
CREATE FUNCTION ad_add_checked(integer,integer)
RETURNS integer
AS 'MODULE_PATHNAME','ad_add_checked'
LANGUAGE C IMMUTABLE STRICT PARALLEL SAFE;
```

MODULE_PATHNAME được cơ chế extension thay theo control file; không gửi nguyên placeholder này như một đường dẫn tùy ý trong một câu CREATE FUNCTION độc lập. Một build PGXS tối thiểu có MODULES=ad_advanced, EXTENSION=ad_advanced, DATA=ad_advanced--1.0.sql, và include PGXS từ installation đã chọn. Dev phải giữ tên library/source/control/SQL thống nhất và cài đúng đích trước khi gọi SQL.

STRICT làm lời gọi có đối số NULL trả NULL mà không đi vào thân hàm này. Metadata ấy phù hợp với code không tự kiểm NULL. IMMUTABLE đúng vì chỉ tính số từ đối số, không đọc bảng/trạng thái môi trường; PARALLEL SAFE cần được xét vì code không có side effects hoặc dùng tài nguyên session không phù hợp. Với một hàm khác, không được chép các nhãn này theo khuôn.

Một Makefile hoàn chỉnh cho module một file, để đọc cùng control/SQL vừa nêu:

```makefile
MODULES = ad_advanced
EXTENSION = ad_advanced
DATA = ad_advanced--1.0.sql
PG_CONFIG ?= pg_config
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)
```

PG_CONFIG do backend chọn trỏ tới installation đích; PGXS cung cấp quy tắc compile/install thông thường. `CREATE EXTENSION ad_advanced` sau cài mới nạp script SQL đăng ký function. Build/install, extension creation và lần gọi function là ba mốc riêng: chỉ mốc cuối mới kiểm đường loader/calling convention tới thân C. Đây là recipe để đọc, chưa được chạy. [PGXS, PostgreSQL 18](https://www.postgresql.org/docs/18/extend-pgxs.html).

## Ví dụ 2: expected và ca lỗi

Sau khi backend đã cài extension:

```sql
SELECT ad_add_checked(20,22) AS answer;
SELECT ad_add_checked(-5,2) AS answer;
SELECT ad_add_checked(NULL::integer,7) IS NULL AS is_null;
SELECT ad_add_checked(2147483647,1);
```

Expected lần lượt 42, -3, true và lỗi numeric_value_out_of_range; câu cuối không trả một số wrap. Test thêm(-2147483648,-1) để bắt underflow, (2147483647,0) để kiểm biên vẫn hợp lệ. Trong transaction đã lỗi, runner phải rollback hoặc dùng savepoint theo contract trước câu kế tiếp; không ghi các câu sau thất bại là lỗi số học mới.

Tính đúng của phần số học: a,b đều trong miền int32; tổng toán học nằm trong[-2^32,2^32−2], vừa miền int64. Phép nâng trước cộng không overflow int32. Nếu total ngoài miền int32 thì báo lỗi, đúng hợp đồng. Nếu nằm trong miền, cast int32 giữ nguyên giá trị và macro trả đúng type SQL. Phần tính toán O(1), dùng bộ nhớ O(1); điều này không bao gồm overhead gọi SQL/load module. Kiểm ABI, loader và NULL convention là những lớp bằng chứng riêng ngoài chứng minh số học.

## System catalogs là dữ liệu có cấu trúc

Catalog ghi metadata về type, function, relation, attributes, operators và các đối tượng khác. OID liên kết các object nội bộ; không hard-code OID của object tự tạo trong lesson vì nó có thể khác giữa environment. Dùng regclass/regprocedure hoặc JOIN catalog đúng khi cần tra một đối tượng theo tên/signature.

Sau khi hàm được tạo, query sau kiểm metadata:

```sql
SELECT proname,provolatile,proisstrict
FROM pg_proc
WHERE oid='ad_add_checked(integer,integer)'::regprocedure;
```

Expected tên ad_add_checked,provolatile='i',proisstrict=true nếu DDL trên đã được nạp đúng. Đây là kiểm metadata, không chứng minh code C luôn trả đúng. Không sửa trực tiếp catalog để “bật” một type hoặc né lỗi dependency; dùng DDL/interface hỗ trợ. Catalog có policy/cache/dependency và version riêng; thay một row tay có thể phá những giả định hệ thống giữ.

## Ví dụ 3: pull-based execution và vòng đời state

Mô hình sư phạm: scan ba tuple(id,mark)=(1,8),(2,9),(3,7), qual mark>7.5, projection id. `next()` lần 1 đọc row 1, qual đúng, trả 1. Lần 2 trả 2. Lần 3 đọc row 3, qual sai, đọc tiếp tới hết và trả end-of-stream. Không trả NULL thay end-of-stream: NULL có thể là giá trị field trong một tuple hợp lệ.

Plan mô tả phép scan/qual/projection; executor state giữ vị trí scan, expression state và tài nguyên của lần thực thi. Khi đóng hoặc rescan, state cần reset/giải phóng theo giao thức. Trong PostgreSQL, một scan node có thể thực hiện qual/projection bên trong thay vì có riêng từng node hình vẽ. Do đó mô hình ba operator logic này không phải ảnh chụp đúng một EXPLAIN vật lý.

Tính đúng của mô hình scan: trước mỗi lần next, mọi tuple trước vị trí hiện tại đã được xét đúng một lần; những tuple đã trả đều thỏa qual. Vòng bên trong chỉ tiến vị trí, nên hữu hạn n tuple thì dừng; khi hết, không còn tuple thỏa bị bỏ sót. Với qual/projection O(1), quét hết O(n), state O(1) ngoài dữ liệu input. Một node sort hoặc hash join có state/cost khác; không lấy chứng minh này áp vào mọi executor node.

Memory contexts xác định dữ liệu nào sống qua một tuple, một query hay transaction; AD83 giải thích reset và copying. Node/Datum/tuple descriptors ở AD84 giải thích cách code phân biệt cấu trúc và giá trị. Tách các lớp giúp đọc một lỗi đúng chỗ: trả sai type khác giữ pointer hết hạn, còn khác việc scan bỏ sót tuple.

## Error handling và thử thay đổi nhỏ

`ereport(ERROR,...)` không chỉ in một dòng rồi tiếp tục nhánh return như printf. Nó chuyển điều khiển theo cơ chế lỗi server, làm statement/transaction đi vào đường xử lý tương ứng; với subtransaction/savepoint có phạm vi khác nhau. NOTICE/WARNING không cùng nghĩa với ERROR; FATAL/PANIC có tác động mạnh hơn và không phải cách thông thường trả validation error cho một bài SQL.

Trong code C, không dựa vào destructor C++ hoặc normal return để dọn mọi tài nguyên khi có ERROR. Memory context/resource ownership giúp quản lý những tài nguyên được hệ theo dõi; file/lock/callback ngoài cơ chế ấy cần cleanup đúng. Bài này không giữ tài nguyên ngoài nên đường lỗi đơn giản. Một thay đổi lớn hơn phải thử cả lỗi giữa chừng và lần gọi tiếp theo, không chỉ happy path.

Cách phát triển thực dụng là một patch nhỏ, giải thích input/output/invariant, build với warnings, chạy regression gồm ca sai và đọc diff. Extension load vào server có khả năng ảnh hưởng backend, nên workspace build/test của khóa phải dùng instance riêng và không có secrets/dữ liệu người khác. Đây là yêu cầu kiến trúc của hoạt động web, không phải lý do bắt người học tự cài môi trường.

## Đọc một build recipe mà không buộc cài trên máy học

Installation from source gồm hai việc khác nhau: tạo binary từ source rồi tạo một data cluster cho binary ấy. Compiler C, build system,parser generators Flex/Bison, Perl và libraries phải theo version/platform; Readline giúp client editing, zlib hỗ trợ compression, ICU liên quan collation, LLVM phục vụ JIT khi bật. PostgreSQL 18 có đường Autoconf/Make và Meson; Windows Visual Studio dùng Meson. Không đưa minimum-version của năm 2019 thành checklist hiện tại. Đội dev ghim toolchain cùng source ref; người học đọc dependency/build logs trong browser. [Requirements18](https://www.postgresql.org/docs/18/install-requirements.html), [installation18](https://www.postgresql.org/docs/18/installation.html).

Một recipe minh họa ở backend Unix có thứ tự configure prefix riêng với debug/assertion options→build→regression check→install vào prefix ấy. Debug symbols giúp gắn source,assertions phát hiện điều kiện nội bộ,giảm optimization có thể giúp bước debugger; chúng không đồng nghĩa build production nhanh hơn. `make check` kiểm nhiều hành vi nền nhưng chưa kiểm extension mới; `make world` còn gồm tài liệu/modules theo target. Đường Meson dùng setup/compile/test/install tương ứng và options riêng, không trộn flags hai hệ. Nếu compile pass nhưng tests fail do collation/locale, giữ failure log và giải quyết khác biệt,không xóa expected để làm xanh.

Sau binary, backend chọn data directory mới không chứa dữ liệu ai khác, initdb tạo cluster cùng shared catalogs/template databases,khởi động server trên port/socket riêng rồi createdb tạo database học. Cluster là tập databases của một server instance; không phải mỗi schema là một cluster. Một instance nghe port 5432 còn sống không cho instance mới dùng cùng endpoint. Client connection cần host/port/database/user đúng; `psql -c` chạy command,`-f` đọc file,meta-command thuộc client. Single-user mode là đường quản trị/khôi phục với quyền rất mạnh,không phải runner SQL học viên; hoạt động này chỉ dùng sơ đồ bước và log giả định,không yêu cầu khởi động hoặc thao tác nó trên máy cá nhân.

Ví dụ lỗi deployment: module được cài prefix A nhưng web nối server prefix B. Source đúng và build pass vẫn cho load failure ở B. Hồ sơ cần pg_config/binary/source ref, data-directory identity,endpoint và SELECT version() phù hợp; không chỉ giữ PATH. Native tests sau này chạy fresh connection khi thay shared library đã load,kiểm object/schema/dependency cleanup và instance identity. Trong lần này chưa có server PostgreSQL/build extension; tên bước là kiến thức đọc quy trình,không phải log thành công.

Một recipe Unix để **đọc log trong browser** có thể có các dòng sau. Các đường `/workspace/...` là đích mới trong sandbox do backend cấp; prefix source và data directory là hai vùng khác nhau. Đây chưa phải các lệnh đã chạy trong lần rà soát này:

```text
./configure --prefix=/workspace/pg18 --enable-debug --enable-cassert CFLAGS='-O0 -g'
make
make check
make install
/workspace/pg18/bin/initdb -D /workspace/pgdata
/workspace/pg18/bin/postgres -D /workspace/pgdata -p 55432
```

Supervisor của backend giữ server sống, cấp authentication/role cho môi trường học và chỉ mở endpoint cần thiết. Khi server sẵn sàng, client của môi trường dùng `createdb -p 55432 ad_lab`, rồi `psql -p 55432 -d ad_lab -c 'SELECT 1'` hoặc `-f lesson.sql`; options host/user/auth phải khớp cấu hình đã cấp. `SELECT 1` trả 1 mới xác nhận một đường kết nối cơ bản, chưa kiểm extension. Source ref/toolchain/tests là đầu vào riêng; dùng lệnh tương tự với binary khác hoặc data directory cũ không tạo cùng environment. Người học sắp xếp/giải thích các bước và đọc logs ngay trên web; thao tác cài, khởi chạy và dọn instance thuộc backend.

## Bản đồ source và catalog có thể kiểm tra

Source root có config/contrib/doc cùng src/backend,src/bin,src/include,src/interfaces,src/pl,src/test; common/fe_utils chia helper,port chứa platform support,timezone chứa data/code liên quan múi giờ,tools phục vụ phát triển,tutorial cho ví dụ. Trong backend,parser scan.l tạo tokens,gram.y grammar,analyze.c gắn semantics; optimizer/path xét access/join paths,plan tạo plan,prep tiền xử lý,geqo tìm join order heuristic. executor thực thi; access quản access methods,storage quản buffers/I/O/locks,rewrite xử lý rules,commands điều phối utility/DDL,catalog quản object metadata,replication/foreign/jit/tsearch phục vụ các subsystem tương ứng. Ví dụ thêm một cú pháp mới nhưng không thêm phân tích type thì raw parse có thể thành công mà query chưa có semantics hợp lệ.

Catalog join dùng identity nội bộ cùng namespace,không ghép bằng tên đơn lẻ. Ví dụ self-study đọc schema có table ad_pg_mark ở schema học: pg_namespace→pg_class qua relnamespace,pg_attribute qua attrelid; lọc attnum>0 và NOT attisdropped để bỏ system/dropped attributes. pg_class còn chứa index,view,sequence và relation kinds khác,nên không diễn nó là chỉ tables. pg_index nối indexrelid với indrelid; pg_proc có functions/procedures và signatures; pg_operator/pg_type mô tả operator/type; system views như pg_tables tổng hợp tiện dùng,không suy mọi view buộc có hậu tố plural. Nếu hai schema cùng có tên mark,ghép relname='mark' thiếu namespace có thể nhân đôi metadata.

Mô hình catalog: Namespace(oid 10,name='lab'),Relation(oid 20,name='mark',namespace 10),Attribute(rel 20,num 1,name='id'),Attribute(rel 20,num 2,name='score'). Join theo OID trả hai cột đúng của lab.mark; thêm public.mark oid 30 không thay output nếu namespace filter đúng. Thuật toán resolve object nhận namespace+name+signature khi cần,lấy OID thích hợp rồi JOIN theo FK-like catalog references. Tính đúng dựa uniqueness identity/điều kiện filter của model; không áp khóa ngoại giả ấy làm DDL sửa pg_catalog thật. DDL supported còn cập nhật cache/dependencies nên không INSERT tay vào catalogs.

## Call-path có kiểu dữ liệu và đường lỗi

Đường simple-query mô hình của sách đi qua PostgresMain/exec_simple_query→raw parser trả list raw trees→analysis/rewrite trả Query trees→planner trả PlannedStmt→Portal/Executor chạy và trả tuples. Một chuỗi có hai statements có thể có hai raw trees; một rewrite có thể sinh nhiều Query trees, nên không buộc list lengths luôn bằng nhau. Utility statement như CREATE TABLE đi qua ProcessUtility thay vì giả mọi statement là scan plan. Extended query protocol/prepared execution có đường parse/bind/execute/cache khác, vì vậy sơ đồ32.9 không phải toàn bộ stack mọi request bản 18. Khi code-reading thực,phải lần hàm đúng ref và ghi đường đã theo.

QueryDesc gom thông tin thực thi như planned statement,parameters,destination/snapshot và executor state; Plan mô tả phép toán,PlanState giữ state sống của lần chạy. Portal có thể chạy/fetch nhiều lượt; một lần ExecutorRun kết thúc sớm không đồng nghĩa đóng query ngay. ExecutorStart khởi tạo,Run tiêu thụ,Finish xử lý phần kết thúc cần thiết trước End dọn state. Sơ đồ32.10 và AD83 giúp chỉ lifetime,không cho phép reset per-query state sau mỗi row. Ví dụ LIMIT 1 đã trả một row nhưng scan có tài nguyên chưa đóng; caller vẫn phải theo shutdown protocol.

ereport gắn SQLSTATE,message,detail,hint để client phân loại lỗi; elog dùng cho thông tin/chẩn đoán nội bộ theo convention. ERROR chuyển điều khiển về handler phù hợp; Assert kiểm lỗi lập trình và có thể không hoạt động trong build không assertions. Transaction cleanup quản lý resources qua cả memory contexts và ResourceOwner/subsystem-specific cleanup,không chỉ “reset bộ nhớ sẽ tự nhả mọi file/lock”. Ví dụ giữ một external handle tự quản rồi ERROR trước normal return: cần cleanup path/callback theo hợp đồng,không chờ hàm kết thúc bình thường. Không thêm PG_TRY/PG_CATCH rồi bỏ qua error state,context/resource restoration; handler muốn tiếp tục phải theo API đầy đủ.

Thêm feature bắt đầu bằng chọn subsystem và so một trường hợp tương tự để hiểu API; reuse list,bitmapset,binary heap,stringinfo hoặc hash infrastructure của đúng ref khi hợp nhu cầu. Bloom filter/HyperLogLog là cấu trúc xấp xỉ với contract khác exact set; dùng chúng để quyết định integrity cần proof bổ sung,không chỉ vì đã có sẵn trong server. Ví dụ feature “lọc top-k” cần xác định tie/NULL/order,đường planner tạo node,executor state,rescan/copy/serialization,parallel/error/memory cùng tests trước patch. Một minimal patch có hypothesis và corner cases giúp cô lập lỗi; cộng đồng/developer documentation là nguồn đọc review/patch conventions,không tự gửi message hoặc patch thay người học.

## Minh họa theo trạng thái

Mô hình biên soạn cho lời gọi ad_add_checked(20,22):

1. SQL được phân giải tới function có signature(integer,integer) và metadata STRICT.
2. Loader tìm library/symbol theo extension đã cài; version/magic phải phù hợp.
3. Interface chuyển hai đối số không NULL tới PG_GETARG_INT32.
4. Code nâng lên int64, tổng 42 nằm trong int32 nên trả 42.
5. Executor nhận Datum đúng type và dựng row kết quả.
6. Đổi input thành maxint32+1: đi nhánh ERROR, rollback theo phạm vi đã định nghĩa, không có output số.

Hoạt động hỗ trợ một: ghép lỗi với lớp loader/type/arithmetics/transaction. Hoạt động hỗ trợ hai: sửa một đoạn cộng int32 trước rồi mới cast. Chuyển giao độc lập là một hàm khác có policy NULL/biên rõ, không mở sẵn thân C của lời giải.

## Luyện tập

1. Vì sao `(int64)(a+b)` không tương đương `(int64)a+(int64)b` khi a,b là int32? Chọn input làm lộ khác biệt và giải thích ở mức C, không chỉ SQL.
2. Xóa STRICT khỏi CREATE FUNCTION nhưng giữ nguyên thân C. Hợp đồng NULL đã được bảo đảm chưa? Đưa hai cách sửa khác nhau và ca kiểm.
3. Tự làm: thiết kế hàm nhân hai integer trả bigint hoặc báo overflow theo contract của bạn. Ghi type đầu vào/đầu ra, NULL policy, lập luận về miền trung gian và ít nhất 4 ca. Nếu chọn bigint output cho int32 inputs, chứng minh tích có vừa miền đó không trước khi thêm một kiểm không cần thiết.
4. Source-reading: vẽ đường từ một SELECT nhỏ qua analyze/plan/executor đến một scan node ở ref được cấp. Mỗi cạnh ghi dữ liệu truyền và một câu hỏi chưa thể kết luận chỉ từ EXPLAIN. Không chỉ nộp danh sách tên file.

## Gợi ý

Mức 1: cast sau khi một phép tính không hợp lệ đã xảy ra không sửa được phép tính trước đó. Function metadata và thân code phải cùng hợp đồng.

Mức 2: câu 1 thử 2147483647+1. Câu 2 hoặc giữ STRICT, hoặc kiểm PG_ARGISNULL theo interface trước khi lấy giá trị. Câu 3 miền lớn nhất cần xét là tích hai đầu mút int32, không lấy hai số “thường dùng” làm bằng chứng.

## Đáp án và lập luận

1. Biểu thức trong ngoặc được tính bằng kiểu của a,b trước khi cast; signed overflow C không phải kết quả wrap được bảo đảm. Nâng từng toán hạng trước cộng cho phép phép cộng diễn ra trong int64, rồi mới kiểm miền kết quả int32.
2. Chưa. Có thể khai STRICT để thân hàm không bị gọi với NULL; hoặc bỏ STRICT nhưng kiểm từng null flag và định nghĩa trả NULL/default/error trước PG_GETARG. Test có NULL ở từng vị trí và cả hai; không giả NULL là 0.
3. Tích hai int32 nằm trong[-(2^31)(2^31−1),2^62], vừa int64 signed. Nâng trước nhân rồi PG_RETURN_INT64 cho bigint là một hợp đồng hợp lý; nếu chọn trả integer32 thì phải kiểm lại miền hẹp. Test0,hai dấu,biên INT32_MIN×INT32_MIN và NULL. Nộp code chỉ được nhận đã chạy khi build/load/test artifact phù hợp có thật.
4. Nhận call-path gắn ref và input/output của các chặng; phải phân biệt plan/state/tuple, tên logic với node vật lý và metadata với runtime measurements. Một EXPLAIN không chứng minh memory lifetime, mọi đường lỗi hoặc tính đúng của extension C. Source ref/số dòng thiếu làm đáp án không tái lập được.

Lời giải C đầy đủ cho câu 3 chọn output bigint và NULL truyền qua. Thêm vào cùng `ad_advanced.c`, dùng các headers đã có:

```c
PG_FUNCTION_INFO_V1(ad_mul_i32);

Datum
ad_mul_i32(PG_FUNCTION_ARGS)
{
    int32 a = PG_GETARG_INT32(0);
    int32 b = PG_GETARG_INT32(1);
    int64 product = (int64) a * (int64) b;
    PG_RETURN_INT64(product);
}
```

Đăng ký trong script extension tương ứng:

```sql
CREATE FUNCTION ad_mul_i32(integer,integer) RETURNS bigint
AS 'MODULE_PATHNAME','ad_mul_i32'
LANGUAGE C IMMUTABLE STRICT PARALLEL SAFE;
```

Expected: `(0,2147483647)→0`, `(-7,6)→-42`, `(-2147483648,-2147483648)→4611686018427387904`, `(-2147483648,2147483647)→-4611686016279904256`, và input NULL→NULL. Hai cực trị nằm trong bigint nên không cần nhánh báo overflow cho contract này; cast phải diễn ra trước phép nhân. DDL với MODULE_PATHNAME thuộc script extension, không phải câu lệnh độc lập dùng nguyên placeholder. Code và expected được kiểm bằng lập luận miền số cùng model hữu hạn; chưa có build/load PostgreSQL.

## Biến thể và cách kiểm

Biến thể thay arithmetic contract, NULL/negative/boundary và lỗi loader có chủ đích trong environment riêng. Checker build và SQL phân biệt compile error, load error, SQL error mong đợi, output sai và runtime crash. Compiler pass chưa đủ; cần SQL regression và bằng chứng version. Proof số học có thể kiểm độc lập trên miền kiểu nhưng không thay ABI/runtime checks.
