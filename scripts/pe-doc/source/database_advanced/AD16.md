# AD16 · XQuery, API và lưu trữ XML

Đã học: AD68, S10, AD13. Nguồn: DSC 7e online §30.4.3–30.7. Môi trường: XQuery 3.1 engine do backend phục vụ qua web; ví dụ là ngôn ngữ XQuery, không phải câu SQL MySQL. Output ở đây là kết quả ngữ nghĩa chuẩn bị; chỉ lượt engine thực mới được ghi đã chạy.

## Query XML có thể vừa chọn vừa tạo cấu trúc mới

XPath giúp chọn nodes. Khi cần một report với tên tag khác, tổng tiền và các nhóm lồng, XQuery cho phép kết hợp path với expressions và constructors. Một kết quả XML không chỉ là bảng chuyển thành chuỗi: thứ tự nodes, attributes, namespace và cách tạo node đều có ý nghĩa. Bài AD68 đã giải tree/schema; ở đây ta theo một transformation tới output và cách triển khai nó.

## Ví dụ 1: FLWOR và tổng của sequence rỗng

```xquery
let $s := <shop>
 <order id="o1">
  <item sku="A"><qty>2</qty><price>10</price></item>
  <item sku="B"><qty>1</qty><price>25</price></item>
 </order>
 <order id="o2"/>
</shop>
return <totals>{
 for $o in $s/order
 let $total := sum(
  for $i in $o/item
  return xs:integer($i/qty) * xs:decimal($i/price)
 )
 order by string($o/@id)
 return <order id="{string($o/@id)}" total="{$total}"/>
}</totals>
```

FLWOR bắt đầu từ các bindings: for duyệt mỗi order; let gắn một sequence/value mà không tự nhân bindings như for; order by sắp bindings trước return; constructor tạo output. Kết quả có order o1 với total45 và o2 với total0. Lexical serialization có thể in 45 hay 45.0 theo type/engine; contract bài này chấm numeric decimal và cấu trúc, không byte-for-byte whitespace.

Với input sequence `(10,20)`, `for $x in (10,20) return <v>{$x}</v>` tạo hai v chứa10 và20; `let $x := (10,20) return <v>{sum($x)}</v>` tạo một v chứa30. Hai for độc lập trên customers2 và orders2 tạo4 bindings trước where; let giữ sequence2 orders trong mỗi customer binding. Where giữ/bỏ cả binding hiện tại. Vì thế số bindings và vị trí predicate quyết định grain của kết quả, giống yêu cầu xác định grain khi join SQL.

Trong constructor, `{...}` chuyển từ XML literal sang expression. `<v>$total</v>` chứa đúng chuỗi `$total`; `<v>{$total}</v>` chứa value. Có thể dựng cùng kết quả bằng computed constructor: `element order { attribute id {string($o/@id)}, attribute total {$total} }`. Attributes phải được tạo trước child content; `element title {$x/title}` sẽ bọc một title element vào title mới nếu $x/title đã là element. Muốn một title chứa chữ, dùng `element title {data($x/title)}` dưới giả định title đơn trị. Cách này tránh lặp tag ngoài ý muốn khi tái cấu trúc.

SUM sequence rỗng trong XQuery có quy tắc khác SUM trên nhóm SQL rỗng ở nhiều ngữ cảnh. Không lấy mẹo SQL NULL rồi áp thẳng. Ở đây o2 tồn tại nhưng không có items; nếu nghiệp vụ coi đó là dữ liệu thiếu chứ không phải tổng0, phải thêm kiểm required items và reject/đánh dấu review trước SUM. Lệnh cast cũng nêu rằng qty/price phải hợp lệ; chuỗi “hai” không được lặng lẽ thành0.

Thuật toán model: duyệt order; với mỗi order đặt subtotal=0, duyệt từng item, validate/cast rồi cộng; sau đó tạo node summary. Bất biến subtotal sau k items là tổng đúng k line đầu của order hiện tại. Vì order/items hữu hạn, tính kết thúc; cost O(O+I) ngoài sorting và serialization. Sorting order theo id thêm O(O log O). Engine có thể optimize/materialize khác; đây là cách tính nghĩa của ví dụ, không phải trace vật lý.

## Ví dụ 2: join hai nhánh XML

Document nhỏ có customers={(c1,An),(c2,Binh)}, orders={(o1,c1,45),(o2,c1,20)}. Giả sử mỗi customer_id chỉ có một customer; nếu không, join có thể nhân kết quả.

```xquery
let $d := <data>
 <customers><customer id="c1"><name>An</name></customer>
            <customer id="c2"><name>Binh</name></customer></customers>
 <orders><order id="o1" customer="c1" total="45"/>
         <order id="o2" customer="c1" total="20"/></orders>
</data>
return <report>{
 for $c in $d/customers/customer
 let $matches := $d/orders/order[@customer = $c/@id]
 order by string($c/@id)
 return <customer id="{string($c/@id)}">
  {$c/name}
  <order-count>{count($matches)}</order-count>
  <total>{sum(for $o in $matches return xs:decimal($o/@total))}</total>
 </customer>
}</report>
```

Kết quả c1 có count 2,total 65; c2 count 0,total 0. Vì for ngoài duyệt customers và let giữ cả matches, khách không order vẫn có node. Nếu viết `for $c ... for $o ... where ... return...`, ta tạo inner-join pairs và khách c2 biến mất. Nested query không tự bảo toàn parent: loại binding và constructor quyết định điều đó.

General comparison `=` giữa sequences có tính tồn tại cặp; value comparison như `eq` yêu cầu cardinality/type phù hợp. Với một element có hai id con, `$x/id = 'c1'` có thể TRUE vì một id khớp, không xác nhận schema đúng. Validate keys/cardinality hoặc dùng expression yêu cầu đơn trị khi contract đòi. `some` và `every` diễn lượng từ; every trên sequence rỗng là TRUE nên câu “mọi item hợp lệ” chưa bảo đảm có ít nhất một item.

### Nested report, aggregate và thứ tự ở từng cấp

Sau binding `$d` ở ví dụ2, thay return bằng đoạn sau để mỗi customer chứa các order của chính mình, sắp customer theo tổng giảm dần và orders theo id giảm dần:

```xquery
return <report>{
 for $c in $d/customers/customer
 let $matches := $d/orders/order[@customer = $c/@id]
 let $total := sum(for $o in $matches return xs:decimal($o/@total))
 order by $total descending, string($c/@id) ascending
 return <customer id="{string($c/@id)}" total="{$total}">{
  for $o in $matches
  order by string($o/@id) descending
  return <order id="{string($o/@id)}" total="{string($o/@total)}"/>
 }</customer>
}</report>
```

Kết quả c1(total65) chứa o2 rồi o1; c2(total0) vẫn có customer element rỗng. Sort ngoài không tự sort trong và ngược lại. Nếu IDs là chuỗi o10,o2 thì lexical order khác numeric suffix order; cần chọn key/collation đúng nghiệp vụ. Totals "10","2" phải cast numeric nếu muốn2 trước10. Thiếu key phụ khiến bài có thể không định nghĩa thứ tự giữa các tổng bằng nhau; contract có thể chấp nhận ties hoặc yêu cầu id làm tie breaker.

Aggregation không đòi flatten rồi nhân hai nhánh: let giữ matches, nested FLWOR tạo sequence numeric để sum. `distinct-values($d/orders/order/@customer)` cho một value c1, hữu ích nếu muốn chuyển từ order-centric sang customer-centric; nhưng nó bỏ khách c2 không có order. Trên values `(c1,c1,c2)`, distinct-values còn c1,c2; không dùng nó để khử hai order thật có total bằng nhau. Các hàm sum/count/distinct-values thuộc function namespace thường bind sẵn fn; path loại trùng theo node identity khác loại trùng theo atomic value. Source trình bày XQuery1.0 nên dùng nested aggregates để nhóm; XQuery3.1 còn có group by, nhưng query hiện tại đã nêu rõ grain và không phụ thuộc cú pháp mới đó.

Một lỗi existential cần tách khỏi join: order có items `(sku A,qty1)` và `(sku B,qty3)`. Predicate `item/@sku='A' and item/qty>=2` đúng vì hai điều kiện được thỏa bởi hai items khác nhau. `item[@sku='A' and qty>=2]` giữ hai điều kiện trên **cùng item**, nên order này không đạt. Viết query phải xác định các values có thuộc cùng một occurrence hay không.

## Ví dụ 3: giữ mixed content khi transform

Note `<note>Giao <em>nhanh</em> trước trưa.</note>` có ba child nodes. `string($note)` cho nội dung chữ “Giao nhanh trước trưa.” nhưng mất cấu trúc em. Nếu tạo `<message>{$note/node()}</message>`, children được đưa vào constructor theo thứ tự, giữ phần nhấn mạnh. Nếu đổi tag em thành strong, cần một hàm transform đệ quy theo kind/name node; không replace chuỗi tên tag vì nó có thể xuất hiện trong text/attributes khác.

Pseudocode transform tổng quát: input một node; text→tạo text với nội dung ấy; element→xác định expanded name đích, transform attributes theo policy, rồi transform children theo thứ tự; comment/processing-instruction→giữ/bỏ theo contract. Bất biến mỗi prefix children được biến đổi đúng thứ tự và không nhập nhầm text thành markup. Tree hữu hạn nên recursion dừng, O(N) khi mapping từng node O(1). Nếu schema đích cấm một element, policy reject hoặc chuyển đổi phải rõ; không tự bỏ âm thầm rồi tuyên bố lossless.

XQuery có function declarations, conditionals và type annotations để đóng gói transformation; namespaces và cast vẫn theo environment. Sequence không phải set: các for bindings có thể phát cùng value nhiều lần. Path expressions có quy tắc node identity/document order riêng; đừng deduplicate mọi output chỉ vì AD01 nói về tập hợp ở đại số quan hệ.

### Hàm có type contract và lượng từ

Đây là một XQuery module nhỏ độc lập; dùng dữ liệu không namespace để tập trung vào argument/return type:

```xquery
declare function local:total($o as element(order)) as xs:decimal {
 xs:decimal(sum(
  for $i in $o/item
  return xs:positiveInteger($i/qty) * xs:decimal($i/price)
 ))
};
let $o := <order id="o9">
 <item sku="A"><qty>2</qty><price>3.50</price></item>
 <item sku="B"><qty>1</qty><price>4</price></item>
</order>
return <result total="{local:total($o)}">{
 if (exists($o/item) and
     (every $i in $o/item satisfies xs:positiveInteger($i/qty) gt 0))
 then <status>has-positive-items</status>
 else <status>empty</status>
}</result>
```

Expected total11 và status has-positive-items. `local:` là namespace dành cho local functions; `xs:` chỉ XML Schema types. `element(order)` yêu cầu đúng một order element; `element(order)*` cho sequence0..n; `?` cho0..1; `+` cho1..n. Type annotation có thể bỏ nhưng mất một phần contract tường minh. Nếu source có namespace, tên element trong type cũng phải resolve đúng namespace. Không thể đưa hai orders vào hàm nhận một order rồi coi đó là tự map từng phần tử.

Điều kiện trên giả định schema/cast hợp lệ; qty=hai làm cast lỗi, không biến thành nhánh empty. Nếu cần phân loại lỗi, phải validate hoặc dùng castable/error handling riêng. `some $i in $o/item satisfies $i/@sku='A'` đúng khi có ít nhất một item A; every trên không item đúng nhưng exists sai. `if-then-else` lựa chọn giá trị/cấu trúc trả về, không sửa input tree. `string(<note>Giao <em>nhanh</em></note>)` cho “Giao nhanh”; `contains(...,'nhanh')` có thể kiểm nội dung sau string conversion, không tìm một element em. `number('hai')` có thể cho NaN theo quy tắc hàm; cast `xs:decimal('hai')` báo lỗi. Không giả mọi conversion đều cùng hành vi. [XQuery 3.1](https://www.w3.org/TR/xquery-31/) quy định constructors, sequence types và FLWOR.

XQJ là giao diện cho chương trình Java gửi XQuery tới XML data source rồi nhận sequence kết quả, có vai trò kết nối tương tự JDBC. Nó không thay DOM/SAX và không nói engine nằm trong browser. Trong web course, backend chọn engine, bind parameters và trả output; learner chỉ làm query trong fixture được cấp.

### Kiểm khóa bằng query và đổi một XML view

Query cũng có thể chẩn đoán constraint khi chưa có schema validator. Với catalog không namespace của AD68, hai biểu thức sau trả boolean theo contract `sku` là đúng một attribute bắt buộc, so sánh chuỗi phân biệt hoa/thường và không tự trim:

```xquery
let $products := $c/product
return
 (every $p in $products satisfies exists($p/@sku))
 and count($products) = count(distinct-values($products/@sku))
```

```xquery
every $p in $c/purchase satisfies
 (exists($p/@sku) and $p/@sku = $c/product/@sku)
```

Bind `$c` vào catalog của AD68: cả hai đúng. Thêm product sku A thứ hai làm kiểm key sai; đổi purchase sku C làm keyref sai. Kiểm keyref không tự kiểm key: hai products A và purchase A vẫn cho keyref đúng dù khóa trùng. Attribute XML không lặp cùng tên nên tồn tại @sku đủ cho cardinality một ở fixture này; nếu key dùng child sku thì cần `count(sku)=1`, không chỉ exists. Trên schema có typed keys, collation/typed equality và scope khác, hai query giản lược này phải đổi theo contract; không nhận chúng là validator tổng quát cho XML Schema.

Một chuyển đổi view cụ thể dùng source `<shop><order id="o1" customer="c1" total="45"/><order id="o2" customer="c1" total="20"/></shop>` và tạo table/row/column shape cho quan hệ Orders. Bind `$s` vào source:

```xquery
<Orders>{
 for $o in $s/order
 return <row>
  <id>{string($o/@id)}</id>
  <customer>{string($o/@customer)}</customer>
  <total>{xs:decimal($o/@total)}</total>
 </row>
}</Orders>
```

Expected hai row với (o1,c1,45),(o2,c1,20). Chiều ngược là `for $r in $v/row return <order id="{string($r/id)}" customer="{string($r/customer)}" total="{xs:decimal($r/total)}"/>`, bọc trong shop. Với đúng một id/customer/total hợp lệ trên mỗi row, phép thuận/ngược giữ ba values và thứ tự rows; nó không giữ lexical total45.00 hay unknown fields. Chứng minh theo từng order: constructor tạo đúng một row theo thứ tự input và copy/cast đúng ba fields; phép ngược lấy đúng ba fields ấy, nên induction theo sequence cho round trip trên miền đã nêu. Trước shred, phải kiểm key/type/missing theo contract; `string(())` thành chuỗi rỗng không phải cách hợp thức hóa field bắt buộc bị thiếu.

## DOM, SAX và chi phí của API

DOM đưa document thành cây truy cập ngẫu nhiên. Tiện cho ancestor/sibling, nhiều pass hoặc sửa cấu trúc nhưng bộ nhớ tăng theo document và overhead nodes. SAX/event API phát start-element,text,end-element; ứng dụng giữ state cần thiết. Với report subtotal mỗi order, stack giữ order hiện tại và accumulator; có thể xuất khi đóng order, không cần giữ mọi orders trong RAM.

Streaming không tự làm mọi query O(depth) memory. Join một customer được khai báo cuối file với hàng triệu orders đầu file có thể cần buffer/index hoặc pass khác. Sort toàn report cũng thường cần materialization/external sort. Event text có thể bị parser tách nhiều chunks, nên không giả mỗi qty luôn tới trong đúng một callback. Gom text của element theo policy rồi cast tại end-element là một cách rõ.

DOM traversal có thể viết ở dạng API pseudocode: lấy documentElement, duyệt firstChild rồi nextSibling, kiểm nodeType/namespaceURI/localName, đọc attributes bằng getAttributeNS và text nodes bằng data. Thêm/xóa node dùng các thao tác appendChild/removeChild/setAttribute theo API của implementation. `getElementsByTagName` thường trả các descendants phù hợp, không chỉ direct children; `<order><note><item/></note><item/></order>` có hai descendant item nhưng chỉ một child item. Khi contract cần order/item trực tiếp, duyệt child nodes và lọc element/name hoặc dùng XPath tương ứng. DOM thuận tiện cho sửa cây nhưng một chuỗi calls điều hướng không phải declarative query plan trên collection lớn.

SAX có thể dựng cây tùy biến thay vì DOM; thuật toán model như sau:

```text
stack := [document_node]
start_element(name, attributes):
    n := new_element(name)
    append_child(stack.top, n)
    attach_attributes(n, attributes)
    stack.push(n)
characters(chunk):
    append_text_or_merge_adjacent_text(stack.top, chunk)
end_element(name):
    assert stack.top.name = name
    stack.pop()
```

Sau mỗi event, stack là đường từ document tới element đang mở; mọi prefix đã parse được gắn vào đúng parent theo thứ tự input. Với `<n>A<b/>B</n>`, stack lần lượt [doc,n], text A dưới n, [doc,n,b], đóng b về n, text B dưới n, đóng n về doc. Thuật toán kết thúc vì số events hữu hạn; cost O(N) với append O(1), memory O(N) cho cây kết quả và O(depth) cho stack. Nếu chỉ cộng qty/price từng item, bỏ cây và giữ accumulator/text buffer cần thiết sẽ tiết kiệm RAM; độ dài text và buffer riêng vẫn phải được tính. API event không có nghĩa đương nhiên không tạo cây.

## Lưu XML theo ba cách

Lưu nguyên chuỗi giữ serialization gần nguồn và dễ nhận dữ liệu mới; query path có thể phải parse nhiều, update một node dễ thành rewrite lớn nếu không có hỗ trợ riêng. Tree representation lưu Node(id,parent_id,ordinal,kind,namespace,local_name,value); child path là join theo parent, descendant cần traversal/label index. Phải giữ ordinal/mixed content, không chỉ bảng tag/value.

Map theo schema quan hệ, chẳng hạn Order,Item(order_id,pos,sku,qty,price), giúp FK/type/index và SQL report. Nó phù hợp khi vocabulary ổn định, nhưng cần mapping riêng cho optional/mixed/unknown fields; không phải mọi XML đều round-trip qua vài bảng cố định. Shredding là tách XML vào representation; publishing là dựng XML từ quan hệ. Quy tắc round trip cần chứng minh thông tin được giữ: node kind, names/namespaces, occurrence/order và values theo phạm vi contract.

Native XML storage/index hỗ trợ tree/path trực tiếp; một column type xml có thể giữ mỗi document một row, với string/binary layout nội bộ và XML indexes tùy backend. XQuery có thể được tích hợp trong SQL để áp lên từng document; đây khác việc tự shred mọi node vào rows của tree table. SQL/XML cung cấp biểu thức constructors/query integration ở hệ hỗ trợ. Không suy rằng MySQL8.4 có toàn SQL/XML/XQuery chỉ vì nó lưu được text/XML string. Web service/data mediation có thể dùng transformation để đổi vocabulary giữa nguồn và đích; semantic mapping và schema evolution vẫn là trách nhiệm tác giả.

### Chọn representation từ yêu cầu query và round trip

Flat file XML hợp với trao đổi/snapshot nhỏ và có sẵn parsers, nhưng tự nó không cung cấp transaction nhiều documents, isolation khi cập nhật đồng thời, hay quyền truy cập ở mức record. Một XML database cần thêm transaction, authorization, client protocol và quản trị, ngoài parse/path. Tái dùng storage manager hoặc relational DB có thể cung cấp các phần hạ tầng đó; model XML không tự bảo đảm các thuộc tính ấy.

Với string storage, có thể chia mỗi order thành một row `OrderPayload(id,customer_id,xml_text,schema_version)`. Index customer_id giúp lọc trước khi parse. Giữ customer_id trùng với attribute trong payload đòi một nguồn sự thật hoặc update/validation đồng bộ; đổi XML mà quên cột index sẽ gây kết quả sai. Ở hệ hỗ trợ expression/function index cho XML extraction, index biểu thức có thể tránh duy trì cột lặp bằng tay; khả năng và độ deterministic của hàm phải kiểm theo backend. Không có index/extraction support, việc tìm sku trong xml_text cần scan/parse; LIKE chuỗi không thay semantic path vì whitespace, prefixes và escaping có thể khác.

Tree table cụ thể cho `<note>Giao <em>nhanh</em>!</note>` có thể lưu:

| id | parent_id | ordinal | kind | local_name | value |
|---|---|---|---|---|---|
| 1 | NULL | 1 | element | note | NULL |
| 2 | 1 | 1 | text | NULL | Giao␠ |
| 3 | 1 | 2 | element | em | NULL |
| 4 | 3 | 1 | text | NULL | nhanh |
| 5 | 1 | 3 | text | NULL | ! |

␠ chỉ một space dữ liệu. Schema thật thêm document_id, namespace URI và attributes với owner/name/value; ordinal của child sequence không áp thứ tự ngữ nghĩa lên attributes. FK parent_id và unique(document_id,parent_id,ordinal) cho child nodes giúp giữ cấu trúc; root policy và acyclicity còn cần kiểm. Dựng note từ children của1 theo ordinal cho text,em,text; chỉ lấy value ở id1 sẽ mất toàn nội dung. Một child path nhiều bước trở thành nhiều joins qua parent_id; descendant cần recursion hoặc index nhãn. Reassembly một subtree lớn cần nhiều rows, là chi phí của generic representation.

Schema mapping giữ các complex elements thành relations; scalar children/attributes thành columns có SQL type phù hợp. Root chỉ làm wrapper và không có attributes dữ liệu có thể được bỏ ở mapping; root chứa metadata nghiệp vụ thì phải được giữ hoặc map metadata rõ ràng. Từ shop có thể tạo `Orders(order_id,customer)`, `Items(order_id,pos,sku,qty,price)` và `Notes(order_id,xml_subtree)`; FK items.order_id→Orders và PK(order_id,pos) bảo toàn occurrences/order ngay cả hai item cùng sku. Một complex child xuất hiện tối đa một lần có thể flatten vào parent nếu vẫn phân biệt được absent với present-empty theo contract. Simple child lặp cũng cần relation với pos; không ép vào một scalar column. Unknown subtree giữ string/tree để tránh mất fields. Publishing dựng order và items theo pos; shredding validate rồi tách đúng rows, xử lý cả batch trong transaction theo policy. XML view có thể là virtual: query XML trên dữ liệu relational qua mapping mà không lưu thêm document vật lý.

Nếu contract cho FD sku→description hiện hành, tách Product(sku,description) khỏi Items; nếu supplier_id→địa chỉ hiện hành, tách Supplier(supplier_id,address) khỏi Orders. Các FKs giữ quan hệ và joins phục hồi thông tin. Nhưng description/địa chỉ được chụp tại ngày đặt hàng có thể khác hiện hành: FD theo sku hoặc supplier_id đơn thuần không đúng trên lịch sử; giữ snapshot hoặc key có version/time. Shredding theo hình dạng XML chưa tự chuẩn hóa hết redundancy, còn chuẩn hóa không được xóa thông tin lịch sử bằng một FD không có thật.

Một document cho part P chứa subpart Q qty2 và R qty1 cần representation đệ quy. Nếu tên part xác định duy nhất cùng cấu trúc, dùng `Part(part_id,name)` và `Component(parent_part_id,pos,child_part_id,qty)`, hai FKs về Part, unique(parent_part_id,pos). Không lặp toàn cây Q ở mỗi chỗ dùng. Nếu cùng tên có phiên bản/structure khác thì phải đưa version hoặc occurrence identity vào key; giả định tên duy nhất không còn đúng. Thứ tự cho round trip cần pos, traversal phải xử lý cycle theo policy BOM. Đây là chuyển giao từ mapping một cấp sang schema đệ quy, không mặc nhiên tuyên bố mọi đồ thị sẽ xuất thành cây hữu hạn.

Để hiểu một tree index có thể lọc gì, dùng mô hình DFS đánh số lúc vào/ra node. Cây `shop(order(itemA,itemB),note)` có nhãn interval: shop[1,12],order[2,7],itemA[3,4],itemB[5,6],note[8,11] (note có text[9,10]). Node x là ancestor của y khi `pre(x)<pre(y)` và `post(y)<post(x)`; child còn cần depth(y)=depth(x)+1. Query tìm item descendants của order chỉ xét nhãn item rồi kiểm khoảng trong[2,7], nhận itemA/itemB, không nhận note. Proof: DFS hoàn tất mọi descendants trước khi đóng x, và chỉ các descendants có cả hai mốc nằm trong interval ấy. Insert có thể buộc đổi nhãn trong cách đánh số tĩnh này; không hứa cập nhật O(1). Đây là ví dụ PE bổ sung cho special-purpose indexes ở §30.6.2.5, không phải khẳng định engine XML nào dùng đúng layout này.

SQL/XML ở §30.6.3 cũng cần một phép dựng cụ thể. Cho quan hệ `Customer(id,name)={(1,'An'),(2,NULL)}`; trong **mô hình SQL/XML chuẩn**, `XMLELEMENT(NAME customer, XMLATTRIBUTES(id AS id), XMLFOREST(name AS name))` cho node customer id1 chứa name An và customer id2 không có node name. NULL bị bỏ theo quy tắc constructor đang xét, không tạo chuỗi "NULL"; chuỗi rỗng lại có thể tạo element name rỗng. `XMLAGG` gom các nodes thành sequence, `XMLCONCAT` nối sequences, và phải định nghĩa thứ tự nếu cần xuất lại đúng. Những biểu thức này cần backend có capability SQL/XML tương ứng; không gửi chúng sang MySQL như mã đã được kiểm.

SQL/XML còn định nghĩa mapping SQL types→schema types, schema/table→XML: một kiểu mapping mặc định dùng element tên table, mỗi row thành row element, mỗi column thành subelement. Với Customer trên có dạng `<Customer><row><id>1</id><name>An</name></row>…</Customer>`; quy tắc NULL và names phải thuộc mapping đã chọn. Đó là export schema/table tiêu chuẩn, khác một business vocabulary customer-centric tự thiết kế.

Ví dụ **mô hình SQL/XML**, dùng `Orders(id,customer,total)={(o1,c1,45),(o2,c1,20)}`:

```sql
SELECT XMLELEMENT(NAME "customer",
         XMLATTRIBUTES(customer AS "id"),
         XMLAGG(
           XMLELEMENT(NAME "order",
             XMLATTRIBUTES(id AS "id"),
             XMLELEMENT(NAME "total", total))
           ORDER BY id))
FROM Orders
GROUP BY customer;
```

Expected một customer c1 chứa o1/total45 rồi o2/total20. GROUP BY chọn nhóm; XMLAGG gom đúng nodes mỗi nhóm và ORDER BY trong aggregate quyết định thứ tự children. Chỉ đọc Orders nên không tự tạo c2 rỗng; muốn giữ c2 cần outer construction từ Customer và aggregate/filter đúng policy NULL. `XMLFOREST(name AS "name")` bỏ element khi name NULL; `XMLELEMENT(NAME "name", name)` vẫn tạo name element với body rỗng khi value NULL. `XMLCONCAT(<a/>,<b/>)` ở dạng ý nghĩa nối hai nodes thành forest, không tự thêm root document; một XML document serialize cuối phải có root theo contract. Các minh họa SQL/XML này là expected semantics, chưa có execution log của backend hỗ trợ.

### XML trong ứng dụng, service và mediator

Configuration có các nhóm settings tùy chọn, bookmarks có thứ tự và trusted-sites lặp là ví dụ dữ liệu structured phù hợp cây. Một query plan có operator children cũng có thể serialize để server gửi cho client vẽ. Các định dạng office như ODF/OOXML dùng XML trong package để giữ cấu trúc documents; việc nhận một file office không đồng nghĩa nó chỉ chứa một XML text document. Những ví dụ này giải thích lợi ích vocabulary chung và parser dùng lại; chọn XML vẫn cần cân chi phí kích thước/query của ứng dụng.

Chuẩn trao đổi chuyên ngành phải thống nhất **cả schema lẫn semantics**: chemical data cần đơn vị nhiệt độ và cấu trúc phân tử, shipping cần sender/receiver/goods/value, B2B cần catalog, quote, inventory và purchase order. RosettaNet là ví dụ họ chuẩn B2B được source dùng; một tag price chỉ có nghĩa rõ khi biết currency, tax và unit. Dữ liệu nested giúp một bên nhận trọn message mà không hiểu relational schema nội bộ của bên gửi; đổi lại có thể lặp description/address và phải xử lý version.

Web service cung cấp operations giới hạn thay vì cho đối tác SQL trực tiếp vào database. Trong mô hình SOAP, request/response dùng XML envelope; message nghiệp vụ nằm trong Body, còn Header dành metadata mở rộng. Ví dụ fixture operation `GetStock(sku A)` trả `Stock(sku A,available 7)` hoặc SOAP Fault; client phải phân biệt kết quả thành công và lỗi trước khi đọc available. HTTP thường làm transport nhưng SOAP không đồng nhất với HTTP. WSDL mô tả operations, input/output types, binding và endpoint; UDDI là mô hình registry/discovery được chương source giới thiệu. Những thuật ngữ này là kiến trúc của họ chuẩn, không phải khẳng định mọi dịch vụ hiện nay có public UDDI hoặc SOAP endpoint. Vị trí Body/Header được đối chiếu [SOAP 1.2](https://www.w3.org/TR/soap12-part1/#soapbody), sửa cách mô tả giản lược “parameters trong headers” của source.

Ví dụ mediator so sánh hai nhà cung cấp: nguồn A xuất `<offer sku="A" currency="USD" price="10" shipping="2"/>`; nguồn B xuất `<offer code="A" currency="USD" total="11"/>`, contract nói total B đã gồm shipping. Mediator map code→sku, tính landed_total A=12 và B=11 rồi so cùng currency. Không cộng shipping lần nữa vào B; nếu B dùng VND thì phải có tỷ giá/thời điểm và policy quy đổi, hoặc giữ hai currency chưa so hạng. Wrapper cho một HTML page phải nhận diện đúng fields rồi tạo XML trung gian; đổi layout có thể làm wrapper lấy nhầm giá nên cần fixture/drift detection. Mediator hợp nhất qua schema chung, giải quyết aliases, cùng tên khác nghĩa, identity và provenance trước khi dùng XQuery/XSLT transform. Parse được XML không tự giải quyết những khác biệt ngữ nghĩa này.

## Biến thể và cách kiểm

Thêm empty sequence, duplicate customer keys, namespace mới, mixed content và schema mismatch. Checker XML so parsed structure/value theo contract, chỉ so bytes nếu đề thật sự cần serialization nguyên. Feedback chỉ ra binding mất hoặc node/type bị thay. API streaming được chấm cả state/memory assumptions, không chỉ output ở file nhỏ.

## Học trên web

Workspace gồm source tree, query, output tree và tab storage mapping. Backend XML engine/version chạy query thật trong fixture; không truy cập URI/doc ngoài attempt tùy ý. Nếu demo chỉ walk tree thì ghi model subset. Người học có thể bấm một output node để thấy input witnesses, rồi nộp transformation trên document mới.
