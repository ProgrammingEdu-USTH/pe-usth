# AD32 · External sort và mô hình I/O

Đã học: Q01, M06; selection/access path sâu ở AD76. Nguồn: DSC7e §15.1–15.4. Môi trường: external-sort model trên web; số I/O dưới đây là page transfer theo giả định, không phải thời gian MySQL đo được.

Query ORDER BY cần kết quả đã sắp dù dữ liệu lớn hơn RAM. Nếu có 20 page nhưng chỉ dành 5 page buffer, gọi sort trên toàn file không phải một thuật toán khả thi trong budget đó. External merge sort tạo những đoạn đã sắp vừa RAM, rồi trộn chúng mà không cần giữ toàn dữ liệu cùng lúc.

Đọc qua index chỉ cho thứ tự **logic**, không tự đặt record theo thứ tự vật lý. Nếu1.000 row nằm trên100 data page mà nonclustering index dẫn qua RID rải rác, một lượt ordered fetch có thể gần1.000 page accesses khi cache không giữ được page; một physical scan chỉ có100 page, cộng công việc sort riêng. Clustering/covering/cache có thể đổi phép so này. Vì vậy index có cùng sort key có thể tránh phép sort nhưng chưa chứng minh tổng I/O nhỏ hơn external sort; input đã vừa RAM có thể dùng thuật toán sort trong RAM với cùng comparator.

## Input, output và điều kiện bộ nhớ

Đặt N là số page input, B là số buffer page dành cho sort. Một run là file/đoạn đã có thứ tự theo comparator đã định nghĩa, gồm kiểu, hướng sắp, NULL và collation khi phù hợp. Ta giả định run ban đầu tối đa B page, có thể đọc/sort trong RAM; merge dùng một output buffer nên fan-in tối đa B−1. Với nhiều run cần B≥3 để mỗi vòng có thể giảm số run. Nếu B=2 thì fan-in 1 không hợp nhất hai run; không áp công thức log cơ học.

Thuật toán tạo run:

```text
runs = []
while input còn page:
    batch = đọc tối đa B page
    sort tất cả record trong batch bằng comparator
    ghi batch thành một run; thêm run vào runs
while count(runs) > 1:
    next_runs = []
    for từng nhóm tối đa B-1 run:
        merge nhóm thành một run mới
        thêm run mới vào next_runs
    runs = next_runs
return run duy nhất, hoặc stream lượt merge cuối theo contract
```

Đọc record có thể cắt qua page theo file format; model bài dùng record đã được page manager cung cấp, không tự cắt byte giữa record. Merge giữ một page đầu cho mỗi input, heap/priority queue hoặc phép chọn tương đương để lấy record nhỏ nhất trong các head còn sống. Output buffer đầy thì ghi/đẩy ra và tiếp tục; input buffer cạn thì nạp page kế của đúng run đó.

## Vì sao merge không bỏ hoặc đảo record?

Mỗi input run đã sắp nên record chưa xuất nhỏ nhất của run nằm ở head. Nhỏ nhất trong các head vì thế là nhỏ nhất trong toàn bộ record chưa xuất của nhóm. Xuất nó bảo toàn output-prefix đã sắp và loại đúng một record khỏi tập chưa xuất. Quy nạp tới khi mọi run cạn: output vừa có thứ tự vừa có cùng multiset input. Khóa bằng nhau phải giữ đủ số bản sao; nếu cần stable sort, thêm thứ tự gốc/tie rule và dùng nhất quán ở mọi pass.

Tạo run giữ multiset và làm từng run có thứ tự. Mỗi merge giữ hai tính chất đó và giảm số run khi fan-in≥2. Có hữu hạn record, nên mỗi merge dừng; số run giảm qua các vòng nên thuật toán toàn cục dừng. Đây là proof về model comparator/buffer đã cho, chưa phải proof mọi implementation xử lý lỗi file/concurrency đều đúng.

## Đếm pass và transfer

Số run đầu R0=ceil(N/B). Khi R0>1, số merge pass là ceil(log_(B−1)(R0)) nếu mỗi pass trộn tối đa B−1 và dùng cách gom chuẩn. Để tránh sai ở ca rỗng hoặc đã vừa RAM, có thể tính trực tiếp R←ceil(R/(B−1)) cho đến R≤1. Pass tạo run cũng là một pass.

Nếu mọi pass đọc và ghi toàn bộ N page, cost=2 N×(1+số merge pass). Giả định page output cùng tổng kích thước với input và bỏ metadata/seek. Nếu lượt cuối pipeline thẳng vào toán tử tiếp theo, có thể bỏ N lần ghi cuối trong mô hình; không bỏ luôn N lần đọc cần cho merge. Nếu query yêu cầu materialize kết quả để dùng lại, không được tự nhận tiết kiệm phần ghi đó.

Ví dụ 1: N 20,B 5. Tạo 4 run, fan-in 4 nên một merge pass. Tổng 2 pass và 80 transfer nếu ghi output; nếu stream cuối,60. Con số không gồm scan của một toán tử khác nếu scan ấy đã là chính input của sort; cần tránh tính cùng I/O hai lần trong plan cost.

Ví dụ 2: N 100,B 4. Tạo 25 run. Các vòng còn 9,3,1 run: ba merge pass, tổng 4 pass. Cost 800 transfer; bỏ ghi cuối còn 700. Dùng log rồi làm tròn sai có thể quên vòng 25→9 hoặc 9→3. Một nhóm cuối chỉ có một run vẫn cần chính sách: nếu chỉ truyền tham chiếu thay vì copy, cost cụ thể có thể thấp hơn công thức upper-bound đọc/ghi đầy đủ. Bài phải khai báo cách hạch toán, không trộn hai mô hình.

Ví dụ 3: sáu page, mỗi page một số, input[9,1,5,8,2,3], B 3. Run đầu[1,5,9] và[2,3,8]. Merge lần lượt lấy 1,2,3,5,8,9. Head của run một sau xuất 1 là 5, không phải đọc mọi record còn lại để chọn lại. Nếu một run cạn, chép/stream phần còn lại đã sắp, vẫn giữ duplicates nếu có.

## Chi phí khác và các trường hợp biên

Nếu N≤B, chỉ cần sort trong RAM sau một lần đọc; output được ghi hay stream quyết định phần còn lại. Nếu N=0, trả empty theo contract, không tính log 0. Nếu record có kích thước biến, budget theo byte và các buffer cần metadata; B page là mô hình dễ tính, không cho phép heap vượt RAM vì số record nhiều hơn dự kiến.

Trên disk từ, số seek và block transfer có vai trò khác; trên SSD hoặc dữ liệu trong RAM, CPU/comparison/cache có thể chiếm ưu thế. Priority queue có chi phí xấp xỉ O(log F) mỗi record với F input run, nhưng giảm pass bằng fan-in lớn có thể tăng bộ nhớ/metadata. Prefetch, double buffering và ghi theo lô giúp thực thi nhưng không đổi multiset/ordering contract.

§15.4.2 cho mỗi run và output `bb` buffer page để đọc/ghi theo lô, nên fan-in là `floor(B/bb)−1`, không còn B−1. Ví dụ N=100,B=20: bb=1 tạo 5 run rồi một merge; bb=4 chỉ trộn 4 run/lượt, cần 5→2→1, hai merge. Buffer mỗi run lớn hơn có thể giảm seek nhưng tăng transfer vì thêm pass. Với p≥1 merge pass và final stream, model bỏ qua run lẻ không copy cho `N(2p+1)` transfer và khoảng `2·ceil(N/B)+ceil(N/bb)·(2p−1)` seek. Đây là hai hạng chi phí riêng có hệ số latency riêng; khi N≤B hoặc fan-in<2 phải dùng các ca biên đã nêu thay công thức này.

Nếu input đã có thứ tự hữu ích từ index hoặc toán tử trước, có thể tránh hoặc giảm sort. Nếu chỉ cần top K, thuật toán khác có thể giữ heap K phần tử; không cần bắt mọi query LIMIT phải sort toàn file. AD37 phân biệt tối ưu top K với yêu cầu ties/order đầy đủ.

## Luyện tập

1. N 45,B 6: tính số run đầu, số vòng merge, transfer khi ghi và khi stream cuối. Ghi từng lần số run thay đổi.
2. N 2,B 5 và N 0,B 5 có cần dùng công thức log không? Trả cost theo contract đọc/ghi file kết quả; phân biệt empty với một page rỗng vẫn được tính là input.
3. Hai run[1,4,4] và[2,4,7]. Tự merge, giữ duplicates. Một implementation khi hai head bằng nhau chỉ xuất một bản rồi tiến cả hai có sai ở đâu?
4. Tự thiết kế dữ liệu và budget gây ít nhất ba merge pass. Viết pseudocode/trace, invariant multiset+order và cách phát hiện input đổi comparator giữa hai pass. Nộp cost với output policy rõ.
5. N=100,B=20,final stream: so bb=1 và bb=4 về fan-in,run counts,transfer và seek theo model bỏ qua savings của run đơn. Với tT=0,1 ms/transfer,tS=4 ms/seek,tính cost kết hợp; vì sao tăng transfer vẫn có thể nhanh hơn? So thêm ordered fetch qua nonclustering index1.000 row/100 page,không đoán cache hoặc covering khi chưa được cho.

## Gợi ý

Tầng 1: pass tạo run tính cả đọc và ghi. Merge có một output buffer. Key bằng nhau không biến sort thành DISTINCT.

Tầng 2: câu 1 ceil 45/6=8 run, fan-in 5. Câu 4 có thể chọn B 3 và đủ nhiều run để 8→4→2→1 hoặc hơn; comparator cần giống nhau ở mọi run.

## Đáp án và lập luận

1. 8→2→1 nên hai merge pass, tổng 3 pass:270 transfer; stream cuối 225. Đây là mô hình mọi pass đọc/ghi đầy đủ; ghi riêng giả định khi dùng tối ưu truyền run đơn.
2. N 2 vừa RAM, đọc 2 ghi 2 thành 4; nếu stream thì chỉ 2 đọc. N 0 không có page input/output cần transfer theo model, nên 0. Nếu file có header/empty page được tính vào N thì phải hạch toán theo cách định nghĩa ấy.
3. [1,2,4,4,4,7]. Có ba bản 4; xuất một rồi tiến cả hai làm mất ít nhất một bản khi có head trùng, đổi bag semantics. Sort chỉ sắp, không loại trùng.
4. Chấp nhận mọi dữ liệu/budget đúng, trace mọi pass và proof giữ multiset. Test kiểm sorted output, đếm từng record/RID và budget. Comparator đổi giữa pass có thể khiến head không còn đại diện nhỏ nhất, phá proof; cần khóa version/collation/direction.
5. R0=5. bb1:fan-in19,5→1,p1,transfer100×3=300,seeks2×5+100×1=110,cost30+440=470 ms. bb4:fan-in4,5→2→1,p2,transfer100×5=500,seeks10+25×3=85,cost50+340=390 ms. Đây là tổng model transfer/seek,không thời gian engine đo; bb4 bớt seek đủ bù thêm transfer với hệ số đã cho. Nonclustering ordered fetch có thể đọc lại gần1.000 page accesses thay vì100 unique pages nếu mỗi RID gây miss; không nhận thứ tự logic là physical sequential access, và phải cộng sort/index-read cost phù hợp trước khi chọn.

## Biến thể và cách kiểm

Model sinh N,B, run lengths và duplicate distribution, có ca vừa RAM, rỗng, thiếu buffer và final-run không đầy. Oracle so output với sort độc lập và multiset input. Phản hồi nhầm pass chỉ đúng vòng còn bị bỏ; không chỉ đưa số cuối. Model I/O không được ghi thành thời gian đo engine.

## Học trên web

Người học phân buffer input/output, xem run và bấm merge từng nhóm; bảng transfer cập nhật từ thao tác. Bài độc lập nhập trace hoặc pseudocode trên web. Nếu có backend đo sort, raw plan/workload/runtime được lưu ở activity riêng.
