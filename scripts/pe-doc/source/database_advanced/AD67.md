# AD67 · Từ file đến cloud: hợp đồng DBMS và tiến hóa kiến trúc

Đã học: C01 của bộ 85 bài và phần ứng dụng cơ bản. Nguồn: DSC7e §1.1–1.9; liên hệ Lecture1 USTH. Môi trường: phân tích yêu cầu và mô hình lỗi trên web.

Một ứng dụng bắt đầu bằng file CSV để quản lý đơn. Khi thêm người dùng, nó cần ngăn hai người cùng bán chiếc cuối, phân quyền ai được xem giá vốn và phục hồi sau khi máy dừng giữa ghi. Nếu chỉ đổi CSV thành một bảng SQL mà không định nghĩa các bảo đảm này, ứng dụng vẫn có thể sai dù query trả được dữ liệu.

## Tại sao một DBMS có nhiều trách nhiệm?

File processing dễ sinh dữ liệu trùng và khác nhau giữa các ứng dụng; mỗi chương trình tự làm truy xuất, kiểm ràng buộc và phục hồi. Đọc một field có thể cần biết layout vật lý, khiến thay đổi cách lưu ảnh hưởng nhiều code. Isolation dữ liệu, access khó, atomic update, concurrent access và security là những vấn đề cụ thể, không chỉ danh sách tính năng quảng bá.

Data isolation ở đây là dữ liệu bị chia giữa nhiều file/định dạng, gây khó kết hợp. Nó khác transaction isolation, tức cách các giao dịch đồng thời được phép nhìn thấy và ảnh hưởng nhau. Hai nhóm vấn đề có chung từ isolation nhưng cần cơ chế giải quyết khác nhau.

Ứng dụng có thể lưu giao dịch bán hàng, lịch sản xuất, đăng ký môn, chuyến bay, cuộc gọi, tài liệu, vị trí địa lý hoặc quan hệ người dùng. Điểm chung là dữ liệu cần tổ chức, truy cập có kiểm soát và bảo vệ khi nhiều tác vụ cùng sử dụng. OLTP thường có nhiều lượt đọc/ghi nhỏ; phân tích thường tổng hợp nhiều dữ liệu để tìm xu hướng hoặc xây mô hình dự đoán. Một cửa hàng vừa ghi từng đơn ở quầy vừa dự báo hàng cần nhập có thể cần cả hai, với yêu cầu độ mới và tài nguyên khác nhau.

Ví dụ 1: chuyển10 từ A sang B bằng cách sửa file A rồi file B. Crash giữa hai lần ghi làm tổng tiền giảm10. Cần unit of work có log/recovery hoặc protocol tương ứng; backup mỗi đêm không tự làm mỗi lần chuyển atomic. Advanced đi từ yêu cầu này tới WAL, concurrency và distributed commit.

## View, logical schema và physical storage

Instance là dữ liệu ở một mốc; schema là cấu trúc/ràng buộc mô tả instance hợp lệ. Physical level nói cách đặt page/index; logical level nói quan hệ/thuộc tính/ràng buộc; view level cho nhóm người dùng thấy phần hoặc phép biến đổi phù hợp. View lọc row chưa tự thu hồi quyền truy cập base; security contract cần thực thi quyền.

Physical data independence hướng tới đổi cách lưu mà không đổi logical interface. Logical changes có thể cần migration/view compatibility. Cùng SQL chưa hứa cùng performance hay thứ tự row tình cờ. Query không ORDER BY không được chấm theo thứ tự file cũ.

DDL khai báo schema; DML thao tác dữ liệu; ngôn ngữ/API còn có quyền, routines và transaction boundaries. Declarative query nói kết quả cần, không chỉ định một thuật toán vật lý duy nhất. Optimizer được đổi plan nhưng phải giữ semantics với NULL, bags, types và constraints.

Schema cũng có các mức tương ứng: physical schema mô tả cách lưu; logical schema mô tả dữ liệu và ràng buộc; view schema hay subschema mô tả phần giao diện dành cho một nhóm dùng. Từ schema trong phân tích này không chỉ có nghĩa namespace của một sản phẩm SQL. Thay một giá trị của instance khác việc thay định nghĩa schema.

## Nhắc lại bốn họ mô hình dữ liệu

Một data model cung cấp khái niệm để mô tả dữ liệu, quan hệ, ý nghĩa và ràng buộc. Nó khác một instance cụ thể và khác thuật toán lưu trữ.

| Họ mô hình | Cách mô tả | Ví dụ trong hệ đăng ký môn |
|---|---|---|
| Relational | Các relation với thuộc tính; query kết hợp dữ liệu qua giá trị | Student, Course, Enrollment có khóa và foreign key |
| Entity–relationship | Entity, relationship và các ràng buộc để thiết kế khái niệm | Student đăng ký Course; một đăng ký có grade |
| Semi-structured | Các bản ghi có thể khác tập thuộc tính hoặc chứa cấu trúc lồng nhau | Hai hồ sơ JSON có thể có hoặc không có trường awards |
| Object-based/object-relational | Kiểu phức hợp, identity, phương thức và quan hệ giữa kiểu/object | Một kiểu Address dùng lại trong nhiều đối tượng hoặc bảng |

ER giúp đặt câu hỏi nghiệp vụ trước khi mapping sang bảng; JSON cho phép linh hoạt về hình dạng nhưng ứng dụng vẫn cần quy tắc để hiểu dữ liệu. Mô hình object-relational có thể đưa kiểu và hành vi vào hệ quan hệ; ORM là một lớp mapping trong ứng dụng, không phải chính mô hình lưu trữ đó. AD09, AD13 và AD14 đi sâu ba phần này.

## Một lệnh tạo cấu trúc và một lệnh đọc dữ liệu

Ví dụ nhắc lại sau dùng dữ liệu PE, không phải dữ liệu mẫu của sách:

```sql
CREATE TABLE ad_department (
    code VARCHAR(12) PRIMARY KEY,
    budget DECIMAL(12,2) NOT NULL CHECK (budget >= 0)
);
INSERT INTO ad_department VALUES ('ART', 20), ('SCI', 40);
SELECT code FROM ad_department WHERE budget >= 30;
```

DDL đầu tiên tạo định nghĩa bảng/kiểu/khóa/ràng buộc trong catalog. INSERT thay instance bằng hai hàng. SELECT trả một bảng kết quả một cột, một hàng SCI; nó không chỉ định phải dùng index hay quét. Không có ORDER BY thì không gán ý nghĩa cho thứ tự ngẫu nhiên của các hàng kết quả. Đổi điều kiện thành `budget >= 0` trả hai hàng, vẫn không tự hứa ART đứng trước SCI.

DML gồm đọc, thêm, xóa và sửa; query language là phần yêu cầu đọc của DML. Procedural DML mô tả cả dữ liệu cần và trình tự lấy dữ liệu; declarative DML mô tả kết quả cần, để hệ chọn cách thực hiện. SQL có nhiều phần mở rộng, nhưng một câu SELECT khai báo kết quả không đồng nghĩa một chương trình giao diện hoàn chỉnh. Host language xử lý form, mạng và luồng ứng dụng rồi dùng API gửi SQL, nhận kết quả. ODBC là họ API dùng với nhiều ngôn ngữ, JDBC dành cho Java; AD11 làm rõ parameter và transaction boundary.

Domain/type, primary key và foreign key là các ràng buộc có cơ chế riêng. Quyền SELECT/INSERT/UPDATE/DELETE cũng phải được cấp đúng đối tượng. Một predicate nghiệp vụ bất kỳ chưa chắc biểu diễn được bằng CHECK đơn giản hoặc kiểm được với chi phí nhỏ; phần thiếu phải được thiết kế và kiểm ở đúng lớp. Catalog lưu metadata để engine phân giải và kiểm lệnh; không sửa trực tiếp các bản ghi catalog để giả lập một DDL.

Ví dụ 2: thêm email index không được làm query mất duplicates hoặc âm thầm đổi DECIMAL thành float. Nó có thể đổi I/O, chi phí ghi và lock pattern. Vì vậy kiểm result đúng và hồ sơ thực thi là hai loại bằng chứng riêng.

## Từ yêu cầu tới thiết kế và vai trò

Application cần entities, relationships, operations, constraints và failure model trước physical schema. DBA quản lý schema, quyền, storage, tuning và recovery; developer xác định transaction boundary và dùng API đúng; end user/analyst quyết định dựa trên result. Một người có thể giữ nhiều vai trò nhưng các trách nhiệm vẫn còn.

Kiến trúc DBMS có query processor, storage manager, transaction/recovery, catalog/authorization và client/service layers. Không phải hệ nào cũng tách process đúng như sơ đồ sách. Catalog phục vụ engine; sửa row catalog trực tiếp không tương đương gọi DDL thêm index theo protocol.

Storage manager phối hợp file manager cấp chỗ và quản lý cấu trúc đĩa, buffer manager đưa page vào RAM và chọn page giữ lại, authorization/integrity manager kiểm quyền/ràng buộc, cùng transaction manager. Data files chứa dữ liệu, dictionary chứa metadata, index hỗ trợ tìm theo khóa; statistics giúp ước lượng chi phí. Có đủ tên file không có nghĩa toàn bộ database vừa trong RAM: buffer manager chỉ giữ một phần cần dùng.

Ở phía query, DDL interpreter ghi nhận định nghĩa; DML compiler phân tích/dịch truy vấn và cân nhắc các plan; query evaluation engine thực hiện plan được chọn. Ví dụ SELECT ở trên có thể qua scan hoặc index khi có một index thích hợp. Hai plan cần trả cùng kết quả theo cùng hợp đồng. Chọn chi phí thấp nhất là trong không gian và ước lượng mà optimizer xét, không phải chứng minh luôn nhanh nhất trên mọi workload.

Transaction manager gồm phần điều khiển đồng thời và phục hồi. Atomicity yêu cầu toàn bộ hoặc không có tác động; consistency yêu cầu transaction được viết đúng để đưa trạng thái hợp lệ sang trạng thái hợp lệ; durability giữ kết quả đã cam kết theo failure model. DBMS không tự biến hai transaction riêng “trừ A” và “cộng B” thành một lần chuyển tiền atomic. Người viết ứng dụng phải chọn đúng ranh giới; trạng thái giữa hai statement có thể tạm không thỏa invariant tổng tiền nên không được công bố như một lần chuyển đã xong.

Thiết kế đi từ yêu cầu dữ liệu và tác vụ, tới conceptual schema, mapping logic theo hệ đích rồi mới chọn tổ chức file/index vật lý. ER và normalization hỗ trợ hai cách lập luận khác nhau về schema. Từ “lưu mọi thứ” chưa cho biết thuộc tính nào cần thu thập: cần trao đổi với người dùng và chuyên gia nghiệp vụ trước.

## Hai tầng và ba tầng khác nhau ở đâu?

Trong mô hình hai tầng, chương trình trên client gọi database server trực tiếp. Trong mô hình ba tầng, client gửi yêu cầu tới application server; server áp dụng nghiệp vụ rồi truy cập database. Ba tầng mô tả vai trò logic, không bắt buộc đúng ba máy vật lý. Một DB server tập trung vẫn có thể dùng nhiều CPU cùng shared memory; cluster có nhiều máy, còn distributed database có thể phân bố dữ liệu/xử lý qua nhiều địa điểm.

Ví dụ sinh viên đăng ký môn: browser gửi mã lớp tới application server; server xác thực người dùng, kiểm quyền và phối hợp transaction kiểm chỗ/thêm đăng ký; database trả kết quả; server trả thông báo cho browser. Gửi thêm trường `is_admin=true` từ client không được biến thành quyền quản trị ở server. Chỉ có application server cũng chưa tự bảo đảm an toàn hay hiệu năng: còn cần kiểm quyền ở server, query đúng, connection/quota và transaction đúng. AD11, AD12 và AD59 xử lý các trường hợp ấy.

Người dùng form dùng chức năng được chuẩn bị; analyst viết query hoặc dùng công cụ phân tích; application programmer viết luồng ứng dụng; DBA giữ quyền kiểm soát dữ liệu/vận hành. DBA còn chọn và đổi schema/cấu trúc lưu/index, cấp quyền, sao lưu ngoài miền lỗi, theo dõi dung lượng trống và các job tốn tài nguyên. Phân loại này nói về cách tương tác và trách nhiệm, không đánh giá năng lực con người.

## Tiến hóa gắn với workload

Các hệ đầu dùng file, tape và batch processing phù hợp phần cứng/ứng dụng thời đó. Direct-access storage và hierarchical/network models hỗ trợ truy xuất record theo cấu trúc định trước. Relational model cùng declarative query tách mô tả dữ liệu khỏi một đường truy xuất cố định, tạo cơ sở cho SQL và optimizer.

Transaction processing và concurrency/recovery phát triển với ứng dụng nhiều người dùng. Relational engines phục vụ OLTP; data warehousing/OLAP và parallel processing phục vụ phân tích lớn. Object orientation, complex types, text/spatial và web applications mở rộng dữ liệu/API, đồng thời còn cần constraints theo contract.

Internet và dịch vụ quy mô lớn thúc đẩy distributed storage, key-value/document systems, replication và partitioning. Tên NoSQL không tự xác định transaction guarantees; NewSQL và các tên khác cũng cần cam kết cụ thể. Cloud, tách compute/storage, in-memory, NVM/SSD và streaming đổi chi phí/failure nhưng vẫn cần isolation, durability và identity.

Kiến trúc mới không tự thay mọi kiến trúc cũ. Query phân tích và point transaction có thể cần layout/index/concurrency khác nhau. Polyglot storage còn phải giữ schema, identity và consistency qua các biên; thêm store có thể thêm công việc phối hợp.

Các mốc sau tóm lược lịch sử được trình bày trong sách xuất bản năm2019, không là bảng xếp hạng sản phẩm hiện nay:

| Giai đoạn | Thay đổi đáng chú ý | Vì sao nó ảnh hưởng thiết kế? |
|---|---|---|
| Trước và trong thập niên1950–đầu1960 | Thẻ đục lỗ, xử lý cơ học, rồi băng từ/batch | Truy cập tuần tự khiến input thường phải sắp cùng khóa để merge sang băng mới |
| Cuối1960–đầu1970 | Đĩa cho truy cập trực tiếp; mô hình hierarchical/network; Codd giới thiệu relational model năm1970 | Có thể tách yêu cầu logic khỏi một đường đi record cố định |
| Cuối1970–1980 | System R ở IBM, Ingres ở Berkeley và các hệ relational thương mại | Compiler/optimizer làm truy vấn khai báo khả thi về hiệu năng; nghiên cứu parallel/distributed và object database phát triển |
| Thập niên1990 | Decision support/parallel database, object-relational và Web mở rộng | Hệ phải phục vụ cả phân tích và lượng giao dịch lớn, với nhu cầu sẵn sàng cao |
| Thập niên2000 | XML/JSON, spatial/graph, hệ mã nguồn mở, tự điều chỉnh, column-store, MapReduce và NoSQL | Kiểu dữ liệu và workload đa dạng dẫn tới cách bố trí, API và consistency khác nhau |
| Thập niên2010 | Nhiều hệ mở rộng lại abstraction/consistency; cloud và SaaS | Chuyển vận hành cho nhà cung cấp còn kéo theo câu hỏi về quyền dữ liệu, trách nhiệm và bảo mật |

SaaS giao cả vận hành ứng dụng lẫn dữ liệu cho bên cung cấp, khác việc chỉ thuê nơi lưu. Lựa chọn triển khai cần xác định ai quản trị, ai có quyền truy cập, cách lấy lại dữ liệu và cách đáp ứng sự cố. Đoạn lịch sử đặt ra vấn đề privacy/security; nó không thay cho tư vấn luật hoặc khẳng định một quy định hiện hành cụ thể.

## Hợp đồng có thể kiểm được

Ví dụ 3 là đặt vé: mỗi vé chỉ bán một lần; retry một request không tạo hai đơn; response thành công gắn mức bền đã định; người dùng không thấy vé của người khác; failure có outcome và cleanup rõ. Mỗi yêu cầu có test/rubric riêng; SELECT COUNT riêng không chứng minh tất cả.

Tài liệu “web ready” cần phân biệt spec với runner triển khai. Model minh họa cho phép học thuật toán; backend engine cho bằng chứng thực thi; proof cho tính chất trong assumptions. Đặt các nhãn cạnh hoạt động giúp người học biết mình đang kiểm điều gì.

## Luyện tập

1. Nêu hai yêu cầu cụ thể khi chuyển CSV sang DBMS. Với mỗi yêu cầu, cho failure case và bằng chứng đạt.
2. Thêm index được nói là không đổi logical schema. Viết hai kiểm semantics và hai khía cạnh chi phí có thể đổi, cùng phép đo.
3. So OLTP và OLAP quét lớn: ít nhất ba khác biệt workload và một bảo đảm toàn vẹn cả hai cần.
4. Chọn kiến trúc lịch sử/hiện đại trong sách và lập bảng contract gồm query model, transaction/failure, scaling, giới hạn. Dùng một yêu cầu ngược để bác tuyên bố “luôn nhanh hơn”.
5. Với đoạn CREATE/INSERT/SELECT trên, lần lượt xác định thứ gì đổi: schema, instance hay chỉ có result. Nếu yêu cầu thêm “mỗi khoa phải có người phụ trách hợp lệ”, cần biết thêm thông tin nào trước khi chọn constraint?
6. Vẽ đường đi của yêu cầu đăng ký trong kiến trúc ba tầng, ghi trách nhiệm ở mỗi nút. Sau đó nêu một tác vụ DBA mà việc thêm application server chưa tự giải quyết.

## Gợi ý

Mức 1: bảo đảm cần có hành vi quan sát được. Data independence không hứa thời gian chạy giữ nguyên.

Mức 2: duplicate, NULL, rounding và ordering giúp bắt semantics đổi âm thầm. Chi phí ghi/disk/lock có thể đổi khi thêm index.

## Đáp án và lập luận

1. Ví dụ atomic transfer kiểm bằng crash giữa hai update; concurrency bằng race bán vé; security bằng request của role thiếu quyền. Kết quả cần invariant/response/failure model rõ.
2. So exact bag và typed values; chỉ so sequence khi ORDER BY yêu cầu. So error/constraint behavior nếu thuộc contract. Write cost, index size, plan/latency và lock behavior có thể đổi; đo trên workload/version rõ.
3. OLTP thường point operations, transaction ngắn và concurrency cao; OLAP thường scan/join/aggregate với memory/I/O lớn. Cả hai cần semantics đúng theo dữ liệu, quyền và freshness đã hứa. Tên workload không loại nhu cầu recovery.
4. Rubric có nguồn/thời kỳ, bối cảnh phần cứng/ứng dụng, contract và counterexample hợp lệ. KV point lookup có thể phù hợp nhưng ad-hoc joins nhiều chủ thể có thể cần thêm index, client work và coordination.
5. CREATE đổi schema/catalog; INSERT đổi instance; SELECT chỉ trả result theo snapshot/quyền, không tự sửa bảng. Cần xác định người phụ trách là entity nào, khóa và tính tồn tại, có cho NULL không, quan hệ một hay nhiều, và điều gì xảy ra khi xóa người ấy. Sau đó mới chọn FK/NOT NULL hoặc cơ chế khác theo đúng nghiệp vụ.
6. Browser nhận/gửi dữ liệu; application server xác thực, kiểm quyền/nghiệp vụ và giữ đúng transaction boundary; DBMS phân giải query, thực thi quyền/ràng buộc/concurrency/recovery rồi trả result. Sao lưu, thử phục hồi, theo dõi dung lượng và job nặng vẫn cần người/quy trình chịu trách nhiệm. Không chấp nhận hình browser gửi thẳng quyền quản trị database khi brief là ba tầng.
