# AD14 · Object-relational và object persistence

Đã học: A02, O04, AD13. Nguồn: DSC 7e §8.2 và online chapter29. Môi trường: object/reference canvas trên web; SQL relational chạy MySQL, cú pháp type/array của hệ khác được ghi riêng. Không coi một class trong ứng dụng là object persistent tự động.

## Hai object bằng giá trị vẫn có thể là hai thực thể

Kho có hai thiết bị cùng model và ngày sản xuất. Nếu dùng toàn bộ thuộc tính làm identity, chúng bị gộp; nếu mỗi object có identifier, hai thiết bị vẫn tách dù values giống nhau. Object identity cần tồn tại qua sửa thuộc tính và qua lần nạp mới. Một địa chỉ RAM chỉ có ý nghĩa trong process đang chạy; nó không tự là persistent identifier.

Với object graph, một thiết bị có thể được hai hợp đồng cùng tham chiếu. Khi nạp, phải quyết định hai reference đó trỏ cùng một instance hay hai bản sao cùng ID. Aliasing ảnh hưởng thay đổi trong bộ nhớ; database transaction còn quyết định thay đổi nào được lưu, khi nào có conflict và người khác nhìn thấy gì. Đây là chỗ object persistence gặp concurrency, không chỉ serialization một cây.

## Ví dụ 1: reference khác copy

Objects gồm Asset a17=(serial=S17,model=M), Contract c1.assets=[ref a17], c2.assets=[ref a17]. Sửa a17.model=M2 phải được cả hai đường tham chiếu nhìn là cùng asset sau lần đọc nhất quán phù hợp. Nếu lưu hai bản nested copy không giữ identity, c1 có thể nói M2 còn c2 nói M; đó có thể là snapshot có chủ ý hoặc lỗi đồng bộ tùy contract.

Mapping relational nhỏ:

```sql
CREATE TEMPORARY TABLE asset(
 asset_id INT PRIMARY KEY,serial VARCHAR(20) UNIQUE,model VARCHAR(20)
);
CREATE TEMPORARY TABLE contract_asset(
 contract_id INT,asset_id INT,PRIMARY KEY(contract_id,asset_id)
);
INSERT INTO asset VALUES(17,'S17','M');
INSERT INTO contract_asset VALUES(1,17),(2,17);
UPDATE asset SET model='M2' WHERE asset_id=17;
SELECT c.contract_id,a.model
FROM contract_asset c JOIN asset a USING(asset_id)
ORDER BY c.contract_id;
```

Kết quả (1,M2),(2,M2). FK có thể thêm trên bảng persistent để bảo vệ reference; bảng TEMP ở ví dụ chỉ minh họa một session, không tuyên bố nó có mọi ràng buộc production. Object REF của chuẩn object-relational và một cột khóa ngoại là hai cơ chế biểu diễn; không gán cú pháp `REF(Type)` cho MySQL nếu không hỗ trợ.

## Ba cách nối object với database

Object-relational DBMS mở rộng type system bên trong DB bằng structured types, references và collections, trong khi giữ truy vấn declarative để optimizer chọn cách tìm dữ liệu. ORM đặt mapping giữa class của chương trình và tables; đối tượng Python/Java không vì thế trở thành một type do DBMS định nghĩa. Native object DB tích hợp persistence với type system của ngôn ngữ để truy cập object trực tiếp. Đây là ba hướng giải quyết khác nhau cho chênh lệch giữa types của chương trình và dữ liệu quan hệ, không phải ba tên của cùng một thư viện.

Ví dụ cần tìm mọi Asset model=M: object-relational SQL hoặc một ORM query có thể biểu diễn một điều kiện để engine dùng index; vòng lặp imperative tự đi mọi pointer rồi kiểm model buộc ứng dụng chọn trước đường duyệt và có thể đọc cả graph. Native integration làm code truy cập thuận tiện, nhưng thiết kế pointer/lifetime sai có thể gây reference lỗi; chương nguồn dùng khả năng tối ưu declarative và rủi ro pointer để giải thích khó khăn lịch sử của hướng object DB. Điều này không chứng minh mọi object DB hiện đại thiếu query language hoặc mọi ORM query đều có plan tốt.

## Object phức hợp và thiết kế quan hệ

Atomicity phụ thuộc các thao tác cần hỗ trợ. Address dưới dạng string là một value nếu hệ chỉ lưu/in nguyên địa chỉ; nếu query cần city, việc giấu city trong chuỗi buộc parse hoặc đoán. Structured Address(street,city,postal) cho phép lấy cả value Address hoặc chỉ city. Composite, multivalued, specialization/generalization của E-R có thể được biểu diễn trực tiếp bằng complex types; thuận tiện ấy vẫn cần cân bằng constraints và workload.

Fixture book7 có title=Data Paths, authors=[An,Binh], publisher=(PE Press,Ha Noi), keywords multiset={SQL,SQL,Index}. Dùng book_id ổn định, không giả title là unique trong ứng dụng thật. Có thể map về `Book(book_id,title,pub_name,pub_branch)`, `Author(book_id,pos,name)` và `Keyword(book_id,occurrence_id,word)`. Tách các collections độc lập tránh tích authors×keywords và giữ parent khi collection rỗng; nếu keywords là set thì khóa `(book_id,word)` đã đủ, còn bag cần occurrence_id. Query một book đầy đủ phải ghép/aggregate các nhánh; một nested book diễn đạt gần object mà người dùng nghĩ tới hơn nhưng không tự thắng mọi query.

Với quan hệ takes nhiều-nhiều, lưu sections trong mỗi student và đồng thời students trong mỗi section nhân đôi cùng fact. Thêm/xóa enrollment ở một phía rồi quên phía kia làm hai câu hỏi trả lời khác nhau. Một quan hệ `Enrollment(student_id,section_id)` với khóa cặp biểu diễn fact một lần; các collections cho UI có thể được dựng từ quan hệ đó. Chỉ giữ hai bản khi đã có policy đồng bộ/transaction và lý do workload rõ.

## Structured types, inheritance và phương thức

Một structured type Address gồm street,city,postal; Student là subtype của Person với student_no. Type inheritance nói về tập thuộc tính/phương thức và substitutability; table inheritance nói về tổ chức các hàng của tables. Một hệ có loại này chưa chắc có loại kia. Dynamic dispatch chọn method theo runtime type cần một contract để phương thức subtype vẫn dùng được ở chỗ chờ supertype; chỉ thêm trường không chứng minh mọi thay thế đều an toàn.

Khi map inheritance sang quan hệ, có ba thiết kế thường gặp. Một bảng Person có discriminator và cột subtype cho join ít nhưng nhiều NULL/constraints theo type. Một bảng mỗi class với PK subtype cũng là FK tới Person giữ phần chung tách nhưng query subtype phải join. Một bảng mỗi concrete class giảm join đọc concrete nhưng dữ liệu chung/UNIQUE across types khó bảo đảm hơn. Không có một mapping thắng mọi workload; cần đọc/write patterns và constraints.

Ví dụ Student(1,An,S01) và Staff(2,Binh,E02). Với class-table mapping, Person có hai hàng; Student có hàng id1; Staff có hàng id2. Query mọi Person không cần UNION; query Student JOIN Person trả đủ dữ liệu. Nếu một Person được phép vừa Student vừa Staff, không được ép discriminator chỉ nhận một role trừ khi đó là business rule thật. Inheritance mô hình hóa “is-a”; membership role nhiều-nhiều đôi khi phù hợp hơn hierarchy.

### Khai báo type, constructor và self

Đoạn sau là minh họa type/table theo mô hình SQL của online §29.2, không phải script chạy MySQL; dialect hỗ trợ structured types có thể cần cú pháp khác. NameT là named type dùng lại được; inline ROW có cùng fields nhưng là unnamed row type, không tự mang toàn bộ identity/method/constructor của NameT.

```text
CREATE TYPE NameT AS (first_name VARCHAR(20), last_name VARCHAR(20)) FINAL;
CREATE TYPE AddressT AS (street VARCHAR(40), city VARCHAR(20), postal VARCHAR(10)) NOT FINAL;
CREATE TYPE PersonT AS
 (id INTEGER, person_name NameT, address AddressT, born DATE) NOT FINAL;
CREATE TABLE PeopleTyped OF PersonT;
-- Một lựa chọn khác cho một column:
person_name ROW(first_name VARCHAR(20), last_name VARCHAR(20))
```

FINAL cấm tạo subtype; NOT FINAL cho phép kế thừa. `p.person_name.last_name` lấy một scalar, còn `p.person_name` trả cả structured value. Một table có column kiểu NameT khác một typed table có toàn bộ row type PersonT. Collection có thể chứa scalar, structured values hoặc rows: interests của một user có thể là collection các rows `(topic,degree)`. Đây là khả năng type system, không có nghĩa mọi DBMS nhận cùng câu khai báo table-valued type ở mọi vị trí.

Constructor tạo một value, chưa tự insert một row persistent. Theo mô hình nguồn, constructor không tham số đặt fields về defaults; constructor nhận first/last phải khai báo riêng và gán `self.first_name=first`, `self.last_name=last`. `new NameT('An','Nguyen')` sau đó tạo NameT(An,Nguyen); overloads cùng tên phải phân biệt được bằng số/kiểu arguments. Một row value inline có thể viết `(An,Nguyen)` theo thứ tự fields, không cần constructor có tên. Khi insert PersonT, cần cung cấp NameT, AddressT và date đúng types thay vì gộp tất cả thành text.

Methods được khai báo trong structured type; body được định nghĩa cho type đó và dùng self để chỉ instance đang gọi. Ví dụ method `renameLast(x)` gán `self.person_name.last_name=x`; gọi trên object P1 đổi chính field của P1, nhưng việc thay đổi đó được commit hay rollback vẫn thuộc transaction/persistence contract. Một method đọc `ageOnDate(d)` dùng self.born và d để trả tuổi theo quy tắc đã chọn; tuổi tròn phải so birthday, không chỉ trừ hai số năm. Với born=2000-11-06 và d=2026-11-05, tuổi tròn là25. Đây là quy tắc PE minh họa self/arguments, không coi một phép date subtraction của mọi engine trả tuổi tròn.

### Kế thừa không đồng nghĩa nhiều roles

StudentT UNDER PersonT thêm degree; TeacherT UNDER PersonT thêm salary. Cả hai thừa hưởng name/address/methods. Method `label()` của PersonT trả name, override ở StudentT trả name cùng degree: một StudentT của An,MSc cho label=An(MSc) dù caller giữ reference ở type PersonT trong model dispatch này. Nếu PersonT FINAL, khai báo StudentT phải bị từ chối; thêm fields không được bỏ qua điều kiện này.

Online §29.3.1 mô tả mỗi value có đúng một most-specific type: StudentT cũng là PersonT qua kế thừa, nhưng StudentT không tự đồng thời là TeacherT. Ví dụ multiple inheritance TeachingAssistant UNDER Student,Teacher trong nguồn là mô hình khái niệm, không phải tính năng SQL mà bài này giả sẵn. name/address có chung nguồn Person nên khác với hai fields department được định nghĩa độc lập: student_dept=CS và teacher_dept=Math cần hai tên/ý nghĩa riêng. Gộp hai department thành một sẽ làm mất thông tin. Với người có hai roles, mapping Person + StudentRole + TeacherRole cho phép cùng person_id ở cả hai bảng mà không phụ thuộc multiple inheritance của DBMS.

## Typed tables, subtable và dereference là cơ chế riêng

Ở mô hình object-relational của §8.2.1, một structured type Person có fields id,name,address và có thể dùng làm row type của typed table People. Address lại là structured value street/city; field interests có thể là collection các rows (topic,degree). Đó là định nghĩa type trong DBMS, khác việc Python có một class Person rồi ORM tạo các cột. Một value Address được copy theo giá trị khác REF tới một Person có identity. Methods có thể được khai báo trên type ở hệ hỗ trợ; method override dùng runtime subtype, còn query declarative vẫn để engine lựa chọn plan.

Table inheritance có thêm quy tắc về phạm vi query. Trong mô hình sách, People có direct row P1=(1,An), subtable Students có S2=(2,Binh,degree=MSc), subtable Staff có T3=(3,Chi,salary=100). Query People thấy cả ba rows nhưng chỉ các fields của Person. Query ONLY People chỉ thấy P1; query Students thấy S2 với field degree. Đây không phải class-table mapping ở ví dụ trước, nơi Person giữ hàng vật lý chung rồi JOIN các bảng con. Nếu một engine chỉ hỗ trợ type inheritance, không thể tự suy query table cha bao gồm các rows của bảng con. Dialect/cross-table uniqueness cần kiểm riêng, không dùng mẫu này như SQL MySQL đã chạy.

REF có target type và có thể bị ràng buộc scope. Mô hình Department(name,head REF Person SCOPE People) với CS.head=ref(P1) cho `head->name` hoặc `deref(head).name` bằng An. Dereference che một bước tìm object; relational mapping tương ứng dùng Department JOIN People theo head_id, chưa làm chi phí truy cập biến mất. Nếu head=NULL thì cần quy tắc giữ department bằng outer join thay vì inner join. Nếu reference trỏ object ngoài scope hoặc đã bị xóa, policy referential integrity/dangling reference của engine phải rõ. System-generated OID có thể được lấy qua ref(row); chọn business id làm reference lại cần quy tắc id ổn định. Hai hệ có syntax REF gần nhau vẫn có thể khác cách kiểm scope và lifetime.

ORM còn cần phân biệt thay một object với bulk update trực tiếp. Ví dụ identity map đang giữ Asset17 model=M nhưng một SQL bulk update bên ngoài scope đổi model=M2. Object cached không tự đổi; refresh/expire hoặc kết thúc unit of work theo policy trước khi đọc lại. ORM query language có thể được dịch sang SQL và giảm khác biệt dialect, nhưng custom SQL/types/isolation vẫn cần kiểm khi đổi DBMS. Update một triệu rows qua từng object còn có thể tốn nhiều queries và dirty-tracking overhead; chọn bulk SQL khi thích hợp phải xử lý cache/transaction consistency, không chỉ giảm số dòng code.

Về update/delete, phạm vi table cha cũng là một phần ngữ nghĩa. Với fixture P1/S2/T3 ở trên, thao tác mô hình `DELETE FROM ONLY People WHERE id=2` không xóa S2 vì row ấy được insert ở Students; `DELETE FROM People WHERE id=2` xóa S2, nên cả query Students lẫn People đều mất id2. UPDATE dùng ONLY có giới hạn tương tự. Mỗi thí nghiệm bắt đầu từ cùng fixture, không chạy nối tiếp rồi so output trên dữ liệu đã bị đổi.

Online §29.3.2 còn nêu consistency cho typed subtables trong mô hình chuẩn của nguồn: mỗi row cha tương ứng tối đa một row trong mỗi immediate subtable, và mọi representations tương ứng phải bắt nguồn từ một row được insert. Vì vậy không được tự insert cùng một person vào Students và Teachers rồi cho rằng đã có overlapping specialization hợp lệ. Giữ Person chung và hai role tables có PK/FK là cách relational biểu diễn overlap; đó là mapping riêng, không phải typed-subtable semantics. Privilege UNDER kiểm soát ai được tạo subtype/subtable dưới một type/table có sẵn, tương tự ý nghĩa kiểm soát phụ thuộc của REFERENCES. Quyền truy vấn bảng cha chưa tự cấp quyền tạo descendants.

Khởi tạo REF cũng cần một thao tác tìm đúng identity. Nếu engine dùng business key làm REF thì key phải ổn định theo contract. Nếu engine cấp OID, model có thể insert Department(CS,NULL), tìm duy nhất Person có id1, lấy `REF(p)` rồi update CS.head thành reference đó. Tìm theo name không unique có thể trả nhiều rows nên không được chọn tùy ý. Sau đó `head->name` hoặc `DEREF(head).name` đọc An; relational implementation dùng LEFT JOIN theo head_id như bài tập5. Khi tạo reference và target có writer khác, transaction/constraint phải bảo vệ target lifetime.

## Ví dụ 2: array và multiset cần giữ loại collection

Một tác giả có bút danh theo thứ tự ưu tiên [An,Anh,An]. Array giữ vị trí và có thể có giá trị lặp; multiset giữ số lần nhưng không thứ tự; set chỉ giữ một occurrence mỗi giá trị. Khi unnest array, dùng (author_id,pos,alias). Nếu bỏ pos rồi DISTINCT, không thể phục hồi array ban đầu.

Pseudocode:

```text
unnest(author_id, aliases):
    for pos from1 to length(aliases):
        emit(author_id,pos,aliases[pos])
nest(rows):
    group by author_id
    validate each pos appears once and positions are contiguous
    output values ordered by pos
```

Với rows (7,1,An),(7,2,Anh),(7,3,An), nest trả đúng [An,Anh,An]. Bất biến unnest sau k bước có đúng k occurrences đầu với index riêng. Nest là phép đảo trên miền rows có một occurrence cho mỗi pos và không mất order; nếu thiếu pos2 hoặc có hai rows cùng pos, cần reject hoặc quy tắc conflict, không lặng lẽ chọn một. Duyệt L phần tử tốn O(L); nếu rows chưa có thứ tự, sorting thêm O(L log L). SQL collection syntax trong sách là mô hình chuẩn/hệ hỗ trợ; MySQL có thể map thành bảng con hoặc JSON, không phải có ARRAY type tương đương đầy đủ.

Một query membership “có ít nhất một alias An” là existential, không nhân hàng tác giả theo số alias trùng. Một query liệt kê mọi occurrence phải giữ số lần. NEST/UNNEST không phải lúc nào cũng lossless nếu phép chọn/chiếu giữa chúng làm mất key/position; dùng invariant như thiết kế quan hệ thay vì tin vào tên operator.

Online §29.4.3 còn có hai collections độc lập trong cùng object. Ví dụ book7 có authors `[An,Binh]` và keywords multiset `{SQL,SQL,Index}`. Unnest đồng thời tạo2×3=6 occurrences; nếu sau đó `collect(keyword)` trực tiếp theo book thì mỗi keyword bị lặp theo số authors, còn collect(author) lặp theo số keywords. DISTINCT không phục hồi multiset `{SQL,SQL,Index}` vì làm mất lần SQL thứ hai. Muốn round trip, giữ key book cùng ordinal riêng cho author và occurrence-id riêng cho keyword, dựng từng collection từ projection có đúng occurrence key của nhánh ấy, rồi ghép về parent. Với book8 có authors rỗng, inner unnest cả hai nhánh tạo0 dòng nên mất cả book; cần giữ quan hệ parent và biểu diễn collection rỗng riêng. Đây là giới hạn cụ thể của việc flatten nhiều chiều, không chỉ là mất thứ tự trong một array.

### Tạo, truy vấn và dựng lại collections

Trong model SQL collection của §29.4, authors có thể khai báo `VARCHAR(20) ARRAY[10]`, giới hạn10 phần tử; keywords là `VARCHAR(20) MULTISET`. `ARRAY['An','Binh']` và `MULTISET['SQL','SQL','Index']` tạo hai loại values khác nhau. `authors[1]` đọc An; gán authors[1]=Chi đổi riêng phần tử đầu thành `[Chi,Binh]`. Literal Publisher được tạo bằng constructor đã định nghĩa, rồi dùng trong Book cùng title, authors, publication date và keywords. Một collection constructor không tự sinh tất cả constructors cho structured fields. Cú pháp này là mô hình của nguồn, không được gửi nguyên sang MySQL.

Một value Book đủ fields trong fixture là `(title='Data Paths', authors=ARRAY['An','Binh'], pub_date=DATE '2026-01-02', publisher=new Publisher('PE Press','Ha Noi'), keywords=MULTISET['SQL','SQL','Index'])`; book_id=7 là identity do ứng dụng dùng khi lưu. Constructor Publisher hai arguments phải có trước; cú pháp named fields ở đây chỉ mô tả value để kiểm types, không là một INSERT đã chạy.

Query “book có keyword SQL” dùng membership `SQL IN UNNEST(keywords)` theo model, trả book7 một lần dù bag có SQL hai occurrences. Query liệt kê `(book_id,author)` dùng UNNEST trong FROM, vì collection đã trở thành một relation để join; với book7 cho An và Binh. `UNNEST(b.authors) WITH ORDINALITY` thêm positions1/2, và b phải có sẵn trong scope để chọn đúng collection của từng book. Query `authors[1],authors[2],authors[3]` chỉ thích hợp khi có contract cardinality/range rõ; không giả mọi book có ba tác giả.

Nesting có hai cách cần phân biệt. COLLECT gom các values thành multiset của từng GROUP BY; trên flat book7 sáu rows, group theo `(book_id,author,publisher)` cho mỗi author bag `{SQL,SQL,Index}`. Nếu group chỉ theo book_id/publisher rồi collect cả hai nhánh, author bị lặp ba lần mỗi người và keyword bị lặp hai lần. Source query minh họa grouping/collect không bảo đảm khôi phục hai collections gốc sau Cartesian expansion; phải kiểm multiplicity và order bằng witness cụ thể.

Một cách dựng lại an toàn từ ba relations Book/Author/Keyword ở trên là mô hình correlated construction sau:

```text
for each b in Book:
    author_array := ARRAY(SELECT name FROM Author a
                          WHERE a.book_id=b.book_id ORDER BY pos)
    keyword_bag := MULTISET(SELECT word FROM Keyword k
                           WHERE k.book_id=b.book_id)
    emit(b.book_id,b.title,author_array,
         Publisher(b.pub_name,b.pub_branch),keyword_bag)
```

Với book7, kết quả là `[An,Binh]` và `{SQL,SQL,Index}`; book8 không có Author/Keyword vẫn tồn tại với hai collections rỗng. Bỏ predicate a.book_id=b.book_id sẽ đưa tác giả của mọi book vào mỗi object. ORDER BY pos là phần của construction array; bag không đòi thứ tự. Correctness: mỗi parent phát đúng một object; các predicates chọn đúng occurrences của parent ấy; sorting theo pos khôi phục array; bag construction giữ mỗi Keyword row một occurrence. Nếu group rows theo book_id sẵn, scan tổng A+K occurrences cộng sort tác giả tốn O(A+K+Σ a_b log a_b) ngoài lookup/output; correlated syntax không chứng minh engine bắt buộc chạy một full scan cho mỗi book. Cần plan của implementation mới biết tối ưu thực tế.

Multiset operators có thể kiểm qua số lần m_M(x). `SET(M)` giữ một occurrence khi count>0; intersection dùng min counts; bag union ALL cộng counts; `M SUBMULTISET N` đúng khi mọi count của M≤count của N. Với M={SQL,SQL,Index}, N={SQL,Python}: SET(M)={SQL,Index}, intersection={SQL}, union ALL={SQL,SQL,SQL,Index,Python}, M không là submultiset của N. Source gọi các aggregates trên nhiều bags là intersection và fusion; model fusion ở đây dùng union ALL để giữ multiplicity. Xóa một occurrence SQL là gán toàn bộ value mới `M EXCEPT ALL MULTISET['SQL']`, cho {SQL,Index}; dùng set difference sẽ trả lời một bài khác. Mô hình chuẩn trong nguồn thay một multiset attribute bằng value mới, không giả có lệnh mutation theo index như array.

## Ví dụ 3: unit of work và stale object

Hai browser mở Asset17 version5,model=M. A đổi model=M2, B đổi model=M3. Nếu cả hai ghi mù `WHERE asset_id=17`, người ghi sau thắng mà không biết có thay đổi. Có thể dùng optimistic version check:

```sql
UPDATE persistent_asset
SET model=?,version=version+1
WHERE asset_id=? AND version=?;
```

Đây là template ứng dụng; schema persistent_asset cần asset_id PK,model,version NOT NULL. Nếu A cập nhật từ version5 thành6 trước, B gửi version5 không match. Dịch vụ trả conflict, đọc lại và hòa giải theo nghiệp vụ; không giả affected_rows=0 luôn là “không có asset”. Dùng row lock là lựa chọn khác với scope/lifetime phù hợp; giữ lock suốt thời gian người dùng sửa form thường không thích hợp.

Persistence theo reachability lưu các objects reachable từ một persistent root theo cơ chế hệ; nó phải xử lý cycle và shared references, không recurse sao chép không dừng. Algorithm model dùng map OID→đã thăm: khi gặp OID cũ, ghi reference; khi gặp mới, ghi object rồi duyệt references. Bất biến mỗi OID có một bản ghi và mọi edge đã duyệt trỏ tới OID được ghi hoặc đang xử lý. Graph hữu hạn nên dừng; O(V+E) ngoài serialization/IO. Nếu truy cập object đang thay đổi trong lúc traversal, snapshot/transaction cần được định nghĩa, nếu không file có thể không tương ứng thời điểm nào.

ORM thường có identity map trong một unit of work, lazy/eager loading và dirty tracking. Identity map tránh tạo nhiều instance cùng key trong scope đó; nó không bảo đảm toàn hệ chỉ có một instance. Lazy loading giúp không lấy graph thừa nhưng có thể tạo N+1 query; eager join có thể nhân rows và đòi ORM ghép đúng identity. Đếm SQL và đo đúng workload trước khi chọn, không đánh giá từ số dòng code ngắn.

### Trace vòng đời ORM

Mapping `Asset{id,serial,model}`→asset và `Contract.assets`→contract_asset tạo SQL từ thay đổi object. Trong một unit of work mới, tạo Asset18(S18,M), gắn vào Contract3 rồi save/commit: cần INSERT asset18 trước link (3,18) khi FK yêu cầu target tồn tại. Query object theo `serial=S18` được dịch thành điều kiện SQL rồi materialize Asset18; một lần lookup khác cùng key trong identity map trả cùng instance theo contract của scope. Đổi model=M2 rồi save sinh UPDATE tương ứng; rollback phải không được quảng bá là đã lưu M2. Muốn delete Asset18 có link còn tồn tại, cần policy: reject, hoặc xóa link trước rồi xóa asset trong transaction, hoặc cascade đã khai báo. “Xóa object khỏi một list UI” chưa tự xác định DELETE target hay chỉ DELETE association.

Trace này tách create/materialize/update/delete và trạng thái commit; ORM giúp giữ lập trình ở object model và có thể tiết kiệm đọc nhờ cache. Cache stale, bulk updates và complex imperative queries vẫn cần đo và đôi khi dùng SQL trực tiếp như ví dụ trước. Khả năng đổi DBMS với cùng object query chỉ có phạm vi mapping/types/operations mà ORM hỗ trợ; migration không tự bảo toàn custom SQL hay isolation semantics.

11. SET(M)={A,B}; intersection={A}; union ALL={A,A,A,B,C}; cả M⊑N lẫn N⊑M đều false (A count2>1; C không có trong M). `M EXCEPT ALL MULTISET[A]` trả {A,B}. Xóa mọi A cần trừ đủ m_M(A) occurrences hoặc lọc mọi value≠A rồi dựng bag lại; không được giảm một count rồi tuyên bố A đã biến mất. Chấm counts từng value, không so order của bag.
