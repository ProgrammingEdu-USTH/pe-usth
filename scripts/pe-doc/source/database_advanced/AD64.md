# AD64 · Distributed files, indexing và key-value stores

Đã học: AD47, AD31. Nguồn: DSC7e §21.5–21.7. Môi trường: model routing/storage và bài thiết kế API trên web; backend hệ khác chỉ mở theo capability đã kiểm.

Một file lớn chia thành nhiều block trên nhiều máy. Directory biết block ở đâu nhưng không giữ toàn bộ nội dung file. Nếu client cache vị trí cũ rồi ghi sau migration, dữ liệu có thể đi sai owner. Cần tách control metadata khỏi data path và xác định phiên bản của cả hai.

## File, chunk và metadata

Distributed file system có thể chia file thành chunk/block có identity và replicas. Metadata ánh xạ file tới chunks, chunk tới locations và version/lease cần thiết. Client hỏi metadata rồi truyền dữ liệu với data node; caching giảm request metadata nhưng cần refresh/redirect khi owner thay đổi.

Một model read gồm: lấy file version và chunk map; chọn replica phù hợp; đọc bytes và kiểm checksum; retry ở replica khác nếu lỗi; kiểm điều kiện version của query. Checksum giúp phát hiện một số corruption theo assumptions; nó không chứng minh đã đọc snapshot nhất quán của file đang ghi.

Ví dụ 1: file F có chunk C1,C2 ở version 7. Client đọc C1v7; giữa đó chủ file ghi C2v8 rồi client đọc C2 mới. Nếu contract cần file snapshot v7, kết quả ghép không đạt điều kiện. Nếu API chỉ hứa đọc từng chunk theo trạng thái hiện có, không được quảng bá cả file có atomic snapshot.

Write/append cần quy định thứ tự giữa replicas, record boundary và retry. Một số hệ có record append atomic theo đơn vị record nhưng có thể đưa duplicate hoặc padding sau failure/retry; hệ khác có semantics khác. Không gọi mọi append “exactly once” từ tên API. Client có thể cần record ID để deduplicate khi đọc.

Metadata authority cũng cần recovery, replication và quyền điều phối. Data node trả heartbeat không chứng minh mọi chunk đã replicate bền đủ theo ACK contract. Repair replica cần chọn đúng version, không copy bản stale chỉ vì nó đang online.

## Global và local indexes

Local index nằm cùng partition với base data. Query biết đúng partition có thể lookup rẻ, nhưng query thiếu partition key có thể hỏi nhiều node. Global index theo key khác có thể định tuyến tới nơi cần; đổi lại việc update base data và index có thể vượt node/transaction boundary.

Global primary index trong cách gọi của §21.5 là index trên **partitioning attributes**: routing chọn partition, rồi local index trên chính các attributes ấy tìm tuples. Chữ primary ở đây không bắt buộc partition key là primary key duy nhất. Nếu R được chia theo city và mỗi partition có local index city, lookup city=HN route tới partition HN rồi lấy mọi row HN; không cần dựng thêm một relation index toàn cục. Một range query được prune hiệu quả khi base dùng range partition theo city; hash city không giữ thứ tự để tự tìm một dải city. Global secondary index dùng Ki khác Kp cần thiết kế hai lần định tuyến dưới đây.

Ví dụ 2: base users partition theo userID, query theo email. Local email index ở mỗi partition vẫn phải fanout nếu không biết userID. Global index (email→userID/location) giảm fanout, nhưng đổi email hoặc migrate user cần cập nhật mapping nhất quán. Entry index trỏ tới bản base đã xóa có thể là ghost nếu đồng bộ chưa đủ.

### Dựng global secondary index thành một relation riêng

Theo §21.5, gọi Kp là partitioning attributes của base R, Ki là index attributes. Tạo relation I chứa(Ki,Kp,Ku), trong đó Ku bổ sung để Kp∪Ku nhận diện duy nhất base tuple khi Kp có duplicates. Partition I theo Ki và dựng local index Ki tại từng partition I. Base partitions có local index(Kp,Ku). Nếu Kp tự là key thì Ku có thể rỗng.

Query Ki=v làm hai lượt route: tính partition của v trong I, lookup các entries; gom entries theo Kp và gửi tới base owners; dùng(Kp,Ku) lấy đúng rows rồi kiểm contract. Mỗi base tuple có một entry với identity đủ nên lookup không nhân hoặc mất tuple; nhiều base tuples cùng Ki phải giữ mọi entry. Với k hits và p base partitions có hits, cần traffic cho k identifiers và tối đa p destination groups theo mô hình, không phải một lookup O(1) bất kể output.

Ví dụ: R partition theo city, có(city=HN,userID=10,email=x),(HN,11,x),(HCM,12,y). Kp=city không duy nhất, nên Ku=userID. I chứa(x,HN,10),(x,HN,11),(y,HCM,12), partition theo email. Tìm x trả hai identifiers cùng nhóm HN rồi lấy đủ hai users. Chỉ giữ(email,city) như một set sẽ gộp hai x và làm mất identity. Đổi email user10 từ x sang z cần xóa entry cũ và thêm entry mới, có thể sang partition I khác; muốn synchronous contract phải commit base/index atomic bằng protocol phù hợp như AD50, hoặc công bố async freshness rõ.

Nếu index cập nhật async, query contract có thể cho stale results hoặc cần verify base version trước khi trả và cơ chế bù entry thiếu. Verify chỉ loại ghost, không tự tìm được row thiếu index. Vì vậy lọc lại base chưa chứng minh completeness của global index async.

Parallel index creation thường scan base, build partitioned sorted runs hoặc hash buckets, rồi publish index khi đã xử lý đúng delta/transaction boundary. Cho query dùng index đang build mà không theo dõi writes xuất hiện giữa chừng có thể bỏ row. Thuật toán online cần phối hợp snapshot và change capture hoặc protocol tương đương; một vòng scan nền chưa đủ.

## Key-value API không có nghĩa không có schema

Key có encoding, ordering và identity. Value có thể là bytes, document hoặc structured record; application vẫn cần schema/version và validation. GET/PUT/DELETE trên một key không tự cho JOIN, GROUP BY hoặc constraint liên key như hệ relational. Batch API có thể chỉ batch network, không phải atomic transaction; đề bài phải chỉ đúng bảo đảm.

Ordered key scan cho range query khi key prefix phù hợp. Ví dụ `(customerID, reverseTimestamp, orderID)` gom đơn theo khách và sort thời gian trong khách; query toàn cục theo ngày cần range/fanout/index khác. Encoding phải bảo toàn thứ tự logic; ghép số thành chuỗi có thể xếp "10" trước "2" nếu không có quy ước phù hợp.

Local storage có thể dùng LSM, memtable, WAL, Bloom filter, block cache và compaction. Mỗi tầng đổi chi phí đọc/ghi/không gian theo AD31, không bảo đảm mọi GET là O(1). Remote GET còn chi phí route/network/replica lag; range query có thể đi qua nhiều partition.

## Compare-and-set và transaction scope

CAS nhận expected version/value và new value, chỉ ghi khi hiện trạng khớp. Nó giải một guard trên một key nếu kiểm và update atomic; GET trước PUT không điều kiện không tương đương. Version đơn điệu tránh một số ABA khi value đổi A→B→A nhưng lịch sử đã khác.

Ví dụ 3: hai client GET stock=10, đều PUT 9 làm mất một lần giảm. CAS từ (version7,stock10) tới (version8,stock9) cho một bên thắng; bên kia đọc lại state rồi quyết định. Nếu nghiệp vụ cần giảm stock và tạo chỗ đặt tại key khác, CAS stock riêng chưa chứng minh chỗ đặt tồn tại đúng một lần. Cần atomic batch/transaction, idempotent workflow hoặc invariant model riêng.

## Triển khai không có declarative query

Ứng dụng có thể tự quản lý multiple indexes, denormalized views và join ở client/service. Application chịu trách nhiệm update fanout, retry, version migration và garbage collection. API đơn giản không tự làm workload đơn giản.

Lập access pattern table trước khi chọn keys: point lookup, range scan, aggregate, relation lookup, write invariants và freshness. Dữ liệu gần nhau giúp đọc nhưng có thể tạo hot partition. Caching, batching, prefetch và compression giảm một số chi phí nhưng cần giữ key/visibility contract; cache invalidation vẫn có chi phí và quy tắc riêng.

## Một đường đọc và ghi của distributed file system

Thiết kế HDFS/GFS được mô tả trong nguồn tách namespace/metadata khỏi data blocks. NameNode giữ tên thư mục/file và danh sách block IDs, mỗi block có các replica locations; DataNode ánh xạ block ID tới file/storage local. Client open file hỏi NameNode một lần cho manifest rồi đọc trực tiếp các DataNode. Data không nhất thiết chảy qua NameNode. Khi DataNode không trả lời, client thử replica khác có version hợp lệ theo contract.

Ví dụ model file 160 MiB, block 64 MiB có ba blocks 64,64,32 MiB. Nếu mỗi block có ba replicas thì payload được lưu là 480 MiB, bỏ metadata/padding. Giữ metadata trong RAM giúp lookup nhanh nhưng tạo giới hạn số files/blocks. Một triệu files 1 KiB vẫn cần một triệu file entries và ít nhất một triệu block identities trong model không packing; tăng block size không làm mất file entry. Vì vậy DFS tối ưu cho files lớn khác KV store tối ưu cho rất nhiều items nhỏ. Các số block size ở đây là fixture học, không cấu hình mặc định hiện hành.

Write model gồm NameNode cấp block và chọn replica locations, ghi metadata, trả mapping; client gửi data theo pipeline tới replicas; ACK thành công phải theo số bản bền mà contract yêu cầu. Nếu B,C cùng rack còn A ở rack khác, có thể gửi A→B rồi B→C để giảm hai lượt cross-rack thành một lượt payload cross-rack. Khi B chưa ACK mà A đã ghi, không được báo “mọi replica đã nhận”. Recovery phải phân biệt append hoàn chỉnh/incomplete bằng version/sequence và dọn phần dở theo protocol. Write-once/read-many trong thiết kế sách cho phép append rồi đọc file đã hoàn tất/close, tránh sửa tùy ý block đang phục vụ. Không suy mọi DFS hiện hành có đúng giới hạn đó; API khác phải khai báo visibility/update/append riêng. Mutable rows thường phù hợp hơn với KV/database có transaction contract cần thiết.

## Biểu diễn sparse columns, versions và column families

KV có thể giữ bytes không diễn giải, document JSON có field tùy chọn, schema cố định, hoặc wide-column rows với tập cột khác nhau từng row. Trong model wide-column, key logic có thể là `(rowID, columnName, version)`. Ví dụ `(u7,name,10)=An`, `(u7,email,11)=a@example`, `(u8,name,10)=Binh`; u8 không có email là thiếu field, không bắt buộc tương đương một SQL NULL đã lưu. `get(u7,email,11)` chỉ đọc một thuộc tính; prefix scan u7 lấy các thuộc tính của u7; request latest chọn version hợp lệ cao nhất theo API. Timestamp client không tự là thứ tự commit toàn hệ.

Sắp key theo rowID làm các thuộc tính một row gần nhau. Với URL, đảo thứ tự domain từ `www.cs.example.edu/p` thành `edu.example.cs.www/p` gom các trang cùng domain/prefix. Nếu lưu riêng từng column, scan một column không kéo mọi column khác. Column family gom những cột thường được đọc cùng nhau, chẳng hạn `(name,email)` và một family riêng cho blob ảnh; nó đổi số lần đọc lấy lượng bytes không cần. Family là bố trí storage logic của model, khác việc nói chung mọi wide-column store đều là analytical column store.

## Tablet server, master và route bị cũ

Master/controller giữ range→tablet→replicas→current tablet server và làm reassignment/load balancing. Tablet server phục vụ requests của tablet; master không cần chuyển mọi GET. Client library cache partition map hoặc router layer giữ bản copy để route song song. Khi server đích nhận request theo epoch cũ sau split/move, nó trả stale-route/redirect; client/router lấy mapping mới rồi retry cùng logical request ID. Retry có hạn và deadline; một vòng redirect không giới hạn che lỗi metadata thay vì phục hồi.

```text
read(key, deadline):
    while before(deadline):
        tablet, owner, epoch = cached_or_fresh_mapping(key)
        reply = owner.GET(key, epoch)
        if reply is valid: return reply
        if reply is stale_route: invalidate_mapping_for(key); continue
        apply_declared_retry_or_error_policy(reply)
    return timeout
```

Nếu mapping cũ `k≥50→T1/B` nhưng split thành `[50,80)→T1/B`, `[80,+∞)→T2/C`, GET(90) tới B phải refresh và đi C; GET(70) vẫn hợp lệ tại B. PUT retry cần dedup/idempotent API thích hợp, vì timeout có thể xảy ra sau khi lần trước đã ghi. Routing đúng không tự cho exactly-once effect.

Geographic replicas có hai mục tiêu: chịu site failure và đặt bản gần người đọc. Nếu local update ACK trước khi remote replica nhận, site local mất hoàn toàn có thể mất update đã ACK theo contract local-durable. Nếu cần remote-durable trước ACK, request phải đợi xác nhận phù hợp qua WAN. Cho một model RTT remote 70 ms và local work 5 ms nối tiếp, phần đường ấy ít nhất 75 ms; async local có thể tránh chờ WAN nhưng đổi RPO/freshness. Cần ghi ACK domain cụ thể, không dùng chung nhãn “replicated”.

## Immutable files, WAL và khôi phục tablet

B+ tree thường sửa page tại chỗ nên không đặt nguyên cách ấy lên API chỉ cho tạo immutable file. LSM ghi memtable rồi tạo sorted run mới và merge sang run mới; không sửa run cũ, nên phù hợp immutable storage. Đây là lý do cấu trúc trong §21.7.2.2 nối với AD31, không phải tuyên bố mọi KV hiện nay dùng cùng engine.

Model recovery của một tablet giữ checkpoint/run chứa state tới LSN 40 và replicated WAL chứa 41,42. Tablet server mới có quyền epoch mới phải tìm đúng checkpoint và committed log prefix, replay 41,42 theo thứ tự/idempotency contract, rồi mới phục vụ. Nếu run có balance 100, record 41 là `+20`, 42 là `−5`, state phục hồi là 115. Đọc ngay 100 làm stale read; replay `+20` hai lần làm 135. Có thể dùng pageLSN/operation identity hoặc afterimage/version phù hợp để replay không lặp hiệu ứng. Log cần sống sót cùng failure domain được hứa; memtable nằm trong RAM node chết chưa phải bản bền.

Mất log của một tablet có thể khác với mất mapping master. Replication do DFS đảm trách hoặc do KV tự làm là hai bố trí khác nhau; dù bố trí nào cũng cần log/state có thể khôi phục và loại partial append bằng sequence/version protocol. Liveness còn phụ thuộc replica/log hợp lệ và authority mới có thể hình thành; source summary không cho proof rằng cứ còn một máy online thì hệ phục vụ được.

## Atomic một row chưa bảo vệ một invariant nhiều row

Giả sử hai rows `doctorA=on`, `doctorB=on`, invariant ít nhất một người trực. T1 đọc B=on rồi atomic PUT A=off; T2 đọc A=on trước PUT của T1 rồi atomic PUT B=off. Mỗi PUT riêng lẻ atomic và mọi update trên từng row được tuần tự hóa, nhưng cuối cùng cả hai off. Không tồn tại thứ tự serial của hai transaction có cùng kết quả nếu mỗi transaction chỉ nghỉ khi thấy người kia on. Muốn bảo vệ invariant phải có transaction nhiều row hoặc đổi model để guard/state cùng một atomic scope. Atomic increment tránh lost increment trên một field nhưng không sửa invariant nhiều row này.

Atomic batch nhiều cột trong **một row** cũng khác batch nhiều row. Synchronous secondary-index maintenance cần base/index cùng commit contract; deferred maintenance chỉ cho freshness đã công bố. Các tên sản phẩm trong sách phản ánh tính năng lúc viết; bài học xét API contract rõ và không dùng danh sách 2019 để phủ định hỗ trợ transaction của sản phẩm hiện hành.

## Join ở lúc đọc hoặc ở lúc ghi

Một mạng xã hội có U theo dõi A,B. Read-time join: GET danh sách follow rồi GET các posts gần đây của A,B, hợp/sort thành feed; chi phí đọc tăng theo số người theo dõi. Write-time materialization: A đăng post p thì gửi update tới feed từng follower; U đọc một feed đã gom sẵn. Ví dụ A có 1.000 followers, mỗi người đọc feed 20 lần trước post tiếp: read-time có thể đọc lại thông tin A nhiều lần; write-time tạo khoảng 1.000 fanout updates và lưu thêm references. Nếu A có hàng triệu followers còn ít người đọc, fanout có thể đắt hơn. Unfollow/delete/privacy change cần sửa materialized state hoặc lọc theo contract, không chỉ thêm posts.

Colocate các rows cùng entity group như customer và orders theo customerID giúp local query/transaction nếu API hỗ trợ phạm vi ấy; query theo ngày vẫn có thể fanout. Stored function chạy gần tablet/entity group có thể trả summary 100 bytes thay vì chuyển blob 1 MiB về client, nhưng tốn CPU server và không tự được quyền chạm tùy ý mọi partition atomic. TTL/version retention giảm storage bằng loại phiên bản cũ; nếu checkpoint/replay hay query còn cần version đã xóa thì phải có retention contract phù hợp.

## Luyện tập

1. Thiết kế read file hai chunks sao cho contract snapshot được kiểm, với replica của một chunk bị stale. Nêu version/cut, checks và retry; không chỉ kiểm checksum.
2. Base partition theo userID, global email index cập nhật async. Cho một ca ghost và một ca missing entry; vì sao verify base chỉ giải một phía?
3. Dùng CAS version để giảm stock với hai request concurrent và một retry. Nêu post-state và ca ABA nếu chỉ so value.
4. Thiết kế key schema cho orders tra theo khách và thời gian. Thêm query toàn cục không được schema ấy phục vụ tốt; đề xuất index/materialized view cùng write/freshness contract.

5. File 150 MiB dùng block 64 MiB và 3 replicas cần bao nhiêu block identities/payload MiB? Trace open/read/write, phân biệt metadata path và data path. Vì sao một triệu files rất nhỏ vẫn gây áp lực NameNode?
6. Thiết kế keys cho u1 có name và email hai versions, u2 chỉ có name. Trace prefix/latest read, phân biệt missing field/NULL và chọn column families khi ảnh lớn ít đọc. Giải thích LSM phù hợp immutable file hơn sửa B+ page tại chỗ.
7. Cached route k≥40 tới B nhưng split tại 75 chuyển phần trên sang C. Trace GET(80) và GET(60), rồi xét PUT timeout sau commit. Nếu local ACK trước remote copy và cả site local mất, điều gì có thể mất? So ACK remote-durable theo RTT model 50 ms+local 4 ms.
8. Checkpoint balance 200 tới LSN 10, log committed 11:+30,12:−8. Trace recovery và một lần replay trùng. Nêu metadata/epoch, log durability và điều kiện trước khi phục vụ.
9. Dựng lịch hai doctors từ on/on thành off/off với PUT atomic từng row. Chứng minh vì sao transaction serial theo guard không thể cho kết quả ấy; đề xuất atomic scope đủ.
10. Một author có 500 followers; mỗi người đọc 10 lần giữa hai posts. So fanout-on-read và fanout-on-write, thêm một privacy deletion. Khi nào dùng entity group, stored summary và TTL sẽ giảm bytes mà vẫn giữ đúng contract?
11. Base R chia theo city có hai users cùng city=HN. So lookup city=HN bằng global primary index theo nghĩa trong nguồn với lookup email=x bằng global secondary index. Cần giữ identity nào để không gộp hai users? Hash city có tự prune một range city không?

## Gợi ý

Mức 1: dữ liệu ở đúng chunk chưa nói các chunk cùng snapshot. Global index có thể thiếu row đúng, không chỉ chứa row sai.

Mức 2: CAS và update version phải cùng atomic operation. Một network batch không tự bảo đảm atomic khi hai PUT tới hai node.

## Đáp án và lập luận

1. Cần file manifest/snapshot identity cùng version tương ứng mỗi chunk; chọn replica chứa đúng version, verify bytes/status và retry hoặc trả lỗi khi thiếu đầu vào hợp lệ. Không trả mix version dưới nhãn snapshot.
2. Ghost: email cũ vẫn trỏ tới user đã đổi email, base check loại được. Missing: user đã có email mới nhưng index chưa có, query index không tìm ra để verify. Completeness cần protocol update/snapshot/delta hoặc chấp nhận eventual contract rõ.
3. Một CAS thắng version7→8; client còn lại bị reject, đọc lại và có thể giảm tiếp stock tới 8 ở version9 nếu guard vẫn hợp lệ. Retry nghiệp vụ đã thành công cần idempotency để không giảm thêm. ABA: value10→9→10 có version khác; chỉ so value bỏ qua lịch sử đã diễn ra.
4. Chấp nhận schema có encoding/ordering được định nghĩa đủ. Global query theo ngày có thể dùng index ngày rồi tới khách/orderID hoặc aggregate view. Cần quy tắc cập nhật, freshness và repair, không chỉ vẽ thêm index.

5. Ba blocks 64,64,22 MiB; payload 450 MiB với ba bản, bỏ padding/metadata. NameNode trả block map/replica locations; client đọc data trực tiếp DataNode và thử replica hợp lệ khác khi lỗi. Write cấp metadata rồi gửi replicas/pipeline, ACK theo durability contract. Nhiều files nhỏ vẫn có file entries/block identities; block size lớn không xóa metadata mỗi file.
6. Ví dụ (u1,name,1), (u1,email,1), (u1,email,2), (u2,name,1); prefix u1 lấy các columns/versions theo API, latest email chọn version 2 hợp lệ. u2 thiếu email chưa tự đồng nghĩa NULL. Gom name/email cùng family và ảnh riêng tránh kéo blob khi đọc profile ngắn. LSM tạo run mới/merge mới nên không cần sửa file cũ; B+ in-place update cần lớp storage hỗ trợ ghi tương ứng.
7. GET(80) tới B bị stale-route, refresh rồi tới C; GET(60) vẫn B. PUT timeout không biết chưa ghi hay đã ghi, retry cần identity/dedup theo contract. Async có thể mất update mới chỉ bền local khi cả site local mất; remote-durable phải chờ đúng replica/log xác nhận, phần path đề ít nhất 54 ms. Không suy toàn latency chỉ có 54 ms.
8. Phục hồi 200→230→222. Áp +30 hai lần thành 252, sai; replay cần last-applied/version hoặc operation identity thích hợp. Có quyền epoch mới/fence owner cũ, checkpoint đúng cut và log committed bền đủ rồi mới phục vụ; không lấy việc node vừa online làm bằng chứng recovery xong.
9. T1 đọc B on; T2 đọc A on; T1 PUT A off; T2 PUT B off. Nếu T1 trước T2 trong serial, T2 thấy A off và không nghỉ; thứ tự ngược lại tương tự. Cần transaction đọc/ghi hai rows với isolation đủ hoặc một record chung chứa trạng thái/guard atomic; CAS một doctor riêng vẫn chưa kiểm guard của doctor kia.
10. Read-time phải ghép posts theo 500×10=5.000 lượt đọc feed của followers trong cửa sổ, nhưng số GET thật còn batching/cache; write-time tạo khoảng 500 feed updates mỗi post rồi các feed reads đơn giản hơn. Privacy/delete đòi xóa/verify references theo freshness contract. Entity group gom dữ liệu cùng access key; stored summary giảm chuyển blob nếu tính server hợp lệ; TTL chỉ xóa versions ngoài retention của query/replay. Chấm theo bytes/workload/semantics đã khai báo, không chọn fanout theo khẩu hiệu.
11. City=HN dùng partition function chọn owner rồi local city index lấy đủ hai users; city không phải unique key vẫn dùng được scheme này. Email=x dùng relation I partition theo email, entries giữ (email,city,userID), rồi group identifiers theo city và lookup base bằng (city,userID). Thiếu userID có thể gộp hai users HN. Hash không giữ thứ tự city nên range trên city thường fanout nếu không có metadata/index khác; range partition mới cho prune theo các khoảng.

## Biến thể và cách kiểm

Model giữ version, directory cache, owner và message IDs; có stale route, duplicate append và CAS race. Chấm access patterns/invariants theo API contract. GET/PUT mẫu là pseudocode của model; không nhận đã chạy trên vendor KV server.

## Học trên web

Người học gửi API request qua form/editor và xem metadata/data path. Native connector được cấp theo bài ở backend; không yêu cầu cài DFS/KV. Đổi membership hoặc repair chạy trong sandbox riêng và có quota.

## Nguồn và đối chiếu

DSC7e §21.5–21.7. AD47 dạy partitioning/migration, AD31 dạy LSM, AD50–AD52 dạy transaction/consensus. Không gán cho API KV chung một bảo đảm atomic thiếu trong contract.
